# 执行器契约

> 所有执行器实现的统一 `Executor` trait。不因节点来源不同而分裂。

## 层归属

- **层:** Layer 4 范畴(Runtime 的下游服务),但逻辑上独立于 Runtime——执行器本身不持有 Runtime 状态
- **上游:** Runtime(接收 `ExecutionRequest`)
- **下游:** Value(通过 `Materializable` 协议)、底层后端(GPU / Python / HTTP)

---

## 定义

执行器是 **接收一次执行请求并返回结果的模块**。它回答:

- 给定 `CapabilityId` + `ExecutionRequest`,我能产出 `ExecutionOutputs` 吗?
- 我支持哪些 Capability?

它**不**回答:

- 是否需要重算? → Planner
- 是否缓存? → Runtime
- 是否写 artifact? → Runtime
- 用户可见结果历史归谁? → Runtime + ArtifactManager;执行器只返回本次结果

---

## 三类执行来源(targetv2 决策)

同一个 `Executor` trait 承载三类首版一等执行来源:

1. **图形处理执行器**: 本地、确定性、适合预览,例如 blur、grade、composite。
2. **可控 Python 后端执行器**: 底层工作流节点,例如 `load_checkpoint`、`clip_text_encode`、`ksampler`、`vae_decode`。本地 / 远端只是部署位置差异,不改变节点定义。
3. **云端 API 执行器**: 黑盒任务节点,例如视频生成、图像生成、背景移除。输出接口必须稳定、少而关键。

**固定规则:**

- 三类来源统一通过 `NodeRegistry` 注册节点,通过 `CapabilityRegistry` 路由执行器。
- 若同种能力可由不同后端执行,用户层面优先显式区分节点来源,不是在同一节点里自动路由。
- API 参数采用"共同核心参数 + provider 专属扩展参数"的分层模式。
- 执行器可以持有内部状态,但节点对外仍按当前 `CookingContext` 求值。
- 执行器不拥有用户可见输出历史;API 节点原生历史面板与显式 `artifact_manager` 节点共享 Runtime / ArtifactManager 的历史抽象。

## Executor trait(targetv2 修订版)

```rust
trait Executor: Send + Sync {
    /// 静态声明: 本执行器提供哪些 Capability
    /// 启动时调用一次,之后不再调
    fn provides(&self) -> Vec<Capability>;

    /// 执行一次请求
    /// cap_id 指明使用哪个 Capability(一个执行器可能提供多个)
    fn execute(
        &self,
        cap_id: &CapabilityId,
        req: ExecutionRequest,
    ) -> Result<ExecutionOutputs, ExecutorError>;

    /// Plan 开始执行前,Runtime 调用一次(targetv2 M5 新增)
    /// 用途: 打开跨 execute() 的资源(视频 encoder、temp file、模型 warm-up)
    /// default no-op
    fn on_plan_started(&self, ctx: &PlanLifecycleContext) -> Result<(), ExecutorError> {
        Ok(())
    }

    /// Plan 完成后,Runtime 调用一次(无论成功/失败/取消,targetv2 M5 新增)
    /// 用途: 关闭跨 execute() 的资源(encoder.finalize、清理 temp、释放 GPU 缓存)
    /// default no-op
    fn on_plan_finished(&self, ctx: &PlanLifecycleContext, status: ExecutionTerminalStatus) {
        // no-op
    }

    /// 健康检查,可选
    fn health(&self) -> HealthStatus {
        HealthStatus::Healthy
    }

    /// 声明本执行器偏好的局部性(可选)
    fn locality_profile(&self) -> LocalityProfile {
        LocalityProfile::Any
    }
}
```

**与 target 的差异:**

| 字段 | target | targetv2 |
|------|--------|---------|
| `provides()` | 不存在 | **新增** |
| `execute()` 签名 | `execute(req) -> ...` | `execute(cap_id, req) -> ...` —— **增加 cap_id 参数** |
| `on_plan_started()` / `on_plan_finished()` | 不存在 | **targetv2 M5 新增**——plan-level lifecycle hooks |
| `health()` | 有 | 保留 |
| `locality_profile()` | 不存在 | **新增**(可选) |

## 核心约束

### 1. 输出无落盘权限(但内部资源管理允许)

执行器 **对"输出"无落盘权限**:

- **不得**把 `ExecutionOutputs.values` 写入用户可见的磁盘位置(那是 Runtime + ArtifactManager 的职责)
- **不得**把执行结果作为 "外部 artifact" 持久化(除非声明了 `SideEffect::FileWrite(...)` 的 Capability,如 `save_video`)
- **不得**修改数据库
- **不得**发送 HTTP POST(除非声明了 `SideEffect::NetworkCall(...)`)

但执行器**允许**管理"内部资源"(targetv2 M6):

- 打开 video decoder/encoder 句柄,跨 execute() 复用
- 加载 AI 模型权重到 GPU,跨 execute() 复用
- **持久化"内部 cache"到磁盘**(API 调用结果、模型权重、解码器位置等)—— 详见 §长寿命内部状态

**判据(targetv2 关键区分):**

| 数据流向 | 是否允许 |
|---------|---------|
| ExecutionOutputs → 用户文件 | ❌ 禁止(归 Runtime / ArtifactManager) |
| ExecutionOutputs → 通过 `save_video` 等 sideeffect 节点写入 | ✅ 允许(显式声明的副作用) |
| 执行器内部 → 自己的资源 cache(decoder pool / model weights / API results) | ✅ 允许(内部资源管理) |
| 执行器内部 → 持久化到 `~/.cache/nodeimg/<executor>/`(跨 session disk cache) | ✅ 允许(M6) |

**判据的本质:** 数据**流出执行器边界**就是"输出"(由 Runtime 管),数据**留在执行器内部 / 自己管理的命名空间内**就是"内部资源"(执行器自管)。

**例外: 导出型节点**

`save_image` 等"文件输出"节点的执行器**必须**在 `provides()` 中声明:

```rust
Capability {
    id: "raster.save",
    version: 0,
    input_types: vec![DataType::Atomic(AtomicType::Image)],
    output_types: vec![DataType::Atomic(AtomicType::Path)],
    side_effects: vec![SideEffect::FileWrite(PathPattern::any_local())],
}
```

这是结构化的权限声明——没有声明就不能写。

### 2. 接受 fidelity 分支,并诚实报告 fidelity_achieved

执行器**必须**处理 `ExecutionRequest.fidelity: EvaluationFidelity`,并在 `ExecutionOutputs` 中**诚实报告**实际达到的精度:

```rust
fn execute(&self, cap_id, req) -> Result<ExecutionOutputs, ExecutorError> {
    let fidelity_achieved = match req.fidelity {
        EvaluationFidelity::Preview { max_side, precision } => {
            if self.supports_preview_downsample() {
                // 降采样执行,报告实际精度
                let result = self.execute_downsampled(max_side, precision, req);
                EvaluationFidelity::Preview { max_side, precision }
            } else {
                // 首版允许忽略 hint,全精度执行——但必须诚实报告
                let result = self.execute_full(req);
                EvaluationFidelity::Full  // 诚实: 我没降级
            }
        }
        EvaluationFidelity::Full => {
            let result = self.execute_full(req);
            EvaluationFidelity::Full
        }
    };

    Ok(ExecutionOutputs {
        values: result_map,
        fidelity_achieved,  // 必填字段
    })
}
```

**约束:**

- 首版允许 Preview 模式**忽略** hint(行为等同 Full)—— 但**必须**在 `fidelity_achieved` 中诚实报告为 `Full`
- Runtime 看到 `fidelity_achieved == Full`(即使请求是 Preview)时,会**把结果写入正式 cache**,避免双倍计算(见 `4.1.2-runtime.md` 流程 1b)
- Full 模式下**绝不**可以偷偷降级(`fidelity_achieved` 不能是 Preview)
- 执行器可以**忽略** Preview 的 `max_side` / `precision` 提示,但**不得**谎报 fidelity_achieved——这是 cache 正确性的前提

**诚实报告原则:**

- 执行器做了降采样 → 报告 `Preview { max_side_used, precision_used }`
- 执行器忽略 hint 全精度算 → 报告 `Full`
- **谎报的后果:** Runtime 会把不完整结果当作 Full 写入正式 cache,污染后续 Full 请求的命中——这是静默数据损坏的典型场景

### 3. 通过 Materializable 获取 Value

执行器**不得**直接访问 `ImageValue.cpu` / `ImageValue.gpu` 等内部字段。必须通过 `Materializable::materialize(target)`:

```rust
fn execute(&self, cap_id, req) -> Result<...> {
    let image: &ImageValue = req.inputs.get_image("in")?;
    let gpu_tex = image.materialize(MaterializationTarget::GpuResident)?;
    // ...
}
```

**可用的 target 变体:**
- `MaterializationTarget::Local` —— 进程堆(对 Image 是 CPU bitmap,对 Audio 是 PCM buffer,对 Vector 是路径数据)
- `MaterializationTarget::GpuResident` —— GPU 资源(对 Image 是 texture,对 Mesh 是 vertex buffer)
- `MaterializationTarget::DiskStreaming` —— `[占位]`
- `MaterializationTarget::RemoteRef` —— `[占位]`

这是真源 ③ 的 Opaque handle 约束(见 `0.1.5-value-materialization.md`)。

### 4. 接受并响应 CancelToken

执行器**应该**定期检查 `req.cancel_token.is_cancelled()`。长时间执行的执行器(>100ms)**必须**检查。

```rust
fn execute(&self, cap_id, req) -> Result<...> {
    for step in steps {
        if req.cancel_token.is_cancelled() {
            return Err(ExecutorError::Cancelled);
        }
        // ...
    }
    Ok(outputs)
}
```

### 5. 通过 ProgressSink 报告进度

执行器**可以**通过 `req.progress_sink` 报告进度。报告不是强制的,但 AI / API 执行器**应该**报告。

```rust
req.progress_sink.report(ExecutorProgressEvent::Fraction {
    current: step,
    total: total_steps,
});
```

## 长寿命内部状态(targetv2 M6 / M5)

### 内存内资源池(已有模式,targetv2 明文化)

执行器**允许**持有跨 `execute()` 调用的内存内资源:

```rust
struct VideoLoadExecutor {
    /// 每个文件一个长寿命解码器
    /// 顺序访问时(frame 0, 1, 2, ...)解码器无须 seek,性能最佳
    decoder_pool: Mutex<HashMap<PathBuf, VideoDecoder>>,
}

impl Executor for VideoLoadExecutor {
    fn execute(&self, cap_id, req) -> Result<...> {
        let path = req.params.get("path").unwrap();
        let frame = req.cooking_context.dimensions["frame"];

        let mut pool = self.decoder_pool.lock();
        let decoder = pool.entry(path.clone()).or_insert_with(|| open_video(path));

        let image = decoder.decode_frame(frame);  // 内部维护 seek 状态
        Ok(ExecutionOutputs { values: hashmap!{ "out" => Value::Image(image) }, ... })
    }
}
```

**典型场景:**

- 视频 decoder pool(`load_video`)
- 视频 encoder(`save_video`,但需 lifecycle hooks 管理 finalize)
- AI 模型权重缓存(`sdxl_inference`)
- GPU pipeline / shader 编译结果
- 流体模拟的 velocity field 状态(`pixel_fluid_animation`)

### 持久化 disk cache(targetv2 M6 新增)

对于**昂贵的外部资源**(API 调用、大模型权重、长时间生成的内容),执行器可以使用**持久化 disk cache**:

```rust
struct ApiVideoGenerateExecutor {
    /// L1: 进程内缓存(快)
    in_memory: Mutex<HashMap<GenerationKey, Arc<GeneratedVideo>>>,
    /// L2: 持久化磁盘缓存路径(跨 session)
    cache_dir: PathBuf,
}

impl ApiVideoGenerateExecutor {
    pub fn new() -> Self {
        Self {
            in_memory: Default::default(),
            // 标准 cache 目录(M8 决议)
            cache_dir: nodeimg_engine::cache_dir("ai.video_generate"),
        }
    }
}

impl Executor for ApiVideoGenerateExecutor {
    fn execute(&self, cap_id, req) -> Result<ExecutionOutputs, ExecutorError> {
        let prompt = req.params.get("prompt");
        let duration = req.params.get("duration");
        let seed = req.params.get("seed");
        let frame = req.cooking_context.dimensions["frame"];

        // Cache key 完全由"输入参数"决定(无 NodeId / RunId)
        let key = GenerationKey { prompt, duration, seed };
        let key_hash = xxhash3_128(stable_serialize(&key));
        let cache_file = self.cache_dir.join(format!("{:032x}.mp4", key_hash));

        // L1: 进程内缓存
        if let Some(video) = self.in_memory.lock().get(&key) {
            return Ok(extract_frame(video, frame));
        }

        // L2: 持久化磁盘缓存
        if cache_file.exists() {
            let video = Arc::new(load_video_from_disk(&cache_file)?);
            self.in_memory.lock().insert(key.clone(), video.clone());
            return Ok(extract_frame(&video, frame));
        }

        // L3: 外部 API 调用(慢且贵)
        let video = self.call_api_blocking(&prompt, duration, seed)?;
        let video_arc = Arc::new(video);

        // 同时写入 L1 和 L2
        save_video_to_disk(&video_arc, &cache_file)?;
        self.in_memory.lock().insert(key.clone(), video_arc.clone());

        Ok(extract_frame(&video_arc, frame))
    }
}
```

### 标准 disk cache 约定(M8 决议)

所有执行器的持久化 cache 必须遵守以下约定:

| 约定 | 内容 |
|------|------|
| **目录位置** | Linux/macOS: `~/.cache/nodeimg/<executor_name>/`<br>Windows: `%LOCALAPPDATA%\nodeimg\cache\<executor_name>\`<br>用户配置可覆盖(`config.cache_dir`) |
| **命名空间** | 每个执行器有独立子目录,以 Capability id 命名(如 `ai.video_generate`、`raster.gaussian_blur` 等) |
| **Cache key** | `xxhash3_128(stable_serialize(input))`,以 hex 字符串作为文件名前缀 |
| **文件命名** | `<key_hash>.<ext>`(扩展名按内容,如 `.mp4` / `.bin` / `.json`)|
| **元数据** | 可选 `<key_hash>.meta.json`,记录创建时间、原始 input、版本 |
| **淘汰策略** | LRU 按文件 access time;默认大小限制 10GB(用户配置可覆盖)|
| **跨 session 存活** | 是 |
| **跨项目存活** | 是(同一 prompt 在不同 project 中复用同一 cache 条目) |
| **跨机器迁移** | 用户可以手动复制 `~/.cache/nodeimg/` 目录 |
| **不进项目文件** | 真源 ⑦——cache 是"跨项目持久,不进项目文件" |

### 与 ArtifactPolicy 的关系

**关键: disk cache 与 Artifact 是两个独立机制。**

| 维度 | 持久化 disk cache | Artifact |
|------|------------------|---------|
| 存放位置 | `~/.cache/nodeimg/<executor>/` | 项目文件内 / 项目级外部存储 |
| 谁管理 | 执行器自己 | ArtifactManager |
| Cache key | `(input_params)` 的 hash | `(NodeId, ExecSignature)` |
| 跨项目复用 | ✅ 是 | ❌ 否(项目绑定) |
| 跨机器迁移 | 复制 cache 目录 | 复制项目文件 |
| 用户可见 | ❌ 通常隐藏 | ✅ 在 GUI artifact history 中可见 |
| 用户能选 | ❌ 否 | ✅ 是(`select_artifact`) |
| 进项目文件 | ❌ 否 | ✅ 通常是 |

**生成节点首版策略:**

- Python/API 生成节点每次成功 Full 执行默认进入用户可见候选历史。
- 执行器自己的 disk cache 只解决"同输入复用昂贵外部结果",不替代项目内候选历史。
- API 视频生成这类按 frame 输出的节点,artifact 粒度是"一次生成的视频候选",不是每帧一个 artifact。
- Python 底层工作流的候选历史主要通过显式 `artifact_manager` 节点暴露。
- API 黑盒任务节点可以原生自带历史面板,但底层仍使用同一 Artifact / History 抽象。

**首版 ApiVideoGenerateExecutor 的 NodeDef 使用 `ArtifactPolicy::Persist`**——Full 生成结果进入项目候选历史;执行器 disk cache 仍作为 L1/L2 内部加速层。

## 错误类型

执行器返回的错误必须是 `ExecutorError`:

```rust
enum ExecutorError {
    Unavailable { message: String },
    InvalidInput { message: String },
    Timeout,
    Cancelled,
    RuntimeFailed { message: String },
    MaterializationFailed { target: MaterializationTarget, message: String },
}
```

更细粒度的错误通过 `message` 字段承载,不作为独立变体。Runtime 负责把这些转译为用户可见的事件。

## 注册流程

执行器在引擎启动时注册:

```rust
// 启动代码
let gpu_executor = Arc::new(GpuRasterExecutor::new()?);
let python_executor = Arc::new(PythonAIExecutor::new()?);

let mut registry = CapabilityRegistry::new();
registry.register_executor(gpu_executor);
registry.register_executor(python_executor);
registry.freeze();
```

注册时 `CapabilityRegistry` 调用 `executor.provides()` 收集能力,存入路由表。

## 交互回路披露(真源 ⑧)

执行器在"参数变更 → 预览刷新"路径上的位置: **末端**——所有规划、路由、cache 查询之后。

**执行器对该路径的义务:**

- `fidelity == Preview` 时**优先**选择降级路径(即使首版允许忽略)
- 支持快速取消(`cancel_token` 检查频率高)
- 不做"热身"或"缓存预热"等阻塞初始化(这些应在首次调用时延迟完成)

**PR review 注意:**

- 任何执行器的启动开销必须明示
- 任何在 `execute()` 中引入的新的同步阻塞操作必须披露
