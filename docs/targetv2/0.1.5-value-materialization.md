# Value 物化协议

> **Tier 1 真源。** `Value` 的物化机制。受 `architecture-invariants.md` 真源 ③ 管辖。

- 本文档定义 `Materializable` 协议 + `MaterializationTarget` 枚举
- `Value` 本身**不**携带 "这是 CPU 还是 GPU" 的状态——局部性是 Runtime 的调度问题

---

## §1 动机

### §1.1 target 时代的问题

target 的 `ImageValue` 定义(见 `0.1.0-models.md` §1.1):

> `Image`:内含 CPU(`DynamicImage`) + GPU(`wgpu::Texture`)双缓存,`OnceLock` 懒转换;任一表示被首次请求时从另一表示自动转换。

这段描述是**实现细节偷跑进了规范**。它带来两个问题:

1. **局部性泄漏到 Value 里**: `Value::Image` 既是 "CPU 图像" 又是 "GPU 纹理",调用方需要知道 "现在哪边是实的"
2. **未来加 Video / Audio / VectorGraphic 时无法统一**: 每种类型都要自己定义一套 CPU/GPU/Disk 双/三缓存 → 代码层面每个执行器都要写类似的材质派发

### §1.2 核心思想

> **`Value` 是 opaque handle,通过 `Materializable` 协议按需物化到 `MaterializationTarget` 之一。**

- 节点看到的 `Value` 只是一个不透明句柄
- 执行器通过"我要 CPU 像素"或"我要 GPU 纹理"的方式**请求**物化
- Runtime 的 Materialization 调度决定**什么时候**、**用什么形式**物化
- 节点 schema、Connection 校验、`ExecSignature` **都不引用** `MaterializationTarget`

---

## §2 数据模型

### §2.1 MaterializationTarget

```rust
enum MaterializationTarget {
    Local,          // 进程堆上的"原生"表示(每个 Value 类型自己定义)
    GpuResident,    // 当前进程的 GPU 资源
    DiskStreaming,  // 磁盘上的流式引用(路径或 chunk 索引)
    RemoteRef,      // 远端(Python / 云端 / 另一个进程)
}
```

**语义抽象原则:**

MaterializationTarget 是**语义上的"在哪"**,不是"什么形式"。对不同 Value 类型,同一 target 落地为不同具体表示:

| Value 类型 | `Local` 的具体表示 | `GpuResident` 的具体表示 |
|-----------|------------------|-----------------------|
| `ImageValue` | `DynamicImage`(CPU 像素) | `wgpu::Texture`(GPU 纹理) |
| `MaskValue` | `Vec<u8>`(CPU 单通道) | `wgpu::Texture`(GPU 单通道) |
| `AudioValue` | `Vec<f32>`(PCM 样本) | (如使用 GPU 音频处理) |
| `VectorValue` | 内存中的路径数据 | 预编译的顶点缓冲 |
| `VideoValue` | 解码后的当前帧 | GPU 帧缓存 |
| `LayoutValue` | 文档树 | (通常 Local-only) |

**为什么不用 `CpuPixels` / `GpuTexture`:** 这些命名**泄漏了像素假设**——`AudioValue::materialize(CpuPixels)` 是无意义的调用。使用 `Local / GpuResident` 让每个 Value 类型定义自己的具体表示,协议本身保持通用。

**首版状态:**

| Target | 首版状态 |
|--------|---------|
| `Local` | 首版支持 |
| `GpuResident` | 首版支持(仅 ImageValue + MaskValue) |
| `DiskStreaming` | **[占位]** 未来支持(大图像 / 视频流式处理) |
| `RemoteRef` | **[占位]** 未来支持(Python VRAM Handle,与 `Value::Handle` 是两件事——前者是 Value 本身物化到远端,后者是指向远端资源的引用凭证) |

### §2.2 Materializable trait

```rust
trait Materializable {
    type Handle;

    fn materialize(
        &self,
        target: MaterializationTarget,
    ) -> Result<Self::Handle, MaterializationError>;

    fn current_targets(&self) -> Vec<MaterializationTarget>;

    fn discard(&self, target: MaterializationTarget);
}

enum MaterializationError {
    UnsupportedTarget(MaterializationTarget),
    InsufficientResources { target: MaterializationTarget },
    Failed { message: String },
}
```

**方法语义:**

- `materialize(target)`: 确保 Value 在目标位置可读。如果已经在目标位置, 返回现有 handle; 如果不在, 执行转换/上传/下载。可能耗时。
- `current_targets()`: 查询当前 Value 已经物化到哪些位置。用于调度决策。
- `discard(target)`: 提示 Runtime "这个 target 可以释放",不强制。

### §2.3 ImageValue 的首版实现

**ImageValue 是多通道 + 元数据的容器**(详细定义见 `0.1.0-models.md` §1.3.1)。Materializable 的物化粒度 = **整个 ImageValue**,不按通道独立物化。

```rust
struct ImageValue {
    inner: Arc<ImageValueInner>,
}

struct ImageValueInner {
    // 形状
    width: u32,
    height: u32,

    // 通道 + 元数据(见 0.1.0-models.md §1.3.1 / §1.3.2)
    channels: BTreeMap<ChannelId, ChannelData>,
    metadata: ImageMetadata,

    // 运行时双缓存(实现细节,不是规范)
    cpu: OnceLock<DynamicImage>,     // 首版:从 channels 构造的 CPU 合成视图
    gpu: OnceLock<wgpu::Texture>,    // 首版:从 channels 构造的 GPU 纹理
}

impl Materializable for ImageValue {
    type Handle = ImageHandle;  // 枚举,指向具体 target

    fn materialize(&self, target: MaterializationTarget) -> Result<Self::Handle, MaterializationError> {
        // 首版: 把 channels 合成为单个 DynamicImage(CPU)或 wgpu::Texture(GPU)
        // 首版默认: R/G/B/A 四通道合成为 RGBA8 或 RGBA32F 纹理
        // 多通道 EXR(如 R/G/B/A/Z/ObjectID)合成到 GPU 时:
        //   - 首版: 只上传 RGBA 通道到 Texture(Z/ObjectID 驻留 CPU,执行器按需读)
        //   - 未来: 多通道 GPU 纹理(array texture 或 multiple bind groups)
    }

    fn current_targets(&self) -> Vec<MaterializationTarget> { /* ... */ }
    fn discard(&self, target: MaterializationTarget) { /* no-op,见 §2.3 */ }
}
```

**首版简化:**

- `channels` 里只有 `R/G/B/A` 时,物化到 GPU = 标准 RGBA 纹理(和 target 时代行为一致)
- `channels` 里有额外通道(如 Z / ObjectID)时:
  - GPU 物化只上传 RGBA(常用视觉通道)
  - Z / ObjectID 保持在 CPU 端,执行器需要时从 CPU 读
  - 未来优化: 多通道 GPU 纹理支持,避免 CPU ↔ GPU 往返

**通道访问接口:**

```rust
impl ImageValue {
    /// 读取特定通道的数据(只读,返回 Arc 共享)
    pub fn channel(&self, id: &str) -> Option<&ChannelData>;

    /// 所有通道 ID 列表
    pub fn channel_ids(&self) -> Vec<&ChannelId>;

    /// 构造新 ImageValue(克隆 Arc,共享底层数据)
    pub fn with_channels(&self, new_channels: BTreeMap<ChannelId, ChannelData>) -> Self;

    /// 只读元数据
    pub fn metadata(&self) -> &ImageMetadata;

    /// 构造新 ImageValue,仅修改元数据
    pub fn with_metadata(&self, new_meta: ImageMetadata) -> Self;
}
```

**关键:** `ImageValueInner` 不是公开 API——节点和执行器通过 `ImageValue` 的方法访问,不直接访问内部字段。`inner: Arc<...>` 的结构可以自由演进。

**关键(不变):** `ImageValueInner` 的 `cpu` / `gpu` 双缓存仍然存在——这是**当前运行时表示**,不是**规范**。未来可以改成别的实现(例如只有 GPU 缓存,CPU 按需从 GPU 回读),**不影响**节点 schema、Connection 校验、ExecSignature。

### `discard` 与 `OnceLock` 的首版决议

`Materializable::discard(target)` 方法的语义是 "提示 Runtime '这个 target 可以释放,不强制'"。**但 `OnceLock` 是一次性初始化结构,不支持清除**——一旦写入,无法重新为空。

**冲突:** 如果 `ImageValueInner` 用 `OnceLock<wgpu::Texture>`,调 `discard(GpuResident)` **不能真正释放** GPU 资源——只能标记"不推荐后续使用",但 GPU 纹理仍然占用显存直到整个 `ImageValue` 被 drop。

**首版决议: discard 是 no-op(首版不真正释放 target)**

```rust
impl Materializable for ImageValue {
    fn discard(&self, _target: MaterializationTarget) {
        // 首版: no-op
        // GPU 资源随 ImageValue 整体 drop 时释放
    }
    // ...
}
```

**理由:**

- 首版不需要 GPU 预算管理——GPU 内存足够大,或者依赖 OS 级 OOM killer
- `OnceLock` 无锁读取的性能好,比 `RwLock<Option<T>>` 快
- `discard` 作为接口保留,未来需要 GPU 预算管理时再改实现

**未来演进路径:**

当 GPU 预算管理成为需求时,`ImageValueInner` 改为:

```rust
struct ImageValueInner {
    cpu: OnceLock<DynamicImage>,
    gpu: parking_lot::RwLock<Option<wgpu::Texture>>,  // 可清除
    width: u32,
    height: u32,
    format: ImageFormat,
}
```

- `cpu` 仍然是 `OnceLock`(CPU 内存不紧张)
- `gpu` 改为 `RwLock<Option<Texture>>`——`discard(GpuResident)` 把 Option 设为 None,下次 `materialize(GpuResident)` 重新上传

**这个改动属于实现演进,不影响** `Materializable` trait **接口本身**——对节点 schema、执行器、Runtime 都透明。

**其他 Value 类型的 discard:** 同样 no-op,除非该类型的资源占用特别紧张(例如大视频文件)。`MaskValue` / `AudioValue` 的首版实现沿用 no-op。

## §3 节点侧的使用模式

### §3.1 节点如何消费 Value

节点函数签名:

```rust
fn execute(
    inputs: ExecutionInputs,
    params: NodeParams,
) -> Result<ExecutionOutputs, ExecutorError>;
```

节点拿到的 `Value::Image` 是 **opaque**。它必须:

```rust
// GPU 执行器需要 GPU 纹理:
let image: &ImageValue = inputs.get_image("in")?;
let gpu_tex = image.materialize(MaterializationTarget::GpuResident)?;
// ... 运行 shader ...
let output = ImageValue::from_gpu_texture(result_tex);
Ok(outputs.set("out", Value::Image(output)))
```

```rust
// CPU 执行器需要 CPU 像素:
let image: &ImageValue = inputs.get_image("in")?;
let cpu_img = image.materialize(MaterializationTarget::Local)?;
// ... 运行 CPU 算法 ...
let output = ImageValue::from_dynamic_image(result_img);
Ok(outputs.set("out", Value::Image(output)))
```

**节点 schema 看不到 `MaterializationTarget`** —— `NodeDef.inputs` 只声明 `data_type: AtomicType::Image`, 不声明 "我要 CPU 还是 GPU"。

### §3.2 能力通过 Capability 隐式表达

执行器声明 Capability 时,隐式地表达它对 Materialization 的要求:

```rust
Capability {
    id: "raster.gaussian_blur",
    version: 0,
    input_types: vec![DataType::Atomic(AtomicType::Image)],
    output_types: vec![DataType::Atomic(AtomicType::Image)],
    side_effects: vec![SideEffect::None],
}
```

这段声明 **没有** 说 "CPU 还是 GPU"——那是执行器内部的选择。Runtime 在路由时:

1. 查 `raster.gaussian_blur` 有哪些 provider
2. 其中一个是 GPU 执行器(启动时探测到 GPU 可用)
3. 另一个是 CPU fallback 执行器
4. Runtime 按 `LocalityHint::PreferGpu` 选 GPU 执行器
5. GPU 执行器在 `execute` 时对输入 Value 调 `materialize(GpuResident)`

**核心非对称:** Capability 描述的是 "做什么",不是 "在哪做"。"在哪做" 属于 Runtime 的调度决策。

## §4 Runtime 的调度责任

Runtime(Layer 4)对 Materialization 的职责:

### §4.1 物化决策

- 执行一个节点前,Runtime **不**预先物化所有输入——让执行器自己调 `materialize()`
- Runtime 可以提供**提示**: "即将运行的执行器是 GPU 的,你可能想预上传"——但这是 advisory,不是强制

### §4.2 驻留策略

- Runtime 管理 GPU 内存预算
- 当 GPU 预算紧张时,Runtime 调 `discard(GpuResident)` 让旧 Value 释放 GPU 资源
- CPU 侧不限额(除非显式配置)

### §4.3 跨节点的 Value 共享

- 多个下游节点共享同一个 `Value::Image` 时,它们通过 `Arc` 共享 inner
- 每个下游节点分别调 `materialize()`——如果 target 相同,返回同一 handle;如果 target 不同, Runtime 会触发转换

### §4.4 preview 路径的物化优化

- preview 模式下, Runtime **可以** 只物化降采样后的版本
- 例如: preview 请求时, Runtime 先调 `materialize(GpuResident)`, 然后对 GPU 纹理做一次 downsample, 再传给执行器
- 这是一种优化,**不是**必须,首版不实现

## §5 与 ExecSignature 的非关系

**关键:** `ExecSignature` **不**引用 `MaterializationTarget`。

- 同一个 `Value::Image`,不管它当前物化为 CPU 还是 GPU,它的签名相同
- 这是真源 ③ "Value 无全局 hash" 的一部分
- 签名由**产出它的节点的 ExecSignature** 间接表达

---

## §6 与持久化的关系

`MaterializationTarget::DiskFile` 是特殊的——它让 Value 可以"落盘存活"。但这**不是** Artifact:

| 概念 | 归属 | 语义 |
|------|------|------|
| Materialization to DiskFile | Runtime 的**调度优化** | 临时磁盘缓存,可随时回收,不属于项目 |
| Artifact | Project 的**历史归档** | 用户可查看、可选用、进项目文件 |

两者不共享存储路径,不共享生命周期。

## §7 节点 schema 的禁止

**禁止在任何地方引用 `MaterializationTarget`:**

1. `NodeDef.inputs[i].data_type` → 只用 `DataType::Atomic(AtomicType::Image)`,不区分 CPU/GPU
2. `NodeDef.outputs[i].data_type` → 同上
3. `Connection` 类型校验 → 同上
4. `ParamDef.data_type` → 同上
5. `ExecSignature` 构造 → 不引用
6. Project 文件 schema → 不引用

**唯一允许的引用点:**

- 执行器内部实现
- Runtime 内部调度代码
- `Materializable` trait 本身

---

## §7.5 诚实承认: MaterializationTarget 扩展的代价

**不是"完全填槽"的部分:**

加一个新的 `MaterializationTarget` 变体(例如未来加 `SharedMemory`)**是轻破坏性变更**:

- 每个 `Value` 类型的 `Materializable` 实现需要更新一次(至少处理新 target → 返回 `UnsupportedTarget` 错误)
- 所有对 `MaterializationTarget` 做 `match` 的地方都需要编译器检查

**影响有限的原因:**

- 新变体**不影响** 节点 schema、`Connection` 校验、`ExecSignature`、`CacheKey`、`NodeDef`
- 只影响 `Materializable` 实现本身和 Runtime 的调度代码
- 单元测试可以覆盖新变体的 `UnsupportedTarget` 路径

**结论:** `MaterializationTarget` 不是完全开放集,它是**有限开放集**——扩展是可能的,但需要一次性更新所有 Value 类型的实现。文档诚实承认这一点,不标榜为"零成本扩展"。

## §8 首版落地清单

**必须实现:**

1. `Materializable` trait 定义
2. `MaterializationTarget` 枚举(至少 `Local` + `GpuResident`)
3. `ImageValue` 实现 `Materializable`
4. Runtime 代码使用 `materialize()` 方法,不直接访问 `ImageValueInner`
5. 节点 schema 不得引用 `MaterializationTarget`

**允许推迟:**

- `DiskFile` / `RemoteRef` 的具体实现
- GPU 内存预算管理
- 驻留策略调优
- preview 路径的物化优化
- 其他 Value 变体(`Mask` / `Video` / `Audio`)的 Materializable 实现
