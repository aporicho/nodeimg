# Runtime —— 执行层

> **Layer 4**。执行副作用的唯一所在地。持有 `single-flight` 全局守卫、cache 读写、artifact 写入、Materialization 调度、执行器分发、取消、进度。

## 层归属

- **层:** Layer 4(Runtime)
- **上游:** Layer 2(Planner)—— 消费 `ExecutionPlan`
- **上游:** Layer 3(CapabilityRegistry)—— 查 Capability 路由表
- **下游:** Executor 池、CacheManager、ArtifactManager、EventSystem
- **消费者:** Layer 5(Session,经 RunHandle 引用)、Layer 7(CLI / Server 直接调用)

**所有权清单:**

- 本模块拥有: `single-flight` 全局守卫、正式 cache 的写路径、artifact 写入触发、执行器调度、取消令牌、进度 sink、Materialization 调度决策、`fidelity` 分路
- 本模块引用但不拥有: `ExecutionPlan`(Planner 产出)、Capability 路由表(CapabilityRegistry)、Value 物化协议接口(Algebra Layer)
- 本模块**不**拥有: `DirtyState`(Planner)、undo 栈(Session)、preview cache(Session)、NodeDef(NodeManager)

---

## 定义

Runtime 是 **执行 `ExecutionPlan` 并产生副作用的模块**。它回答的问题:

- 这个 ExecutionPlan 能不能开始跑?(single-flight 守卫)
- 每个节点的输入从哪儿来?(cache 命中 / artifact 回源 / 上游输出)
- 每个节点让谁执行?(Capability 路由)
- 执行成功后结果写到哪?(cache + 可能的 artifact)
- 出错 / 取消 / 完成时通知谁?(events)

它**不**回答:

- 这个图的依赖顺序是什么? → Planner
- 哪个节点需要重算? → Planner(DirtyState)
- 图长什么样? → GraphController

## 职责边界

### 属于 Runtime

- **`single-flight` 全局守卫**
- `ExecutionPlan` 的消费与执行驱动
- Cache 查询、回源、写入
- Artifact 回源、写入
- 执行器分发(按 `CapabilityId` 查 `CapabilityRegistry`)
- Materialization 调度(决定 Value 何时物化到 CPU / GPU / 磁盘)
- 取消令牌的创建与传播
- 进度 sink 的广播
- `fidelity` 分路(Preview / Full 的调度差异)
- Preview 抢占 Full 的调度决策(真源 ⑧)

### 不属于 Runtime

- 执行计划生成(归 Planner)
- 脏状态(归 Planner)
- Capability 路由表的**所有权**(归 CapabilityRegistry;Runtime 只查询)
- Preview cache 的**所有权**(归 Session;Runtime 的 cache 是正式 cache)
- undo 栈(归 Session)
- 节点定义的注册(归 NodeManager)
- 图的结构(归 GraphController)

## 提供接口

```rust
trait Runtime {
    /// 尝试启动一次执行。返回 Err(RunInFlight) 如果守卫被占用
    /// 除非 fidelity 是 Preview 且当前是 Full——Preview 会抢占 Full
    fn try_start_run(
        &self,
        plan: ExecutionPlan,
        fidelity: EvaluationFidelity,
    ) -> Result<Arc<RunHandle>, RuntimeError>;

    /// 取消当前 run
    fn cancel(&self, run_id: RunId) -> Result<(), RuntimeError>;

    /// 查询当前状态
    fn get_state(&self) -> RuntimeStateSummary;

    /// 查询某次 run 的终态摘要
    fn get_result(&self, execution_id: ExecutionId) -> Option<ExecutionResultSummary>;

    /// 等待某次 run 完成(同步接口,通常只有 CLI / 测试使用)
    fn await_run(&self, run_id: RunId) -> Result<ExecutionResultSummary, RuntimeError>;
}
```

**`try_start_run` 的完整决策表:**

| 当前状态 | 新请求 fidelity | 行为 | 被抢占的 Full 去向 |
|---------|----------------|------|---------|
| `None`(空闲) | `Preview` | **直接启动** Preview | N/A |
| `None`(空闲) | `Full` | **直接启动** Full | N/A |
| `Some(current=Full)` | `Preview` | **抢占**:取消 current 整个 run,**把 current Full 的 Plan 移入 `pending_full`**,启动 Preview | Preview 完成后自动恢复 |
| `Some(current=Preview)` | `Preview` | **替换**:取消 current Preview,启动新 Preview | N/A |
| `Some(current=Full)` | `Full` | **拒绝**:返回 `RunInFlight` | N/A |
| `Some(current=Preview)` | `Full` | **排队**:不抢占 Preview,Full 放入 `pending_full`,Preview 完成后自动启动 | N/A |

**返回类型: 始终返回可追踪的句柄,不用 Err 表达"已排队":**

```rust
enum TryStartRunResult {
    /// 立即启动,返回 RunHandle
    Started(Arc<RunHandle>),

    /// 已排队,返回 pending 句柄
    /// caller 可通过 pending_id 订阅后续 ExecutionStarted 事件追踪实际启动
    Queued {
        pending_id: PendingRunId,
        reason: QueueReason,
    },
}

enum QueueReason {
    /// 排在正在运行的 Preview 之后
    BehindPreview,
}

fn try_start_run(
    &self,
    plan: ExecutionPlan,
    mode: ExecutionMode,  // targetv2: 之前是 fidelity,现在 mode 包含 fidelity
) -> Result<TryStartRunResult, RuntimeError>;
```

**ExecutionMode 与首版状态(M3 转正):**

- `ExecutionMode::OneShot { fidelity }` —— **首版完整实现**(Preview/Full)
- `ExecutionMode::Continuous { OsClock, target_fps }` —— **首版完整实现**(60fps 实时持续 cook)
- `ExecutionMode::Continuous { External(_) | DataPull(_), .. }` —— 占位,首版返回 `RuntimeError::TickSourceNotImplemented`
- 详见 `0.1.1-execution-models.md` §1.4 + 本文件 §Continuous 模式

`RuntimeError::QueuedBehindPreview` 被移除——排队不是错误,而是一种**结果**。

**新的 Runtime 错误:**

```rust
enum RuntimeError {
    RunInFlight,
    CapabilityUnavailable(CapabilityId),
    ExecutorFailed(ExecutorError),
    CachePoisoned,
    MaterializationFailed(MaterializationError),
    Cancelled,
```

**伪代码:**

```rust
fn try_start_run(&self, plan, mode) -> Result<TryStartRunResult, RuntimeError> {
    // 首版接受 OneShot 与 Continuous { OsClock, .. };
    // External / DataPull tick source 首版未实现
    match &mode {
        ExecutionMode::OneShot { fidelity } => {
            // 走 OneShot 路径(下面是 OneShot 决策表)
        }
        ExecutionMode::Continuous { tick_source: TickSource::OsClock, target_fps } => {
            // 走 Continuous 路径(见 §流程 1c)
            return self.start_continuous_run(plan, *target_fps);
        }
        ExecutionMode::Continuous { tick_source: TickSource::External(name), .. }
        | ExecutionMode::Continuous { tick_source: TickSource::DataPull(name), .. } => {
            return Err(RuntimeError::TickSourceNotImplemented(name.clone()));
        }
    }
    let mut guard = self.single_flight.lock();

    match (&guard.current, &fidelity) {
        // 空闲,直接启动
        (None, _) => {
            let handle = start(plan, fidelity);
            guard.current = Some(handle.clone());
            Ok(TryStartRunResult::Started(handle))
        }

        // 新 Preview + 当前 Full → 抢占,把 Full 移入 pending_full
        (Some(current), EvaluationFidelity::Preview { .. }) if current.is_full() => {
            // 关键: pending_full **只存 ExecutionRequest**,不存 Plan
            // 见下方"为什么 pending_full 不存 Plan"
            let preempted_request = current.original_request.clone();

            // 如果 pending_full 已有东西,说明之前有排队的 Full——
            // 被更"新"的 Full 覆盖。给被覆盖的原调用方发事件
            if let Some(existing) = self.pending_full.take() {
                publish(ExecutionReplaced {
                    pending_id: existing.pending_id,
                    reason: ReplacedByNewerFull,
                });
            }
            self.pending_full = Some(PendingFull {
                pending_id: PendingRunId::new(),
                request: preempted_request,
            });

            // 取消当前 Full 整个 run(所有 subtask)
            current.cancel_token.cancel();
            wait_for_cleanup(current);

            // 启动 Preview
            let handle = start(plan, fidelity);
            guard.current = Some(handle.clone());
            Ok(TryStartRunResult::Started(handle))
        }

        // 新 Preview + 当前 Preview → 替换当前 Preview(不影响 pending_full)
        (Some(current), EvaluationFidelity::Preview { .. }) if current.is_preview() => {
            // 注意: 不动 pending_full——它仍然是之前排队的 Full,等所有 Preview 做完后启动
            current.cancel_token.cancel();
            wait_for_cleanup(current);
            let handle = start(plan, fidelity);
            guard.current = Some(handle.clone());
            Ok(TryStartRunResult::Started(handle))
        }

        // 新 Full + 当前 Preview → 排队
        (Some(current), EvaluationFidelity::Full) if current.is_preview() => {
            // 如果 pending_full 已有东西,覆盖前给原调用方发事件
            if let Some(existing) = self.pending_full.take() {
                publish(ExecutionReplaced {
                    pending_id: existing.pending_id,
                    reason: ReplacedByNewerFull,
                });
            }
            let pending_id = PendingRunId::new();
            // 关键: 只存 request,不存 plan——恢复时重新规划
            self.pending_full = Some(PendingFull {
                pending_id,
                request: original_request,  // 调用方传入的 ExecutionRequest
            });
            Ok(TryStartRunResult::Queued {
                pending_id,
                reason: QueueReason::BehindPreview,
            })
        }

        // 新 Full + 当前 Full → 拒绝
        (Some(_), EvaluationFidelity::Full) => {
            Err(RuntimeError::RunInFlight)
        }
    }
}

/// 当前 run 结束时,检查 pending_full 是否需要启动
fn on_run_finished(&mut self) {
    self.guard.current = None;
    if let Some(pending) = self.pending_full.take() {
        // 关键: 不直接复用旧 Plan,而是**重新提交**给 Scheduler facade
        // Scheduler facade 会用**当前 Graph** 重新规划,避免 Plan 陈旧
        publish(PendingFullResubmitted {
            pending_id: pending.pending_id,
            request: pending.request.clone(),
        });
        // Scheduler facade 的事件订阅者收到此事件后,会自动调
        // scheduler.request_execution(pending.request) 重新触发执行
        // 新的 run_id 通过随后的 ExecutionStarted { from_pending_id: Some(pid) } 事件关联
    }
}
```

### 为什么 pending_full 不存 Plan

**核心原因: Graph 可能在 Preview 期间变化。**

场景:
1. 用户点"导出" → Full 开始,Plan 基于 Graph v1
2. 用户拖滑条改参数 → Graph v2,Preview 抢占 Full
3. Preview 完成
4. 如果自动启动**旧 Plan**(Plan v1)→ 用 Graph v1 的参数跑 → 产出**错误的导出结果**

**修复: pending_full 只存 ExecutionRequest(请求意图),不存 Plan。** Preview 完成后:

1. Runtime 发 `PendingFullResubmitted { pending_id, request }` 事件
2. Scheduler facade 订阅此事件,收到后调 `request_execution(request)` 重新规划
3. Scheduler facade 用**当前 Graph** 生成新 Plan
4. Runtime 启动新 Plan,事件中 `from_pending_id` 关联原 pending_id
5. 原 caller 看到 `ExecutionStarted { from_pending_id: Some(pid) }` 得知自己的 pending 变成真 run

**数据结构:**

```rust
struct PendingFull {
    pending_id: PendingRunId,
    request: ExecutionRequest,  // 只存请求意图
    // 不存 Plan——Plan 在恢复时重新规划
}
```

**如果 Request 引用的 target 在新 Graph 里已经不存在**(例如用户 Undo 删除了那个节点):

- Scheduler facade 重新规划时会发现 target 无效
- 返回 `SessionError::PlannerError(PlannerError::UpstreamMissing(...))`
- 或 `EngineError::InvalidGraph`
- 原 caller 通过错误事件得知 "你的 pending Full 已作废"

**pending_full 的可见性:**

- `get_state()` 的返回值包含 `pending_full: Option<PendingRunId>`
- caller 可通过 `pending_id` 知道自己的 Full 是否还在排队
- 订阅事件可以看到 `ExecutionStarted { from_pending_id: Some(pid) }` 得知自己的 pending 变成真 run
- `ExecutionReplaced { pending_id }` 事件通知原 caller 其 pending 已被覆盖

### pending_full 的失效场景

当以下事件发生时,**pending_full 被清空并通过事件通知原 caller**:

| 事件 | 行为 | 通知事件 |
|------|------|---------|
| `clear_cache` | 清空 pending_full(generation 会变,旧请求意图仍有效但决定不 自动继续) | `ExecutionCancelled { pending_id, reason: CacheCleared }` |
| `replace_graph` | 清空 pending_full(整图替换,原 target 可能不存在) | `ExecutionCancelled { pending_id, reason: GraphReplaced }` |
| 新 Full 请求覆盖 | 旧 pending 被新 Full 替换 | `ExecutionReplaced { pending_id, reason: ReplacedByNewerFull }` |
| Undo / Redo 导致 Graph 变更 | **不**直接清空 pending_full;但 Preview 完成后恢复时,Scheduler facade 用新图重新规划,**如果 target 无效则返回错误** | 通过重新规划的错误事件(`PlannerError::UpstreamMissing` 等) |

**关键:** `clear_cache` 和 `replace_graph` 会明确清空;Undo/Redo 不清空而是依赖"恢复时重新规划"的 fail-fast。

**抢占粒度说明:**

当 Preview 抢占 Full 时,**整个 Full run 被取消**——所有剩余 subtask 都不再执行。理由:

- Full run 的状态是"半完成",部分 subtask 跑完了,部分没跑
- 被取消的 Full 的 Plan 被**保存在 `pending_full`** 中,Preview 完成后自动恢复
- 恢复时 Runtime 重新调用这个 Plan—— Planner 已经把 Plan 变成自洽的(不依赖外部 Graph),所以可直接复用
- 重新执行时 Runtime 查正式 cache,已完成的 subtask 结果命中 cache,跳过重算
- 不需要"只取消当前 subtask"的细粒度——cache 机制承担了"已完成"的记忆

**wait_for_cleanup 的时间预算(真源 ⑧ 约束):**

`wait_for_cleanup(current)` 在 try_start_run 中是同步调用,会阻塞调用方(Session / CLI)直到当前 run 的清理完成。这**可能**成为交互回路的瓶颈,所以:

- **执行器合约(见 `4.11.2-executor-contract.md`):** 长时间执行的 executor(>100ms 执行时间)**必须**频繁检查 `cancel_token`(建议每 10ms 一次)。这让 wait_for_cleanup 在最坏情况下也只阻塞 10~50ms。
- **首版阻塞预算:** wait_for_cleanup 应在 **50ms 内** 完成(目标,非硬约束)
- **超预算处理:** 如果清理超过 100ms,Runtime 打印 warn 日志并继续等待(不强制 kill)
- **未来演进:** 如果需要真正的低延迟抢占,可以把 try_start_run 改为"立即返回 + 后台清理"——这是 Runtime 内部实现调整,不影响对外接口

**为什么首版选择同步:** 异步清理让 RunHandle 的状态机更复杂(Cancelling vs Cleaning),增加 bug 面。首版优先简单性。

**Full 排队的语义:**

- 如果 `try_start_run(plan, Full)` 返回 `Ok(TryStartRunResult::Queued { pending_id, reason })`,调用方**知道** Full 被排队了
- Runtime 内部持有 `pending_full: Option<(ExecutionPlan, EvaluationFidelity)>`
- 当前 Preview 完成时,Runtime 自动取出 `pending_full` 并启动,产生新的 `RunHandle`
- 调用方通过事件 `EventSystem` 的 `ExecutionStarted { run_id }` 得知 Full 开始
- 如果在等待期间又来了新的 Preview,新 Preview 会**替换** `pending_full`(不清除)——因为 Preview 抢占了当前执行,Full 依然等着

**简化: 首版只支持一个 pending_full 槽。多个排队的 Full 按最后一个覆盖前面的。**

## 依赖接口

### 对 CacheManager

```rust
get_result(key: &CacheKey) -> Option<Value>
put_result(key: CacheKey, value: Value) -> Result<(), CacheError>
```

**Runtime 只做读和写,不做 invalidate。**

`invalidate_subgraph` 和 `clear_all` 由 **Scheduler facade 直接调用**——它响应 `GraphChangedEvent` 时同时做两件事:
1. 通过 Planner 推导新 DirtyState
2. 直接调 `CacheManager::invalidate_subgraph(affected_nodes)`

Runtime 不关心缓存失效时机——它只在执行时读写。

**关键:** Runtime 使用的是 **正式 cache**——与 Session 的 preview cache 完全分离。Preview 模式下 Runtime **不写**正式 cache(避免污染),仅在 Full 模式下写。

```rust
resolve_artifact_for_restore(node_id, signature) -> Option<Value>
create_artifact(node_id, value, metadata) -> ArtifactId
```

**Preview 路径限制:** `fidelity == Preview` 时**不得**调用 `create_artifact`。

## 关键流程

### 流程 1: 正常执行一个 ExecutionPlan(Full 模式)

```
1. try_start_run(plan, Full)
   - 查 single_flight
   - 若需抢占(Preview 覆盖下)走抢占路径
   - 创建 RunHandle + CancelToken
   - Runtime 注入 run_id + generation
2. publish(ExecutionStarted { fidelity = Full })
3. for subtask in plan.subtasks:
    for layer in subtask.layers:
        for node in layer:  (可并行)
            a. 查正式 cache(signature → 正式 cache,generation 作为防回灌)
            b. miss → 从 artifact 回源
            c. 仍 miss → 收集 inputs(从 cache),调 Executor
            d. Executor 执行(经 CapabilityRegistry 路由,fidelity=Full 传下去)
            e. **结果写正式 cache**(关键: 仅 Full 模式)
            f. 如果 purity=Impure,写 artifact
            g. publish(NodeExecutionFinished)
4. publish(ExecutionFinished { fidelity = Full })
5. 清除 single_flight.current
6. 若 pending_full 存在,它是当前完成的 Full 本身,不处理
```

### 流程 1b: Preview 模式执行

```
1. try_start_run(plan, Preview { max_side, precision })
   - 抢占当前 run(如果有;Full 会被移入 pending_full)
   - 创建 RunHandle + CancelToken
2. publish(ExecutionStarted { fidelity = Preview })
3. for subtask in plan.subtasks:
    for layer in subtask.layers:
        for node in layer:
            a. 查正式 cache(可能命中 Full 结果——可作为 fallback)
                - 命中 Full: 调用 Runtime 内部 downsample,按 max_side 降采样
                - 返回 downsample 结果(不再执行 executor)
            b. miss → 收集 inputs,调 Executor
            c. Executor 执行(fidelity=Preview 传下去)
            d. 执行器返回 ExecutionOutputs,其中包含 fidelity_achieved 字段
            e. **根据 fidelity_achieved 决定是否写正式 cache:**
                - 若 fidelity_achieved == Full: 执行器忽略了 preview hint,产出的是全精度
                  → Runtime 把结果**写正式 cache**(不浪费计算)
                - 若 fidelity_achieved == Preview { ... }: 执行器降级了,不写正式 cache
            f. **Preview 模式永远不写 artifact**(即使 fidelity_achieved = Full)
            g. publish(NodeExecutionFinished)
            h. 通过 progress_sink 发 Preview { output, value } 事件——Session 订阅并存入 preview cache
4. publish(ExecutionFinished { fidelity = Preview })
5. 清除 single_flight.current
6. 调用 on_run_finished(),若 pending_full 存在,取出并自动启动
```

### 流程 1c: Continuous 模式执行(targetv2 M3)

Continuous 模式是 Runtime 的**长生存期 run 状态**——它进入后持续 cook 同一个 plan,直到调用方显式 stop。

```
1. try_start_run(plan, Continuous { OsClock, target_fps: 60.0 })
   - 检查 single_flight: 必须空闲(否则按抢占规则处理)
   - 创建 RunHandle (state = Running, 标记为 Continuous run)
   - 调用所有用到的 Executor 的 on_plan_started(plan_lifecycle_ctx)  ← M5 lifecycle hook
   - 启动 tick loop 后台线程
2. publish(ExecutionStarted { run_id, fidelity, mode = Continuous })
3. 进入 tick loop:
   loop {
       let tick_start = Instant::now();

       // 计算当前 cooking_context(从时钟驱动)
       let elapsed_seconds = (tick_start - run_start).as_secs_f32();
       let current_frame = (elapsed_seconds * source_fps).floor() as u64;
       let context = CookingContext {
           dimensions: hashmap!{ "frame".to_string() => DimensionValue::Int(current_frame % loop_length) }
       };

       // 用最新 plan + 这一帧 context 执行
       for subtask in &plan.subtasks {
           // (subtask 通常是按 plan 中的拓扑层级)
           for layer in &subtask.layers {
               for node in layer {
                   if !node.realtime_capable {
                       // 慢节点: 只读 cache,不重新执行(关键 M3 行为)
                       if let Some(cached) = cache.get(&node.exec_signature) {
                           insert_into_pipeline(node.id, cached);
                       } else {
                           publish(NodeMissingInContinuous { run_id, node_id: node.id });
                           insert_into_pipeline(node.id, placeholder_image());  // 黑帧
                       }
                   } else {
                       // 实时节点: 命中 cache 跳过, 未命中执行
                       let value = if let Some(cached) = cache.get(&node.exec_signature) {
                           cached
                       } else {
                           let result = execute_via_executor(node, current_context);
                           cache.put(node.exec_signature.clone(), result.clone());
                           result
                       };
                       insert_into_pipeline(node.id, value);
                   }
               }
           }
       }

       // 把 preview_output 节点的结果通过 progress_sink 送给 Session
       publish_preview_frame_event(run_id, current_frame);

       // 等到下一 tick
       let tick_duration = Duration::from_secs_f32(1.0 / target_fps);
       let elapsed = tick_start.elapsed();
       if elapsed < tick_duration {
           sleep(tick_duration - elapsed);
       } else {
           publish(ContinuousTickOverrun { run_id, target_ms: tick_duration.as_millis(), actual_ms: elapsed.as_millis() });
       }

       // 检查取消信号
       if cancel_token.is_cancelled() { break; }
   }
4. publish(ExecutionFinished { run_id, status: Cancelled, mode = Continuous })
5. 调用所有用到的 Executor 的 on_plan_finished(plan_lifecycle_ctx, status)  ← M5 lifecycle hook
6. 清除 single_flight.current
```

### Continuous 模式与 GraphChangedEvent

用户在 Continuous 模式运行期间改图(调参数、加节点等):

1. GraphController → `GraphChangedEvent`
2. Scheduler facade 收到事件 → 调 `Planner::propagate_dirty` → 更新 DirtyState
3. **重新规划:** Scheduler facade 调 `Planner::plan` 生成新 plan
4. **替换当前 Continuous run 的 plan**(原子地,在下一 tick 边界)
5. 下一 tick 用新 plan 执行
6. **不重启 Continuous run**——Continuous run 持续运行,只是 plan 被热替换

**关键: Continuous run 的 plan 是可热替换的**(与 OneShot 不同——OneShot 一旦开始,plan 固定到完成)。

### 慢节点的"warm"工作流

进入 Continuous 之前,如果某个慢节点(`realtime_capable=false`)的正式 cache 是空的,Continuous 会显示黑帧 + 发警告事件。用户的解决路径:

1. **先按 "Run Once" / "Generate" 按钮** → 触发 OneShot Full 执行 → 慢节点跑一次 → 结果存入正式 cache
2. **再进入 Continuous 模式** → 慢节点 cache 命中,实时播放正常

GUI 应该在用户尝试进入 Continuous 时**自动检测** plan 中是否有未 warm 的慢节点,提示用户先 warm。

### single-flight 与 Continuous 的互斥

| 当前状态 | 新请求 | 行为 |
|---------|-------|------|
| Idle | OneShot | 启动 OneShot |
| Idle | Continuous | 启动 Continuous |
| OneShot Full 运行中 | OneShot Preview | Preview 抢占(已有规则) |
| OneShot 运行中 | Continuous | 取消 OneShot, 启动 Continuous |
| Continuous 运行中 | OneShot Full | **暂停 Continuous, 跑 OneShot, 完成后恢复 Continuous**(用于跑慢节点 warm) |
| Continuous 运行中 | OneShot Preview | **拒绝**(Continuous 本身已经是实时预览,不需要 Preview 抢占) |
| Continuous 运行中 | Continuous | 取消旧 Continuous,启动新 Continuous |

**关键:** Continuous 模式下用户按 "Run Once" → Runtime 暂停 tick loop → 跑 OneShot Full → OneShot 完成后 → 自动恢复 tick loop。这让"实时预览中临时跑一次慢节点"成为流畅体验。

### Continuous 模式的事件流

| 事件 | 含义 |
|------|------|
| `ExecutionStarted { run_id, mode = Continuous }` | Continuous run 开始 |
| `ContinuousTickStarted { tick_index, current_frame }` | 每个 tick 开始(可选,频率高) |
| `ContinuousTickFinished { tick_index, duration_ms }` | 每个 tick 完成(可选,可累积) |
| `ContinuousTickOverrun { tick_index, target_ms, actual_ms }` | tick 超时(性能警告) |
| `NodeMissingInContinuous { node_id }` | 慢节点 cache 未命中 |
| `ContinuousPlanReplaced { old_plan_id, new_plan_id }` | 用户改图导致 plan 热替换 |
| `ContinuousPaused { run_id, reason }` | Continuous 被 OneShot 暂停 |
| `ContinuousResumed { run_id }` | OneShot 完成后 Continuous 恢复 |
| `ExecutionFinished { run_id, status, mode = Continuous }` | Continuous 退出 |

---

**关键分路约束(真源 ⑧ + targetv2 修订):**

| 事情 | Full 模式 | Preview 模式,fidelity_achieved=Preview | Preview 模式,fidelity_achieved=Full |
|------|----------|----------------------------------------|--------------------------------------|
| 写正式 cache | ✓ | **✗** | **✓**(执行器没降级,结果可复用) |
| 写 preview cache(经 Session) | (不直接) | ✓ | ✓ |
| 写 artifact | 按 ArtifactPolicy | ✗ | **✗**(即使 fidelity_achieved=Full,Preview 模式始终不写 artifact——artifact 是用户的显式导出动作) |
| 读正式 cache | ✓ | ✓(命中则 downsample) | ✓ |

**为什么 fidelity_achieved=Full 下仍不写 artifact:**

artifact 的语义是"用户导出的结果"——它应该只在用户**显式**请求 Full 时产生,不应该因为执行器偷偷全精度算了一下就被登记为导出。这保持了"Full 模式 = 正式产出"和"Preview 模式 = 探索性计算"的清晰边界。

### 流程 2: Preview 抢占 Full

```
1. try_start_run(preview_plan, Preview)
2. 发现 current 是 Full,cancel current
3. 等 current 清理完成(取消令牌)
4. 启动 preview_plan
5. preview_plan 执行期间,Full 请求排队或拒绝(Full 不抢 Preview)
```

### 流程 3: Materialization 调度

```
1. 执行器需要某个 Value 在特定 target(例如 GpuResident)
2. 执行器调 value.materialize(GpuResident)
3. Materializable 实现查 current_targets
   - 已经在目标位置 → 返回 handle
   - 不在 → 触发转换(CPU → GPU 上传 / 磁盘 → CPU 读取)
4. 执行器获得 handle,执行计算
5. 计算结束后,Runtime 可调 value.discard(obsolete_target) 释放内存
```

## 状态与生命周期

Runtime 作为长期服务存在:

- **空闲:** `single_flight.current == None`
- **运行中:** `current = Some(RunHandle { state: Running })`
- **正在取消:** `current = Some(RunHandle { state: Cancelling })`
- **终态短暂:** 一个 run 完成后,Runtime 在发出 `ExecutionFinished` 后立即把 `current` 置空

Runtime 本身不"关闭"——它的生命周期与引擎进程相同。

## 交互回路披露(真源 ⑧)

Runtime 在"参数变更 → 预览刷新"路径上的位置:

```
用户改参数 → Session → Scheduler → Planner → Runtime (就是本模块)
                                                ↓
                                           Executor Pool
                                                ↓
                                           Value 返回
                                                ↓
                                           Runtime 写 cache
                                                ↓
                                           publish event
                                                ↓
                                           Session 收到事件,更新 UI
```

**Runtime 对该路径的义务(真源 ⑧ 结构义务):**

1. **preview / full 分路**:`fidelity: EvaluationFidelity` 是 `try_start_run` 的必填参数
2. **Preview 抢占 Full**:当 Full 正在运行时,Preview 请求必须立即抢占——不排队
3. **preview 路径不写 artifact**:即使节点声明 `ArtifactPolicy::Persist`
4. **preview 路径独立的执行器 hint**:执行器在 `fidelity == Preview` 时允许降分辨率 / 降精度

**PR review 注意:**

- 任何在 Runtime 引入"Preview 必须等待 Full 完成"语义的变更都违反真源 ⑧
- 任何修改 single_flight 语义让 Session / CLI 可直接操纵守卫的变更都违反真源 ①/⑧
