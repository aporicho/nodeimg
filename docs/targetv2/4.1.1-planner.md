## 层归属

- **层:** Layer 2(Planner)
- **上游:** Layer 1(Graph)、NodeManager(只读查询 NodeDef 及其快照的 `capability_version`)
- **下游:** Layer 4(Runtime,消费 ExecutionPlan)

**关键: Planner 不直接依赖 Layer 3 CapabilityRegistry**

为避免 Layer 2 → Layer 3 的逆向依赖(违反分层方向),Capability 的版本信息由 **NodeManager** 在启动时从 CapabilityRegistry 一次性快照到每个 NodeDef 的内存表示里。Planner 运行时只读 NodeDef,**不**调用 CapabilityRegistry。

由于 Capability 注册是启动时完成且冻结(决议 M3),NodeManager 的快照是安全的——运行期不会变化。

**所有权清单:**

- 本模块拥有: 纯函数的**规划逻辑**、依赖分析缓存(内部 memoization)、`ExecSignature` 构造算法
- 本模块**不**拥有(都归 Scheduler facade 或其他模块):
  - `DirtyState`(归 Scheduler facade——Planner 作为纯函数不能持有可变状态)
  - `Graph`(归 GraphController)
  - `NodeDef`(归 NodeManager)
  - `Capability` 元信息(归 CapabilityRegistry,Planner 间接读 NodeManager 快照)
  - 实际执行、cache、artifact、取消令牌、进度事件、single-flight(都归 Runtime)

## 核心约束: Planner 是纯函数

```rust
fn plan(
    graph: &Graph,
    cooking_context: &CookingContext,
    dirty: &DirtyState,
    node_defs: &dyn NodeDefQuery,  // 只读 NodeDef 查询
) -> Result<ExecutionPlan, PlannerError>
```

**语义:**

- 给相同的 `(graph, cooking_context, dirty, node_defs 快照)`,永远产出相同的 `ExecutionPlan`
- `&self` 仅持有内部 memoization cache(不影响函数语义,只是优化)
- `dirty: &DirtyState` 是**只读引用**——`DirtyState` 由 Scheduler facade 持有并在调用前/后更新
- 不读文件、不访问正式 cache、不发 HTTP、不写日志(除 debug log)
- 可以被**单元测试**为纯函数: 给固定输入,断言固定输出
- 可以被 **CLI / Server / UI / 测试** 任意调用,互不影响

### 调用方约束与线程安全

- **调用方保证(Scheduler facade 承诺):** 对同一 Planner 实例的 `plan` / `propagate_dirty` / `rebuild_dirty` 调用**串行化**——首版 Scheduler facade 在单线程事件循环中处理所有调度请求
- **memoization cache 的线程安全:** 首版依赖调用方串行化,memoization cache 可以是 non-concurrent HashMap。未来若放宽串行化假设,需要改为 `DashMap` 或 `RwLock<HashMap>`(这属于 Planner 内部实现调整,不影响对外接口)
- **Planner 实例的 `&self` 方法在串行化前提下是纯函数等价的**:相同输入总产出相同输出,memoization 只影响性能

### 性能特性

| 方法 | 时间复杂度 | 空间复杂度 |
|------|----------|----------|
| `plan` | `O(\|dirty\| × \|context_range\|)` | `O(\|plan\|)`——产出 plan 的大小 |
| `propagate_dirty` | `O(\|affected\|)`——增量算下游 | `O(\|current\| + \|affected\|)`——返回新 DirtyState |
| `rebuild_dirty` | `O(\|graph\|)`——扫描全图 | `O(\|graph\|)` |
| `upstream_of` / `downstream_of` | `O(\|subgraph\|)` | `O(\|subgraph\|)` |

**DirtyState 复制代价:** `propagate_dirty` 返回新 `DirtyState` 是深拷贝。首版 Graph 通常 <500 节点,每次复制 <1ms,可接受。未来若需要更大图,可改为结构共享(`im::HashSet`)降低复制代价——这是 Planner 内部实现调整,不影响对外 API。

**为什么这重要:**

- 纯函数意味着**所有对"为什么这样规划"的追问都是可回答的**——给定输入,输出确定
- 调试变得可重现: 复现 bug = 捕获 `(graph, ctx, dirty)` 三元组
- 未来优化(并行规划、跨项目缓存规划)不需要改接口

## 定义

Planner 是 **把"想跑什么"翻译成"跑什么顺序 / 什么签名 / 什么 context"** 的纯函数模块。

它回答的问题:

- 给定当前图和上下文,哪些节点需要重算?
- 执行顺序应该是什么?
- 每个节点的 `ExecSignature` 是什么?
- CookingContext range 如何展开为多个子 plan?

它**不**回答:

- 执行器是哪个? → Runtime 按 Capability 查 CapabilityRegistry
- 缓存命中了吗? → Runtime 查
- 结果应该写到哪? → Runtime 决定
- 执行是否成功? → Runtime 处理

## 职责边界

### 属于 Planner

- 依赖分析(拓扑排序、传递闭包)——**纯函数**
- 脏状态传播**算法**(参数变 → 下游脏的计算逻辑)——注意是算法,不是状态
- `CookingContext` 枚举(对 range 做笛卡尔积)
- 每个节点的 `ExecSignature` 构造(读 NodeDef 快照的 `capability_version` 和 `cooking_sensitivity`)
- `ExecutionPlan` 生成(分层拓扑 + 子 plan 列表)
- 增量失效(从 `&DirtyState` 决定哪些节点进 plan)
- 图快照的纯函数分析

### 不属于 Planner

- **`DirtyState` 的所有权(归 Scheduler facade——Planner 只接受 `&DirtyState`)**
- 缓存读写(归 Runtime)
- 执行器分发(归 Runtime)
- single-flight 守卫(归 Runtime)
- 取消令牌、进度 sink(归 Runtime)
- artifact 写入(归 Runtime)
- Materialization 调度(归 Runtime)
- Capability 路由表(归 CapabilityRegistry,Planner 间接读 NodeManager 快照)
- 节点定义的注册(归 NodeManager)
- 图的结构编辑(归 GraphController)
- `run_id` / `generation` / `fidelity`(由 Runtime 在消费 Plan 时注入)

## 数据模型

**ExecutionPlan(纯函数输出,自洽不依赖外部 Graph):**

```rust
struct ExecutionPlan {
    subtasks: Vec<PlanSubtask>,
}

struct PlanSubtask {
    cooking_context: CookingContext,
    layers: Vec<Vec<PlannedNode>>,
}

struct PlannedNode {
    // 身份
    node_id: NodeId,
    type_id: String,

    // 执行参数(Planner 从 Graph 和 NodeDef 中提取)
    params: HashMap<String, Value>,      // 节点的有效参数值
    input_sources: HashMap<String, PinSource>,  // 输入口的来源

    // 路由与签名
    requires: Vec<CapabilityId>,          // 来自 NodeDef.requires(AND 语义)
    exec_signature: ExecSignature,
    cache_hit_expected: bool,             // 提示 Runtime 先查缓存
}

enum PinSource {
    /// 从其他节点的输出读取
    UpstreamOutput { node_id: NodeId, output_pin: String },
    /// 直接使用默认值或常量
    Constant(Value),
    /// 从参数展开(参数输入接口,见 ParamExpose::Input)
    FromParam(String),
}
```

**自洽性(targetv2 强化):**

`ExecutionPlan` **不引用 `Arc<Graph>`**——Runtime 消费 Plan 时**不需要** `Graph` 本体。所有需要的节点信息都在 `PlannedNode` 里预先提取好:

- `type_id`: 给 Runtime 用来查 `NodeDef`(经 NodeManager)
- `params`: 节点的有效参数(覆盖默认值)
- `input_sources`: 输入来源(上游节点 / 常量 / 参数)

**好处:**

1. **Runtime 完全不依赖 Graph**——Runtime 只需要 Plan + NodeManager(读 NodeDef)
2. **Plan 可序列化** —— 未来可能需要 "保存 Plan、延迟执行"(例如后台渲染任务)
3. **减少 Arc<Graph> 生存期依赖** —— 用户切换 Graph 不会让正在执行的 Plan 崩溃

**关键: `ExecutionPlan` 不包含 `run_id`、`generation`、`fidelity`、`graph_snapshot`、`graph_version`**

这些是 Runtime 在消费 Plan 时注入的运行时参数或不需要的:

- `run_id`: 由 Runtime 在 `try_start_run` 时生成
- `generation`: 由 Runtime 读 `GenerationId` 持有者(**CacheManager**,见真源 M7)得到
- `fidelity`: 由调用方传给 `try_start_run`
- `graph_snapshot`: 不需要——Plan 已经自洽
- `graph_version`: 不需要——Plan 自洽意味着规划时和执行时的"图"概念无关

Planner 作为纯函数只产出 **规划结果**,不持有或预测 Runtime 的执行环境。

**DirtyState(Scheduler facade 持有,Planner 只读):**

```rust
struct DirtyState {
    dirty_nodes: HashSet<NodeId>,
    dirty_reasons: HashMap<NodeId, DirtyReason>,
}

enum DirtyReason {
    ParamChanged,
    UpstreamChanged,
    StructureChanged,
    ArtifactSelectionChanged,
    Forced,
    CookingContextRangeChanged,   // targetv2 新增:CookingContext range 变化
}
```

**`DirtyState` 的首版策略(见 `0.1.3-cooking-context.md` §4.5):**

- 按 `NodeId` 记脏,**不**按 CookingContext 分片
- "节点 N 在 frame=5 脏 / frame=10 不脏" 这类细粒度无法表达
- 真正的命中判定由 Runtime 在执行前查 cache 完成

**脏状态的产生与消费:**

- **产生**: Scheduler facade 接收 `GraphChangedEvent` 后调 `Planner::propagate_dirty(&event, graph, &mut dirty)` 纯算法推导出新的 dirty
- **消费**: Scheduler facade 调 `Planner::plan(&graph, &ctx, &dirty, &node_defs)` 时传入只读引用
- **重置**: Runtime 执行完成后,Scheduler facade 调 `dirty.clear_completed(&run_result)` 清除已执行节点的脏标记

**`PlanSubtask` 的语义:**

- 每个 subtask 对应一个 CookingContext 下的整图(或受影响子图)求值
- 空 CookingContext → `subtasks.len() == 1`
- 多维 CookingContext → `subtasks.len() == 各维度笛卡尔积`
- 每个 subtask 内的 `layers` 是拓扑分层的节点组

## 提供接口

Planner 的所有方法都是**纯函数**或近似纯(只有 memoization):

```rust
trait Planner {
    /// 主接口: 给定图、context、脏状态、NodeDef 查询、选用查询,返回 ExecutionPlan
    /// 纯函数
    fn plan(
        &self,
        graph: &Graph,
        cooking_context: &CookingContext,
        dirty: &DirtyState,
        node_defs: &dyn NodeDefQuery,
        selections: &dyn ArtifactSelectionQuery,  // targetv2: Impure 节点签名依据
    ) -> Result<ExecutionPlan, PlannerError>;

    /// 脏状态的增量推导:给定图变更事件,产出新的 DirtyState
    /// 纯函数——不修改任何状态,而是产出新的 dirty
    ///
    /// graph_after 参数必须是**变更后**的图快照——Scheduler facade 应先调
    /// GraphController::get_graph_snapshot() 得到变更后的图,再传入此方法。
    fn propagate_dirty(
        &self,
        changes: &GraphChangedEvent,
        graph_after: &Graph,
        current: &DirtyState,
    ) -> DirtyState;

    /// artifact 选用变更的脏传播
    /// 纯函数;选用某个节点的 artifact → 该节点的 downstream 变脏(upstream input 变了)
    fn propagate_artifact_selection_change(
        &self,
        node_id: NodeId,
        graph: &Graph,
        current: &DirtyState,
    ) -> DirtyState;

    /// 全量重建 DirtyState(从图快照)
    /// 纯函数
    fn rebuild_dirty(&self, graph: &Graph) -> DirtyState;
}

/// ArtifactManager 向 Planner 暴露的只读查询接口
trait ArtifactSelectionQuery {
    /// 返回指定节点当前选用的 artifact id,None 表示未选用
    fn current_selection(&self, node_id: NodeId) -> Option<ArtifactId>;
}

// 注: 依赖查询(upstream_of / downstream_of)不属于 Planner 的接口,
// 它们是 Graph 的属性,属于 GraphController 的职责范围。
// Planner 内部做脏传播时直接使用 graph.downstream_of(node_id)——这是 Graph 的内联方法。
// 外部模块(Session、UI)需要做图查询时也直接调 graph.upstream_of / graph.downstream_of,
// 不要绕经 Planner。

/// NodeManager 向 Planner 暴露的只读查询接口
trait NodeDefQuery {
    fn get_node_def(&self, type_id: &str) -> Option<Arc<NodeDef>>;

    /// 查询某个 Capability 的版本
    /// NodeManager 在启动阶段 4 从 CapabilityRegistry 快照下来,
    /// 以 HashMap<CapabilityId, CapabilityVersion> 的形式持有
    ///
    /// 版本是 Capability 自身属性,不依赖哪个 Node 使用它 —— 所以签名不带 type_id
    fn capability_version(&self, cap_id: &CapabilityId) -> Option<CapabilityVersion>;
}
```

**关键非对称: `propagate_dirty` 返回新 `DirtyState` 而不是 `&mut`**

这让 Planner 严格保持纯函数性。Scheduler facade 的代码写成:

```rust
// Scheduler facade 内部
let new_dirty = planner.propagate_dirty(&event, &graph, &self.dirty);
self.dirty = new_dirty;  // facade 负责状态替换
```

`DirtyState` 的**生命周期和所有权**完全在 Scheduler facade 手里——Planner 只做纯计算。

## 依赖接口

### 对 GraphController

```rust
get_graph_snapshot() -> Arc<Graph>
```

### 对 NodeManager(唯一的元信息来源)

```rust
trait NodeDefQuery {
    fn get_node_def(&self, type_id: &str) -> Option<Arc<NodeDef>>;
    fn capability_version(&self, cap_id: &CapabilityId) -> Option<CapabilityVersion>;
}
```

**重要:** Planner **不**直接查 `CapabilityRegistry`。`capability_version` 由 NodeManager 在启动时从 CapabilityRegistry 快照为内部 `HashMap<CapabilityId, CapabilityVersion>`——Planner 只从 NodeManager 读。

**启动顺序(见 `4.1.3-capability-registry.md` §注册流程):**

1. 阶段 1: 内置执行器注册 → CapabilityRegistry
2. 阶段 2: 外部 NodeSource 注册 → CapabilityRegistry + NodeManager
3. 阶段 3: CapabilityRegistry::freeze()
4. **阶段 4: NodeManager 调用 `registry.snapshot_versions()` 一次性读所有 (cap_id → version)**
5. **阶段 4(续): NodeManager 遍历 NodeDef,对每个 `requires` 为空的调用 normalize**
6. 阶段 5: NodeManager::freeze()(M6 冻结)
7. 阶段 6: Scheduler facade 开始工作

**Planner 只在阶段 6 之后被调用**——此时 NodeManager 的快照已经稳定,运行期 Capability 注册表冻结(M3),NodeManager 冻结(M6),Planner 读到的是**不可变**的元信息。

**为什么这样设计:**

- Layer 2(Planner)依赖 Layer 3(CapabilityRegistry)违反分层方向
- NodeManager 是**跨层服务**(不在 8 层的纵向里,类似 EventSystem),Planner 依赖它不违反方向
- Capability 注册启动时冻结(决议 M3),NodeManager 注册启动时冻结(决议 M6)——双冻结保障快照安全

### 对 EventSystem

Planner **不直接**发事件。相关事件(如"规划开始"、"规划完成")由 Scheduler facade 或 Runtime 代发。

## ExecSignature 构造规则

见 `0.1.1-execution-models.md` §3.1 的完整公式。Planner 实现:

```rust
fn build_signature(
    node: &Node,
    node_def: &NodeDef,
    upstream_sigs: &[ExecSignature],
    cooking_context: &CookingContext,
    node_defs: &dyn NodeDefQuery,
    selections: &dyn ArtifactSelectionQuery,
    graph: &Graph,  // 用于 build_params_hash 判断参数接口连线
) -> ExecSignature {
    // params_hash 规则见 0.1.1-execution-models.md §3.1.1
    // 关键: (a) 按当前 CookingContext 采样 Animated 参数;
    //       (b) 跳过参数输入接口(由 upstream_signatures 承担);
    //       (c) 按 key 字典序排序
    let params_hash = build_params_hash(node, node_def, cooking_context, graph);

    // 计算"有效 cooking_sensitivity":
    // = NodeDef 显式声明 + 节点实例的 Animated 参数自动推导(见 0.1.0-models.md §2.5.2)
    let effective_sensitivity = effective_cooking_sensitivity(node_def, node);

    // 按有效 sensitivity 过滤 context——向后兼容的关键
    let cooking_ctx_hash = build_cooking_context_hash(
        cooking_context,
        &effective_sensitivity,
    );

    // 从 NodeManager 读启动时快照下来的 capability_version
    // 多个 requires 的情况取它们的组合 hash(首版: 按字典序排序后 xxhash)
    let cap_version = combine_capability_versions(
        &node_def.requires,
        node_defs,
    );

    // Impure 节点: 读当前选用的 artifact id;Pure 节点: 恒为 0
    let selected_artifact_id = match node_def.purity {
        Purity::Pure => 0u64,
        Purity::Impure => selections
            .current_selection(node.id)
            .map(|id| id.as_u64())
            .unwrap_or(0),
    };

    let hash = xxhash3_128([
        hash_upstream(upstream_sigs),
        params_hash,
        hash(node_def.type_id),
        node_def.version as u128,
        cooking_ctx_hash as u128,
        cap_version as u128,
        selected_artifact_id as u128,
    ]);
    ExecSignature { hash }
}

/// 按 cooking_sensitivity 过滤 context(见 0.1.3-cooking-context.md §2.4)
fn build_cooking_context_hash(
    context: &CookingContext,
    sensitivity: &[DimensionId],
) -> CookingContextHash {
    if sensitivity.is_empty() {
        return 0;  // 空敏感度 → 恒零(向后兼容)
    }
    let mut filtered = BTreeMap::new();
    for dim_id in sensitivity {
        if let Some(value) = context.dimensions.get(dim_id) {
            filtered.insert(dim_id.clone(), value.clone());
        }
    }
    xxhash3_64(stable_serialize(&filtered))
}
```

**关键:**

1. `cooking_ctx_hash` 通过 `cooking_sensitivity` 过滤——空敏感度恒为 0
2. `cap_version` 首版恒为 0(所有 Capability 版本都是 0)
3. **两个字段必须在公式中**,首版恒零是占位,未来填入真实 hash 不破坏旧节点签名
4. `combine_capability_versions` 必须对 `requires` 排序后再 hash,确保顺序无关

```rust
fn combine_capability_versions(
    requires: &[CapabilityId],
    node_defs: &dyn NodeDefQuery,
) -> u32 {
    if requires.is_empty() { return 0; }
    let mut versions: Vec<(String, CapabilityVersion)> = requires
        .iter()
        .map(|cap| {
            let v = node_defs.capability_version(cap).unwrap_or(0);
            (cap.clone(), v)
        })
        .collect();
    versions.sort_by(|a, b| a.0.cmp(&b.0));  // 按 cap_id 字典序排序
    xxhash3_32(stable_serialize(&versions))
}
```

详细占位字段规则见 `0.1.1-execution-models.md` §3.4。

## 脏状态传播规则(纯函数算法)

`propagate_dirty(&event, &graph, &current) -> DirtyState` 是**纯函数**,根据事件类型计算新 DirtyState:

### 参数变更

```
SetParam(node_id, param, value)
    → new.dirty_nodes = current.dirty_nodes ∪ {node_id} ∪ downstream_of(node_id)
    → reasons[node_id] = ParamChanged
    → reasons[downstream...] = UpstreamChanged
```

### 连线变更

```
Connect / Disconnect
    → new.dirty_nodes ∪ {to_pin.node_id} ∪ downstream_of(to_pin.node_id)
    → reasons[...] = StructureChanged
```

### 节点增删

```
AddNode(node_id)     → 单节点入脏,不级联
RemoveNode(node_id)  → 该节点所有 downstream 入脏
```

### CookingContextRange 变更(targetv2 新增)

```
SetCookingContextRange(range)
    → 不改 DirtyState
    → 理由: cooking_sensitivity 为空的节点签名不变,cache 继续命中
           cooking_sensitivity 非空的节点签名变,cache 自然未命中
           DirtyState 不需要参与
```

### Artifact 选用变更(targetv2 新增)

```
ArtifactSelected(changed_node_id)
    → changed_node 本身**不**变脏(它的输出就是用户选用的 artifact)
    → downstream_of(changed_node) 全部变脏,DirtyReason::ArtifactSelectionChanged
    → changed_node 的签名**会**变化(因为 selected_artifact_id 进入公式)
      ——这让 downstream 的 upstream_signatures 自动变,从而其签名也变
      ——但 DirtyState 仍需显式标记 downstream,让 Planner 重新规划包含它们
```

**算法实现 `propagate_artifact_selection_change`:**

```rust
fn propagate_artifact_selection_change(
    &self,
    node_id: NodeId,
    graph: &Graph,
    current: &DirtyState,
) -> DirtyState {
    let mut new_dirty = current.clone();
    for n in graph.downstream_of(node_id) {
        new_dirty.dirty_nodes.insert(n);
        new_dirty.dirty_reasons.insert(n, DirtyReason::ArtifactSelectionChanged);
    }
    // 注: changed_node 本身不入 dirty——它的"输出"就是选用的 artifact,不需要重算
    new_dirty
}
```

### clear_cache / replace_graph

```
clear_cache()    → 不改 DirtyState,但 Runtime 会 bump generation
replace_graph(g) → 全量 rebuild_dirty(&g)
```

**关键:** 所有规则都是"根据输入产出新 DirtyState"——**不改变**输入的 `current`。Scheduler facade 在调用后替换自己持有的 DirtyState。

## 交互回路披露(真源 ⑧)

Planner 在 "参数变更 → 预览刷新" 路径上的位置:

```
用户改参数 → Session → Scheduler → Planner.propagate_dirty()
                                        ↓
                                   Planner.plan()
                                        ↓
                                   Runtime.execute()
```

**Planner 对该路径的义务:**

- `propagate_dirty` 必须是**增量**的,不能内部调用 `rebuild_dirty`
- `plan` 必须**只**为 `dirty_nodes` 生成 `PlannedNode`,其他节点默认 `cache_hit_expected = true`
- `plan` 不得有 I/O(包括读 NodeManager 的文件系统缓存)——应使用 NodeManager 的内存索引

**PR review 注意:**

- 任何使 `plan` 的时间复杂度从 `O(dirty)` 提升到 `O(graph)` 的变更都必须披露
- 任何引入 I/O 到 `plan` 的变更都必须披露
