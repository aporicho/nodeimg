# 会话层 Session

> **Layer 5**。一次"打开 Project"或"新建 scratch Graph"的生存期,持有交互性状态。

---

## 文档状态

`draft` —— Session 是 targetv2 新引入的层,首版所有权清单已冻结,内部结构仍可调整。

## 层归属

- **层:** Layer 5(Session Layer)
- **上游:** Layer 7 Interface(GUI / AI 操作员)
- **下游:** Layer 4 Runtime(启动执行)、Layer 1 GraphController(undo/redo 逻辑)、Layer 4 CacheManager(preview cache 独立实例)

**关键非对称:**

- **GUI / AI 操作员** 经 Session 访问引擎
- **CLI / Server** 可以**不经过** Session,直接调用 Runtime
- "无 Session 的执行" 是合法路径——Session 是交互层的**服务**,不是执行的**必经**

---

## 定义

Session 是 **"一次用户打开项目的生存期" 对应的交互状态容器**。它回答:

- 用户的交互意图如何翻译成 `ExecutionRequest`?
- preview 热路径缓存长什么样?
- undo / redo 栈存在哪里?
- 哪些事件该推送给 GUI,哪些是 CLI 也关心的?

它**不**回答:

- 执行语义(归 Runtime)
- 图结构(归 GraphController)
- 项目文件(归 ProjectManager)
- Capability 路由(归 CapabilityRegistry)

---

## 生存期

```
创建: 打开 Project / 新建 scratch Graph
销毁: 关闭 Project / 退出 App

状态: 与 Project 的打开状态一一对应
     但: 生存期不等于 Project 的生存期
     Project 关闭时 Session 销毁,但 Session 的状态(undo 栈等)不写回 Project 文件
```

**关键约束(真源 ⑦):**

- Session 状态**不跨进程**
- Session 状态**不进项目文件**
- 当前查看 frame / 播放头位置、当前选中节点、焦点面板、打开的历史窗口都属于 Session
- 凭证不属于 Session 项目状态,也绝不进入项目文件
- 同时可以有多个 Session(多 Project 场景),但首版支持单 Session

## 多 Session 与 Runtime 的关系

即使未来支持多个 Session 共存(多 Project 场景):

- **Runtime 仍然是进程级的唯一实例**
- **single-flight 守卫是进程级的**——所有 Session 的执行请求**共享**同一个 single-flight
- 这意味着 Project A 的用户调参数时,Project B 的 export 会被抢占

**理由:** GPU / CPU 资源是硬件级的,必须全局竞争。多 Session 共享 Runtime 符合这个物理事实。

**如果未来需要 Project 级资源隔离**(如 Project A 和 B 有独立的执行上下文),这是**破坏性变更**——需要先改真源 ① 的责任边界,把 single-flight 从"进程级"改为"Project 级",然后让每个 Project 有自己的子 Runtime。首版不做。

## Session 并发模型(同一 Session 多调用方)

同一个 Session 可以被**多个调用方同时使用**——典型场景:

- GUI 用户手动操作
- AI 操作员自动化脚本
- 两者共享一个 Session(一个 Project)

**Session 的并发保证:**

1. **线程安全**: Session 内部状态(undo 栈、preview cache、focus)用锁或原子类型保护,保证多调用方的操作不会数据竞争
2. **操作原子性**: 单个 `apply_edit` / `submit_interaction` 调用是原子的——不会被中途打断看到半状态
3. **事件广播**: 一个调用方的修改会通过 `SessionEvent` 广播给所有订阅者,包括其他调用方

**Session 不保证的:**

- **用户意图不互相干扰**: GUI 用户改参数 A、AI 同时改参数 B,两者都会生效,但 UI 层可能会"意外地看到 A 和 B 都变了"——这是**用户意图冲突**,不是数据冲突,解决归 UI 层
- **undo 栈分组**: 首版所有调用方的操作进同一个 undo 栈。如果 AI 的批量操作会污染 GUI 用户的 undo 历史,未来可以扩展 `apply_edit(edit, options { add_to_undo: bool })`——首版不做。

**CLI 不在这个并发模型里**——CLI 不经 Session,没有 undo / preview cache 的并发需求。

## undo 栈所有权细节

**逻辑所有权归 Session,实现可以在 GraphController 里,但生存期受 Session 控制。**

### GUI 路径

1. Session 启动时,通过 `GraphController::new_with_undo_tracking()` 构造 GraphController,启用 undo 跟踪
2. 每次 Session::apply_edit → GraphController::apply_edit → 内部把新 Graph 值 push 到 undo 栈
3. Session::undo → GraphController::undo → 从栈里 pop 并设置为当前 Graph
4. Session 关闭时 → GraphController 实例销毁 → undo 栈随之销毁

### Undo / Redo 与 in-flight run 的交互(targetv2 明文)

用户按 Undo / Redo 时,如果 Runtime 有一个 run 正在执行:

1. **GraphController::undo()** 改变 Graph,产生 `GraphChangedEvent { reason: Undo }`
2. Scheduler facade 收到 `GraphChangedEvent`,执行**常规流程**:
   - 调 `Planner::propagate_dirty(&event, &graph_after, &current)` 推导新 DirtyState
   - 调 `CacheManager::invalidate_subgraph(affected_nodes)`
   - **检查 in-flight run 的 Plan 是否仍然有效**
3. **in-flight run 的处理:**
   - 如果 in-flight 是 **Preview**: 立即取消(Preview 是探索性的,没有恢复价值)
   - 如果 in-flight 是 **Full**: 取消,并移入 `pending_full`(其 `ExecutionRequest` 保留)
4. Preview / Full 都发 `ExecutionCancelled { reason: GraphChanged }` 事件
5. 如果 Undo 把 Graph 改得 pending_full 的 target 已失效,恢复时 Scheduler facade 重新规划会返回错误(见问题 45 修复的细节)

**关键:** Undo / Redo 不是特殊事件,它们是普通的 `GraphChangedEvent`,走常规 dirty 流程。这让 "Undo 与抢占" 的正确性依赖于 **`pending_full` 只存 Request 不存 Plan** 的设计(见 `4.1.2-runtime.md` §pending_full 失效场景)。

**首版限制:** 不尝试"Undo 后立即 Redo 恢复到 in-flight run 的 Plan 对应的图" —— 这种优化复杂且价值低,首版一律重新规划。

### CLI 路径

1. CLI 启动时,通过 `GraphController::new_without_undo()` 构造 GraphController,禁用 undo 跟踪
2. CLI::apply_edit → GraphController::apply_edit(no-undo 模式)→ 不 push 栈
3. `GraphController::undo` 在 no-undo 模式下返回 `Err(UndoDisabled)`
4. CLI 退出时 → GraphController 销毁

### CLI 路径

1. CLI 启动时,通过 `GraphController::new_without_undo()` 构造 GraphController,禁用 undo 跟踪
2. CLI::apply_edit → GraphController::apply_edit(no-undo 模式)→ 不 push 栈
3. `GraphController::undo` 在 no-undo 模式下返回 `Err(UndoDisabled)`
4. CLI 退出时 → GraphController 销毁

**关键约束:**

- GraphController 有两种构造模式: `with_undo_tracking` 和 `without_undo`
- Session **只**使用 `with_undo_tracking`
- CLI / Server **只**使用 `without_undo`
- 这让 "undo 栈归 Session 拥有" 在逻辑上成立——即使实现分散在 GraphController 里,**生存期完全受 Session 控制**

**权威定义:** `4.2.0-graph-controller.md`(待 targetv2 修订)应添加 `with_undo_tracking` / `without_undo` 两种构造方式,和对应的 `apply_edit` 行为差异。

## 职责边界

### 属于 Session(拥有)

- **undo / redo 栈的生存期**(逻辑实现委托 GraphController;见 "undo 栈所有权细节")
- **preview 热路径缓存**(`PreviewCache`,独立于正式 cache)
- **事件总线订阅者注册**
- 当前选中节点、焦点节点、脏标记前缘(UI 状态)
- 当前查看 frame / 播放头位置
- 对 Scheduler facade 的 `Arc` 引用
- 将交互意图翻译成 `ExecutionRequest` 的逻辑
- Preview / Full 模式的决策(默认 Preview,导出时 Full)
- 结果历史面板的交互入口(选择版本、标记、清理),但不拥有正式 artifact store

### 不属于 Session(不拥有)

- **`single-flight` 权限**(归 Runtime)
- **当前 RunHandle 引用**(Session 不持有,所有查询走 `scheduler.query_state()`——避免并发竞态)
- **正式 cache**(归 CacheManager)
- Artifact 历史 / 当前选中版本的正式存储(归 ArtifactManager,并由 ProjectManager 持久化)
- 节点定义(归 NodeManager)
- Graph 数据结构本体(归 GraphController;Session 持有引用)
- 执行语义、取消令牌、进度 sink(归 Runtime)
- Capability 路由(归 CapabilityRegistry)
- Provider 凭证(归凭证管理器,不进项目文件)

## 数据模型

```rust
struct Session {
    // 生存期关联
    project_handle: Option<Arc<ProjectHandle>>,  // None = scratch

    // 与 Runtime 路径的桥梁
    scheduler: Arc<SchedulerFacade>,   // Session 只调用 scheduler,不直接调 Runtime / Planner

    // 交互状态
    undo_stack: UndoStack,
    redo_stack: UndoStack,
    preview_cache: PreviewCache,
    focus: FocusState,
    playback: PlaybackState,
    interaction_events: EventQueue<InteractionEvent>,

    // 事件订阅
    event_subscribers: Vec<EventSubscriber>,

// 注意: Session **不持有** RunHandle 引用

struct PreviewCache {

}
```

### 对 Scheduler facade(唯一的执行入口)

Session **只**调 Scheduler facade 的高层接口,**不**直接调 Runtime 或 Planner:

```rust
// Session 内部
fn request_preview(&self, target: ExecuteTarget) -> Result<PreviewResult, SessionError> {
    // 三级缓存查询: Session preview_cache → Runtime 正式 cache → 执行器
    //
    // 第 1 级: 查 Session 自己的 preview_cache
    // Session 首先构造 PreviewCacheKey 所需的签名——
    // 这需要知道 target 节点的 ExecSignature,通过 scheduler.query_signature(target) 获取
    if let Some(sig) = self.scheduler.query_signature(target)? {
        let cache_key = PreviewCacheKey {
            node_id: target.node_id(),
            output_pin: target.output_pin().to_string(),
            exec_signature: sig,
            fidelity_class: FidelityClass::Preview1024,
        };
        if let Some(entry) = self.preview_cache.get(&cache_key) {
            return Ok(PreviewResult::CacheHit(entry.value.clone()));
        }
    }

    // 第 1 级未命中 → 提交给 Scheduler facade
    // Scheduler 内部会走 第 2 级(正式 cache 命中 + downsample)或 第 3 级(执行器)
    let request = ExecutionRequest {
        target,
        mode: ExecutionMode::OneShot {
            fidelity: EvaluationFidelity::Preview {
                max_side: Some(1024),
                precision: PreviewPrecision::Float16,
            },
        },
    };

    let ticket = self.scheduler.request_execution(request)?;

    // Scheduler 内部触发执行后,执行器或 Runtime 会通过 progress_sink 把结果送回 Session
    // Session 订阅者收到后写入自己的 preview_cache(见"Preview cache 写入的精确路径")
    Ok(PreviewResult::InProgress(ticket))
}

enum PreviewResult {
    /// 命中 Session preview_cache,立即返回
    CacheHit(Value),
    /// 未命中,已提交执行,通过事件异步接收
    InProgress(ExecutionTicket),
}

fn request_export(&self, target) -> Result<ExportTicket, SessionError> {
    let request = ExecutionRequest {
        target,
        mode: ExecutionMode::OneShot {
            fidelity: EvaluationFidelity::Full,
        },
    };
    let ticket = self.scheduler.request_execution(request)?;
    Ok(ExportTicket::from(ticket))
}
```

**封装规则:**

- Session **不**直接调用 `Planner::plan` —— 规划是 Scheduler facade 内部事
- Session **不**直接调用 `Runtime::try_start_run` —— 执行是 Scheduler facade 内部事
- Session **不**持有 `RunHandle` 引用 —— 所有状态查询走 `scheduler.query_state()` 或订阅事件
- 这样的封装让 Session 的代码不依赖 Runtime / Planner 的内部细节,只看到 Scheduler facade 的稳定接口

**查询当前 run 状态:**

```rust
// 不是持有 Weak<RunHandle>,而是主动查询
let state = self.scheduler.query_state();
match state.runtime_state {
    RuntimeState::Running { run_id, fidelity, progress } => { /* ... */ }
    RuntimeState::Idle => { /* ... */ }
    RuntimeState::Planning { .. } => { /* ... */ }
}

// 或订阅 EngineEvent,被动接收状态变化
self.event_subscribers.push(subscriber);
```

## 交互意图翻译流程

```
1. 用户改一个参数(UI 操作)
    ↓
2. GUI → SessionHandle::submit_interaction(ParamChanged { ... })
    ↓
3. Session 收到 InteractionEvent:
    a. 若 preview = true: 只更新 preview overlay,不改 Graph
    b. 若 preview = false: 通过 GraphController 提交真正的 Graph 编辑
    ↓
4. Session 决定"需要刷新 preview 的节点"
    ↓
5. Session 构造 ExecutionRequest(mode = OneShot { fidelity = Preview {...} })
    ↓
6. Session 调 Scheduler facade 提交执行请求
    ↓
7. Runtime 可能抢占当前 Full 运行,调度 Preview
    ↓
8. Executor 返回结果 → Runtime 按 fidelity_achieved 决定是否写正式 cache
    ↓
9. Session 从正式 cache 读 / 或接收 ExecutorProgressEvent::Preview 的预览值
    ↓
10. Session 把结果存入 preview_cache(LRU)
    ↓
11. Session 发 SessionEvent::PreviewUpdated 给 GUI
```

## 与 single-flight 的非关系

**关键:** Session 对 `single-flight` 的角色是 **申请者 + 查询者**:

- **申请者:** 通过 `scheduler.request_execution(request)` 申请启动(间接经 Runtime::try_start_run)
- **查询者:** 通过 `scheduler.query_state()` 主动查询当前 run 状态,或订阅 EngineEvent 被动接收

Session **不是 single-flight 的管理者**,也**不持有 RunHandle**。它不能:

- 直接设置 `single_flight.current = None`
- 绕过 Runtime 启动 run(Session 只通过 Scheduler facade 走正式路径)
- 共享 single_flight 与其他 Session 实例
- 持有指向当前 RunHandle 的任何 Rust 引用(避免并发竞态)

**原因(真源 ①/⑧):** CLI / Server 不经过 Session,但必须被同一条 single-flight 约束。如果 Session 管 single-flight,CLI 路径就失去这条不变量。

## Preview Cache 的生命周期

- **创建:** Session 启动时构造,给定内存预算
- **读取:** 按 `PreviewCacheKey` 查询
- **写入路径(关键):** Session 通过订阅 Runtime 的执行事件写入
- **淘汰:** LRU,按 `last_accessed` 时间
- **清空:** `close_project` 时全部清空

### Preview cache 写入的精确路径

Preview 的结果通过**事件**送达 Session。Runtime 只有在 `fidelity_achieved == Full` 时才可把 Preview 请求的结果写入正式 cache;降级 Preview 结果不写正式 cache:

```
Runtime (Preview 执行)
   ↓
   执行器产出 Value
   ↓
   Runtime 调 progress_sink.report(ExecutorProgressEvent::Preview {
       output: "out",
       value: value.clone(),
   })
   ↓
Session (订阅 progress_sink)
   ↓
   收到 Preview 事件,构造 PreviewCacheKey
   ↓
   写入自己的 preview_cache
   ↓
   发 SessionEvent::PreviewUpdated 给 GUI
```

**不对称: Runtime 不直接调 Session**

- Runtime 不知道 Session 的存在(它是 Layer 4,不认识 Layer 5)
- Session 通过订阅 `progress_sink`(Runtime 提供的事件通道)收听
- `progress_sink` 在 `ExecutionRequest` 构造时注入,Session 在构造 preview 请求时传入自己的 sink

**Full 模式下不经过这条路径:**

- Full 模式下 Runtime 直接写正式 cache
- Session 可以订阅 `ExecutionFinished` 事件,然后主动去正式 cache 查结果——**但通常不需要**,因为 GUI 刷新走 `SessionEvent` 或直接 getter

### Preview 命中正式 cache 的 fallback

- Preview 请求时,Runtime **先查正式 cache**
- 如果命中(例如用户刚做过 Full 导出,结果还在 cache 里):
  - Runtime 内部 downsample 到 Preview 的 `max_side`
  - 把 downsample 结果通过 progress_sink 发给 Session
  - **不再调用执行器**
- 如果未命中:走 Preview 执行路径

**收益:** 用户改一个小参数,大部分上游节点的正式 cache 仍然命中,只有受影响的子图需要 Preview 执行——这是"快反馈"的基础。

### Session 与正式 cache 的只读关系

- preview_cache **不共享**内存与正式 cache
- preview_cache **可以通过 Runtime 的 fallback 机制**间接读正式 cache——Session 本身不直接访问正式 cache

## 结果历史面板与 undo/redo

Session 提供结果历史面板的交互入口,但正式数据由 ArtifactManager 管理:

- 浏览历史: Session 查询 ArtifactManager 的只读视图并转成 UI 事件。
- 切换当前版本: Session 发起 artifact selection mutation,再让 Scheduler facade 调 `propagate_artifact_selection_change`。
- 标记版本 / 清理历史: Session 发起 ArtifactManager mutation。
- 以上 mutation 都进入 undo/redo 语义;撤销后要恢复 selection / mark / deletion 前的状态。
- 打开的历史窗口、当前焦点版本等临时界面状态只属于 Session,不进项目文件。

## Continuous warm 交互

当 Continuous 中收到 `NodeMissingInContinuous { node_id }`:

1. Session 将缺失节点标记到 UI 状态,提示需要 warm。
2. 用户触发 warm 时,Session 暂停 Continuous 请求路径,提交 `OneShot { fidelity: Full }`。
3. Full 完成后 Runtime 把正式结果写入 cache / artifact history。
4. Session 收到完成事件后请求恢复 Continuous,下一 tick 使用 warm 后的 cache。

### 三级缓存命中路径总结

Session 的 `request_preview` 走三级命中路径,从快到慢:

| 级别 | 来源 | 内容 | 成本 |
|------|------|------|------|
| **1** | Session 的 `preview_cache` | 已 downsample 的 Preview 结果 | 零成本(HashMap 查询) |
| **2** | Runtime 的正式 cache + downsample | Full 结果 + Runtime 内部 downsample 生成 Preview | downsample 的 GPU 开销 |
| **3** | 执行器实际执行 | 调执行器按 Preview 或 Full 精度执行 | 完整执行成本 |

**级别 1 在 Session 内完成**:Session 自己查自己的 cache,命中则直接返回,**不调用 Scheduler**。
**级别 2 在 Runtime 内完成**:Session 提交请求 → Scheduler facade → Planner 规划 → Runtime 查正式 cache 命中 → Runtime 内部 downsample → 经 `progress_sink` 送回 Session。
**级别 3 在执行器完成**:级别 2 未命中 → Runtime 调执行器 → 结果经 `progress_sink` 送回 Session。

**级别 2 和 3 的结果都会被 Session 存入自己的 preview_cache(级别 1)**,下次命中。

**性能含义:**

- 首次 preview(冷启动)→ 级别 3 → 完整执行
- 再次同一 preview → 级别 1 → 零成本(~microseconds)
- 改了一个参数 → Session cache 未命中(签名变),正式 cache 可能有上游结果 → 级别 2 → 局部重算 + downsample
- 这三级联动实现 "快反馈"(真源 ⑧)

## 交互回路披露(真源 ⑧)

Session 在"参数变更 → 预览刷新"路径上的位置: **最接近用户的一层**。

**Session 对该路径的义务:**

1. 交互意图到 `ExecutionRequest` 的翻译**必须快**—— 不阻塞 UI 线程
2. preview 默认为 `Preview { max_side: 1024, ... }`(首版可简化)
3. `submit_interaction` 之后**立即**发 `InteractionAck`,不等待执行完成
4. preview_cache 命中时**不触发**执行
5. Session 对 Runtime 的调用**不得**持有 blocking 锁

**PR review 注意:**

- 任何使 `submit_interaction` 阻塞的变更都违反义务 1
- 任何使 Session 持有 single-flight 权限的变更违反真源 ①
- 任何使 CLI 被迫创建 Session 的变更违反真源 ①

## 状态与生命周期

```
Idle (no project):
    only constructed, empty

Open (with project):
    undo_stack populated
    preview_cache active
    event_subscribers active
    (run state 查询走 scheduler.query_state(),Session 不持有)

Closing:
    flush events
    drop undo_stack
    clear preview_cache
    unsubscribe events
    → Idle
```
