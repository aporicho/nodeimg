# Capability 注册表

> **Layer 3**。`CapabilityId → Vec<Arc<dyn Executor>>` 路由表。启动时注册,运行时只读。

---

## 文档状态

`impl`

---

## 层归属

- **层:** Layer 3(Capability Layer)
- **上游:** Executor 实例(注册时调用 `provides()`)
- **下游:** Layer 4 Runtime(路由决策)、Layer 2 Planner(查 capability_version)

**所有权清单:**

- 本模块拥有: `CapabilityId → Vec<Arc<dyn Executor>>` 映射表、`Capability` 元信息表、路由规则
- 本模块引用但不拥有: Executor 实例(实际执行器属于执行器池,注册表只持有 `Arc` 引用)
- 本模块**不**拥有: 执行语义、路由决策的副作用(Runtime 的事)

---

## 定义

`CapabilityRegistry` 是 **"Capability 到执行器" 的映射服务**。

它回答:

- 有哪些 `CapabilityId` 被注册?
- 某个 `CapabilityId` 有哪些执行器提供?
- 某个 `CapabilityId` 的 `version` 是多少?
- 根据局部性提示,应该选哪个执行器?

它**不**回答:

- 执行器内部如何实现? → 执行器自己
- 某次执行成功了吗? → Runtime
- 缓存命中了吗? → Runtime

---

## 职责边界

### 属于 CapabilityRegistry

- 注册阶段收集所有 Executor 的 `provides()` 声明
- 构造 `CapabilityId → Vec<Arc<dyn Executor>>` 路由表
- 构造 `CapabilityId → Capability` 元信息表
- 提供只读查询接口(给 Runtime / Planner)
- 提供路由规则(首版: 按局部性提示过滤,取第一个健康的)

### 不属于 CapabilityRegistry

- 执行器的创建(归启动代码)
- 执行器的实际调用(归 Runtime)
- 执行器的健康检查机制(归 Runtime 或执行器自身)
- Capability 的热插拔(冻结决议 M3: 不支持)

## 数据模型

```rust
struct CapabilityRegistry {
    capabilities: HashMap<CapabilityId, Capability>,
    providers: HashMap<CapabilityId, Vec<Arc<dyn Executor>>>,
}

struct Capability {
    id: CapabilityId,
    version: CapabilityVersion,
    input_types: Vec<DataType>,
    output_types: Vec<DataType>,
    side_effects: Vec<SideEffect>,
}

type CapabilityId = String;
type CapabilityVersion = u32;

enum SideEffect {
    None,
    FileRead(PathPattern),
    FileWrite(PathPattern),
    NetworkCall(HostPattern),
    PythonProcess,
}

enum LocalityHint {
    PreferGpu,
    PreferCpu,
    PreferRemote,
    Any,
}
```

详见 `0.1.4-capability.md` §2。

## 提供接口

```rust
trait CapabilityRegistry {
    /// 启动阶段: 注册一个执行器
    /// 执行器的所有 provides() 声明都会被加入注册表
    fn register_executor(&mut self, executor: Arc<dyn Executor>) -> Result<(), CapabilityRegistryError>;

    /// 启动阶段: 注册 fallback Capability
    ///
    /// 与 register_executor 不同: 这里显式声明 cap_id,即使 executor.provides() 不包含该 cap_id
    /// 用途: 为每个 ExecutorType 注册一个默认 Capability,给 NodeManager 的 normalize_requires 使用
    fn register_fallback_capability(
        &mut self,
        cap_id: CapabilityId,
        version: CapabilityVersion,
        executor: Arc<dyn Executor>,
    ) -> Result<(), CapabilityRegistryError>;

    /// 启动完成: 冻结注册表
    /// 调用后 register_executor / register_fallback_capability 不再生效
    fn freeze(&mut self);

    /// 查询某个 Capability 的元信息
    fn get_capability(&self, id: &CapabilityId) -> Option<&Capability>;

    /// 查询某个 Capability 的版本
    /// 注: NodeManager 在启动时会调用此方法**一次**把所有 version 快照到内部 HashMap,
    /// 之后 Planner 从 NodeManager 读 version,不再直接调用此方法。
    fn capability_version(&self, id: &CapabilityId) -> Option<CapabilityVersion>;

    /// 查询某个 Capability 的所有提供者
    fn providers_of(&self, id: &CapabilityId) -> &[Arc<dyn Executor>];

    /// 路由决策: 给 Runtime 调用
    fn route(
        &self,
        id: &CapabilityId,
        locality: LocalityHint,
    ) -> Option<Arc<dyn Executor>>;

    /// 组合 AND 路由: 查找一个同时提供多个 Capability 的执行器
    /// 用于 NodeDef.requires 多值情况(AND 语义,见 0.1.4-capability.md §2.4.1)
    fn route_combination(
        &self,
        cap_ids: &[CapabilityId],
        locality: LocalityHint,
    ) -> Result<Arc<dyn Executor>, CapabilityRegistryError>;

    /// 所有已注册 Capability 列表(给 NodeManager 启动时快照使用)
    fn list_capabilities(&self) -> Vec<&Capability>;

    /// 快照所有 (CapabilityId, CapabilityVersion) 配对
    /// 供 NodeManager 在启动完成后一次性读取
    fn snapshot_versions(&self) -> HashMap<CapabilityId, CapabilityVersion>;
}
```

## 注册流程 + 启动顺序

Capability 有**两条注册路径**(对外部开发者只暴露 NodeRegistry 一个入口)。整个引擎启动按**严格顺序**执行,确保 NodeManager 的快照发生在 CapabilityRegistry 冻结之后:

### 阶段 1: 内置执行器注册(路径 A)

```
1. 引擎进程启动
2. 创建内置 Executor 实例:
   - GpuRasterExecutor
   - PythonAIExecutor
   - HttpApiExecutor
3. 直接调用 capability_registry.register_executor(executor)
4. 对每个 Executor:
    a. caps = executor.provides()
    b. for cap in caps:
        - 若 cap.id 首次出现: capabilities[cap.id] = cap
        - 若 cap.id 已存在: 校验 cap.version 与已有一致 → 不一致则注册失败
        - providers[cap.id].push(executor.clone())
5. 注册 fallback Capability(显式,不经 provides):
   - register_fallback_capability("fallback.image", 0, gpu_raster_executor)
   - register_fallback_capability("fallback.ai",    0, python_executor)
   - register_fallback_capability("fallback.api",   0, http_api_executor)
```

### 阶段 2: 外部扩展注册(路径 B)

```
1. 遍历配置好的 NodeSource 列表(内置 builtins + Python scan + API providers)
2. 对每个 NodeSource:
    a. regs = source.collect() → Vec<NodeRegistration>
    b. 对每个 NodeRegistration:
        i.  把 static_def 交给 NodeManager(尚未完成)
        ii. 把 capability_bindings 转发到 capability_registry.register_executor
```

### 阶段 3: Capability 注册冻结

```
1. capability_registry.freeze()
2. 之后 register_executor / register_fallback_capability 返回 Frozen 错误
```

### 阶段 4: NodeManager 快照 Capability 版本

```
1. NodeManager 调 registry.snapshot_versions() → HashMap<CapabilityId, CapabilityVersion>
2. NodeManager 把这个 HashMap 存为内部字段 capability_version_snapshot
3. NodeManager 遍历所有已注册 NodeDef:
    a. 对每个 def 调用 normalize_node_def(&mut def):
        - 若 def.requires.is_empty(): 填充 fallback(见 0.1.4-capability.md §5)
    b. def 的 capability_version 不直接存——Planner 查询时通过 capability_version_snapshot
4. NodeManager::freeze()
```

### 阶段 5: 系统就绪

```
1. 引擎创建 Scheduler facade / Session(如果是 GUI 模式)
2. Runtime 开始接受 try_start_run 调用
3. 系统可用
```

**关键约束(冻结决议 M3 + M6):**

- **M3**: CapabilityRegistry 冻结后,执行器和 fallback 无法增减(已有)
- **M6**: NodeManager 冻结后,NodeDef 无法增减或修改(targetv2 新增,见 `architecture-invariants.md` §7)
- **阶段 4 必须在阶段 3 之后**: 否则 NodeManager 的快照可能不包含最后注册的 Capability

**对外部开发者的可见性:**

| 路径 | 外部可见? | 入口 |
|------|----------|------|
| 路径 A | ✗ 不可见 | 引擎启动代码,不是 API |
| 路径 B | ✓ 可见 | `NodeRegistry::register(source)` |

这维持了 "`NodeRegistry` 是唯一对外扩展入口" 的承诺,同时允许引擎自己构造内置执行器。

## 路由规则

首版实现(简化):

```rust
fn route(&self, id: &CapabilityId, locality: LocalityHint) -> Option<Arc<dyn Executor>> {
    let providers = self.providers.get(id)?;
    if providers.is_empty() { return None; }

    providers.iter()
        .filter(|e| e.health() == HealthStatus::Healthy)
        .filter(|e| matches_locality(e, locality))
        .next()
        .cloned()
}

fn matches_locality(executor: &dyn Executor, hint: LocalityHint) -> bool {
    // 首版: 所有执行器都 match Any
    // 未来: 执行器声明自己的 LocalityProfile,匹配 hint
    hint == LocalityHint::Any || /* ... */
}
```

**首版不是目标:**

- 负载均衡
- 成本优化
- 故障转移
- 健康探测

这些是未来填槽的空间。

## 冻结决议 M3: 不支持热插拔

**决议:** Capability 注册**在 Runtime 启动时完成,运行时不支持热插拔**。

**理由:**

- 热插拔意味着执行中的 run 可能在半路切换执行器,很难保证正确性
- 热插拔意味着 `capability_version` 可能在 run 中途变化,导致签名不一致
- Insert 执行器比 update 执行器简单得多——如果真的需要动态执行器,走独立的 Provider 机制(例如 API Provider 的模型切换)

**变更门槛:** 见 `architecture-invariants.md` §7 M3。

## 状态与生命周期

- **注册阶段:** 接受 `register_executor` 调用,构建映射表
- **冻结后:** 只读,`register_executor` 返回 `Frozen` 错误
- **生命周期:** 与引擎进程同生共灭

---

## 交互回路披露(真源 ⑧)

本模块在"参数变更 → 预览刷新"路径上:

- `capability_version` 查询是 **O(1)** 内存查表,不会延长路径
- `route` 是 **O(providers)** 的扫描,首版只有少量 providers,不会成为瓶颈
- 不持有任何锁(冻结后是纯只读)

**本模块不会成为交互回路的瓶颈**,除非未来引入动态路由决策。
