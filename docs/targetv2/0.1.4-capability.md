# Capability 路由

> **Tier 1 真源。** 执行器路由的唯一主键。受 `architecture-invariants.md` 真源 ②/⑤ 管辖。

- 本文档定义 `Capability` 类型、注册表、路由规则
- 执行器声明 **提供哪些 Capability**,节点声明 **需要哪些 Capability**,Runtime 按此路由

---

## §1 动机

### §1.1 为什么要放弃 executor_type 做路由主键

target 时代的路由机制:

```rust
enum ExecutorType { Image, AI, Api }

// Scheduler 内部:
match node_def.executor_type {
    ExecutorType::Image => image_executor.execute(req),
    ExecutorType::AI    => ai_executor.execute(req),
    ExecutorType::Api   => api_executor.execute(req),
}
```

**问题:**

1. **枚举封闭**: 加一种 `VideoExecutor` 要改 `ExecutorType` 枚举 → 所有 `match` 点都要更新
2. **一对一绑定**: 一个 `ExecutorType` 对应一个执行器,不能表达"GPU 高斯模糊 vs CPU fallback 高斯模糊"
3. **职责不够细**: "AI 节点"太粗——有本地推理、远程 API、Python 子进程三种,它们的失败模式完全不同

### §1.2 Capability 路由的核心思想

> **节点声明"我需要做什么样的计算",执行器声明"我能做什么样的计算",Runtime 做中介。**

- `Capability` 是**执行能力的细粒度单位**
- 节点通过 `NodeDef.requires: Vec<CapabilityId>` 声明需求
- 执行器通过 `Executor::provides() -> Vec<Capability>` 声明能力
- 一个 Capability 可能有**多个**执行器提供(首选 + 备选 + 降级)
- Runtime 按 Capability 查路由表,加局部性策略,选一个执行器

### §2.2 Capability

```rust
struct Capability {
    id: CapabilityId,
    version: CapabilityVersion,
    input_types: Vec<DataType>,
    output_types: Vec<DataType>,
    side_effects: Vec<SideEffect>,
}

type CapabilityVersion = u32;

enum SideEffect {
    None,
    FileRead(PathPattern),
    FileWrite(PathPattern),
    NetworkCall(HostPattern),
    PythonProcess,
}
```

**字段说明:**

- `id`: 上面定义的开放字符串
- `version`: Capability 的语义版本。首版全部为 0。换算法或改行为时递增 → 通过 `ExecSignature.capability_version` 字段影响缓存命中。
- `input_types` / `output_types`: 类型校验依据。用于节点 `requires` 与 Capability 匹配时的静态检查。
- `side_effects`: 允许执行器声明副作用。**执行器没有 `FileWrite` 副作用就不能写文件**——这是真源 ① "执行器无落盘权限" 的结构化保障。

### §2.3 Executor trait

```rust
trait Executor: Send + Sync {
    fn provides(&self) -> Vec<Capability>;

    fn execute(
        &self,
        cap: &CapabilityId,
        req: ExecutionRequest,
    ) -> Result<ExecutionOutputs, ExecutorError>;

    fn health(&self) -> HealthStatus { HealthStatus::Healthy }
}
```

**关键非对称:**

- `provides()` 是**静态声明**,启动时调一次
- `execute()` 接收 `CapabilityId` 作为第一个参数——**一个执行器可以提供多个 Capability**,`execute` 通过 cap 分发到内部实现
- `health()` 是**可选**的,默认健康

### §2.4 NodeDef.requires

```rust
struct NodeDef {
    // ... 其他字段
    executor_type: ExecutorType,       // 保留作为粗粒度分组
    requires: Vec<CapabilityId>,       // 新增:路由主键(AND 语义)
    // ...
}
```

**约束:**

- `requires` **必填**,首版允许包含 0~N 个 CapabilityId
- `requires` 为空时,节点是"纯数据节点"(如 `constant_int`),不走执行器路由
- `executor_type` 保留是为了**首版兼容**——Planner 可以把 `executor_type` 当作 Capability 的默认分组

### §2.4.1 多值 `requires` 的 AND 语义

**核心规则: `requires` 是 AND 语义,不是 OR。**

```
requires: vec!["raster.load", "raster.save"]
  意味着: 本节点的执行器必须同时提供 raster.load 和 raster.save 两个 Capability
  Runtime 必须找到**一个**执行器同时提供这两个 cap
  找不到 → CapabilityUnavailable 错误
```

**不是 OR(fallback)语义**: `requires` 不表示 "任一可用即可";多值不代表多备选。

**顺序不影响签名:** `vec!["a", "b"]` 和 `vec!["b", "a"]` 构造出的 `ExecSignature.capability_version` **必须相同**—— Planner 在 `combine_capability_versions` 内部先按字典序排序再 hash。

**首版典型情况:**

- **99% 的节点**: 单值 Vec(如 `vec!["raster.gaussian_blur"]`)——AND 语义退化为单值路由
- **组合节点**: 多值 Vec(如 `vec!["raster.load", "raster.save"]`)——要求执行器同时提供

**AND 的 fallback 不存在:** 如果想表达 "GPU 优先 + CPU 备选",**不应**用多值 `requires`。应该:

- 方案 A: 两个不同的 Capability(`raster.blur.gpu` / `raster.blur.cpu`),由 Runtime 按局部性策略选一个
- 方案 B: 一个 Capability(`raster.blur`),由多个执行器提供,Runtime 按局部性选择

**方案 B 更清洁**——节点声明"我要模糊",运行时决定在哪跑。

### §2.4.2 Runtime 路由的 AND 决策

```rust
fn route_for_node(
    registry: &CapabilityRegistry,
    requires: &[CapabilityId],
    locality: LocalityHint,
) -> Result<Arc<dyn Executor>, CapabilityError> {
    if requires.is_empty() {
        return Err(CapabilityError::NoRequirements);
    }

    if requires.len() == 1 {
        // 最常见: 单值路径
        return registry.route(&requires[0], locality)
            .ok_or(CapabilityError::NoProvider(requires[0].clone()));
    }

    // AND 语义: 找出同时提供所有 cap 的执行器
    let candidates: Vec<Arc<dyn Executor>> = registry
        .providers_of(&requires[0])
        .iter()
        .filter(|exec| {
            requires[1..].iter().all(|cap| {
                registry.providers_of(cap).iter().any(|e| Arc::ptr_eq(e, exec))
            })
        })
        .cloned()
        .collect();

    match candidates.into_iter().next() {
        Some(exec) => Ok(exec),
        None => Err(CapabilityError::NoProviderForCombination(requires.to_vec())),
    }
}
```

## §3 CapabilityRegistry

### §3.1 数据结构

```rust
struct CapabilityRegistry {
    // CapabilityId → 提供者列表
    providers: HashMap<CapabilityId, Vec<Arc<dyn Executor>>>,

    // CapabilityId → 元信息
    capabilities: HashMap<CapabilityId, Capability>,
}
```

### §3.2 注册流程

Capability 通过**两条路径**写入 CapabilityRegistry,但它们都在启动时完成,对**外部扩展者**只看到 `NodeRegistry` 一个入口:

**路径 A: 内置执行器(引擎启动代码直接注册)**

```
引擎启动代码:
1. 创建内置 Executor 实例(GpuRasterExecutor / PythonAIExecutor / HttpApiExecutor)
2. 直接调用 CapabilityRegistry::register_executor(executor)
3. CapabilityRegistry 调用 executor.provides(),收集 Capability,写路由表
```

这条路径**不经过 NodeRegistry**——它是引擎自身的内部构造,不是"扩展"。对外部开发者不可见。

**路径 B: 外部扩展(经 NodeRegistry,通过 NodeSource::capability_bindings)**

```
外部扩展者:
1. 实现 NodeSource trait
2. 在 collect() 返回的 NodeRegistration 中填 capability_bindings
3. NodeRegistry::register(source) 接收注册
4. NodeRegistry 内部转发 capability_bindings 到 CapabilityRegistry
```

外部开发者**只看到 `NodeRegistry::register`** 这一个入口。它内部帮你分发给 CapabilityRegistry。

**结论:** "NodeRegistry 是唯一对**外**扩展入口" 的承诺成立。CapabilityRegistry 对外部**不可见**——它是引擎启动流程的内部实现细节。

**注册合并规则:**

无论路径 A 还是 B,最终都走到 CapabilityRegistry:

```
1. 对每个 (CapabilityId, Executor) 配对:
    a. 注册到 capabilities 表(首次)或校验版本一致(后续)
    b. 把 Executor 加入 providers[cap_id] 列表
2. 所有路径 A + 路径 B 完成后
3. CapabilityRegistry::freeze() 冻结
```

**冻结决议 M3(见 `architecture-invariants.md` §7):**

- Capability 注册**在 Runtime 启动时完成**
- **运行时不支持热插拔**
- 未来加入热插拔需要先改本文档 + 真源 ② + `4.1.3-capability-registry.md`

### §3.3 路由规则

```rust
fn route(
    &self,
    cap_id: &CapabilityId,
    locality_hint: LocalityHint,
) -> Option<Arc<dyn Executor>> {
    let providers = self.providers.get(cap_id)?;
    if providers.is_empty() { return None; }

    // 首版:按局部性提示过滤,再取第一个健康执行器
    providers.iter()
        .filter(|e| e.health() == HealthStatus::Healthy)
        .filter(|e| matches_locality(e, locality_hint))
        .next()
        .cloned()
}

enum LocalityHint {
    PreferGpu,
    PreferCpu,
    PreferRemote,
    Any,
}
```

**首版策略简化:** 路由按"第一个能匹配的"选,不做负载均衡、不做成本优化。加入这些是"填槽"而不是"挖槽"。

### §3.4 Capability 未命中

如果节点的 `requires` 包含的 CapabilityId 没有任何执行器提供:

- Planner 在构建 `ExecutionPlan` 阶段就报错: `ExecutorError::Unavailable { message: "No provider for capability 'xxx'" }`
- 不允许运行时再报——必须前置检测

## §4 与 ExecSignature 的挂接

`capability_version` 是 `ExecSignature` 的构造输入之一(见 `0.1.1-execution-models.md` §3.1):

```
ExecSignature = xxHash3_128(
    upstream_signatures,
    params_hash,
    node_def_type_id,
    node_def_version,
    cooking_context_hash,
    capability_version,     // <- 本文档负责这一项
)
```

**首版实现:**

- 首版所有 Capability 的 version 都是 0
- `capability_version` 输入恒为 0
- `ExecSignature` 行为与 target 时代一致

**未来升级某个 Capability:**

- 把它的 version 从 0 改为 1
- 所有使用该 Capability 的节点,签名自然变化 → 缓存按版本隔离
- 其他 Capability 不受影响

**关键: 为什么首版就要放这一项**

- 如果首版 ExecSignature 公式里没有 `capability_version` 这一项,未来加入它时:
  - 方案 A: 改公式 → 旧签名全部失效 → 缓存清零
  - 方案 B: 在 Planner 阶段动态换个签名 → 两套签名系统并行
- 现在占位,未来恒零改为真实 hash → 旧节点签名不变(它们使用的 Capability 版本恒为 0),新节点签名自然新

## §5 与 executor_type 的迁移路径

target 的 `ExecutorType` 枚举保留,但**降格为 Capability 的粗粒度分组**。

**关键: fallback 逻辑发生在 NodeManager 层,不在 Runtime 层**

为避免 Runtime 路由代码出现两条路径(Capability 路由 + executor_type fallback),**fallback 在节点加载时就翻译掉**:

```rust
// NodeManager 内部:加载 NodeDef 时
fn normalize_requires(def: &mut NodeDef) {
    if def.requires.is_empty() {
        // requires 为空 → 翻译为 executor_type 对应的默认 Capability
        def.requires = vec![
            default_capability_for(def.executor_type)
        ];
    }
}

fn default_capability_for(et: ExecutorType) -> CapabilityId {
    match et {
        ExecutorType::Image => "fallback.image".to_string(),
        ExecutorType::AI    => "fallback.ai".to_string(),
        ExecutorType::Api   => "fallback.api".to_string(),
    }
}
```

**对应地,CapabilityRegistry 在启动时为每个 executor_type 注册"fallback Capability"。这需要 CapabilityRegistry 提供一个显式接口:**

```rust
impl CapabilityRegistry {
    /// 注册 fallback Capability。
    ///
    /// 与 register_executor 不同: register_executor 读取 executor.provides() 里声明的 Capability;
    /// register_fallback_capability 显式把某个 executor 绑定到一个"虚拟"Capability(例如 "fallback.image"),
    /// 即使该 executor 的 provides() 不包含这个 cap_id。
    ///
    /// 仅供引擎启动代码内部使用。
    fn register_fallback_capability(
        &mut self,
        cap_id: CapabilityId,
        version: CapabilityVersion,  // fallback Capability 的版本,首版恒为 0
        executor: Arc<dyn Executor>,
    ) -> Result<(), CapabilityRegistryError>;
}

// Runtime 启动代码
registry.register_fallback_capability(
    "fallback.image".to_string(),
    0,
    gpu_raster_executor.clone(),
)?;
registry.register_fallback_capability(
    "fallback.ai".to_string(),
    0,
    python_executor.clone(),
)?;
registry.register_fallback_capability(
    "fallback.api".to_string(),
    0,
    http_api_executor.clone(),
)?;
```

**fallback Capability 的元信息:**

- `id`: `"fallback.{type}"`
- `version`: 恒为 0,永不升级(因为 fallback 是过渡机制)
- `input_types`: 与该 executor_type 的典型输入一致
- `output_types`: 与该 executor_type 的典型输出一致
- `side_effects`: `vec![SideEffect::None]`(保守)

**NodeManager 在加载 NodeDef 时对空 `requires` 的处理:**

```rust
// NodeManager 内部
fn normalize_node_def(def: &mut NodeDef) {
    // normalize_requires: 空 Vec 填充 fallback
    if def.requires.is_empty() {
        def.requires = vec![
            format!("fallback.{}", match def.executor_type {
                ExecutorType::Image => "image",
                ExecutorType::AI    => "ai",
                ExecutorType::Api   => "api",
            })
        ];
    }
}
```

**注意:** NodeManager 修改的是**自己持有的 NodeDef 内部快照**,不修改 NodeSource 原始传入的 NodeDef。NodeSource 的 NodeDef 一旦传入 NodeRegistry 后由 NodeManager 接管所有权——NodeManager 可以自由加工。

**结果:**

- **Runtime 的路由代码只有一条路径**——永远按 `NodeDef.requires` 查 `CapabilityRegistry`
- Runtime **不知道** `executor_type` 的存在
- "空 requires" 的情况在 NodeManager 层就消失了,不会污染 Runtime

**首版工作流程:**

1. 所有现有节点继续声明 `executor_type: ExecutorType`
2. 现有节点的 `requires` 首版可以为空
3. NodeManager 加载时自动 `normalize_requires`,填入 `fallback.{type}`
4. Runtime 路由走单一路径: `CapabilityRegistry::route(requires[0], locality)`

**未来(去执行器时代):**

- 所有节点逐步填充真实的 `requires`(如 `["raster.gaussian_blur"]`)
- `fallback.*` Capability 被真实 Capability 替代
- 最终 `executor_type` 字段标记为 `deprecated`
- 某个版本后移除该字段(破坏性变更,需改真源 ⑤)

## §6 首版落地清单

**必须实现:**

1. `NodeDef.requires: Vec<CapabilityId>` 字段存在(即使首版全部节点 requires 为空)
2. `Executor::provides()` 方法存在(即使首版返回 `executor_type` 映射的默认 Capability 组)
3. `CapabilityRegistry` 模块存在(即使首版是 `HashMap` 薄包装)
4. Runtime 路由代码有 "按 Capability 查表" 分支(即使首版走退化路径)
5. `ExecSignature` 公式包含 `capability_version` 输入,首版恒为 0

**允许推迟:**

- 所有节点迁移到 Capability 路由
- `executor_type` 字段移除
- 多执行器竞争 / 负载均衡
- 局部性策略具体实现
- 运行时热插拔
