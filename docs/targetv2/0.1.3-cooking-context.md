# CookingContext

> **Tier 1 真源。** Graph 多次求值的唯一机制。受 `architecture-invariants.md` 真源 ⑥ 管辖。

- 本文档定义 `CookingContext` 类型及其在 Planner、Runtime、ExecSignature 中的位置
- 它**不**替代 `List<T>`——两者职责严格分开,边界见 §4

---

## §1 动机与背景

### §1.1 为什么需要 CookingContext

整个图式引擎有两种 "同一张图跑多次" 的场景:

1. **批处理 / 序列帧**: "对 100 帧各跑一遍这张图"
2. **参数扫描 / 多种子**: "对 {seed=1, 2, 3} 各跑一遍这张图"

target 时代的做法是 **把这两种场景塞进 `List<T>`**——图像节点默认对 `List<Image>` 做 map 执行。这条路径的三个问题:

1. **类型系统污染**: 节点既要处理 `Atomic(Image)` 又要处理 `List(Image)`,增加语义负担
2. **`List<BoundingBox>` 和 `List<Image>` 被当成同一类东西**: 前者是值,后者是调度维度,但类型系统无法区分
3. **多维扫描困难**: `{frame × seed}` 需要 `List<List<Image>>`,被真源禁止

### §1.2 CookingContext 的核心思想

引用自 Houdini / OpenTimelineIO 的 cooking 概念: **图本身不知道批次,Planner 按 Context 枚举图的多次求值**。

- 类型系统始终看到 `Image`,不看到 `List<Image>`
- Planner 拿到 `(Graph, CookingContext)`,展开为 N 次求值
- 每次求值是一个**独立的** `ExecutionPlan` 子任务
- 多次求值的结果由 **显式 collect 节点** 汇总回 `List<T>`(如果需要)

## §2 数据模型

### §2.1 CookingContext

```rust
struct CookingContext {
    dimensions: HashMap<DimensionId, DimensionValue>,
}

type DimensionId = String;

enum DimensionValue {
    Int(i64),
    Float(f64),
    String(String),
    Json(serde_json::Value),
}
```

**首版状态:**

- `dimensions` **可以为空**
- 空 context 等价于 "对整图求值一次"
- 首版不要求任何具体维度被实现

### §2.2 CookingContextRange

Planner 在展开图时,需要知道 **哪些 context 组合要被枚举**。这由 `CookingContextRange` 表达:

```rust
struct CookingContextRange {
    axes: Vec<CookingAxis>,
}

struct CookingAxis {
    dimension: DimensionId,
    values: Vec<DimensionValue>,
}
```

**语义:**

- 多个 `axes` 做**笛卡尔积**(即 `frame × seed` 展开为 `len(frames) × len(seeds)` 次求值)
- 空 `axes` = 单次求值,`context = CookingContext { dimensions: {} }`
- 求值顺序**未定义**(Planner 可以重排 / 并行)

### §2.3 CookingContextHash

为了嵌入 `ExecSignature`:

```rust
type CookingContextHash = u64;

impl CookingContext {
    fn hash(&self) -> CookingContextHash {
        // 稳定序列化 dimensions 后走 xxHash3-64
        // 空 context 的 hash 约定为 0
    }
}
```

**关键约束:**

- 空 context 的 hash **恒为 0**
- 这是 `ExecSignature` 里 `cooking_context_hash` 占位的值
- **这个约定永远不能改**——否则所有 target 时代的签名会和 targetv2 签名不同

## §2.4 向后兼容的关键: `cooking_sensitivity` 声明

**核心约束:** 未来加 CookingContext 维度**不破坏**旧节点的缓存——这个承诺只在"Planner 知道哪些节点不受新维度影响"时才成立。这靠 `NodeDef.cooking_sensitivity` 字段保障。

```rust
struct NodeDef {
    // ... 其他字段
    cooking_sensitivity: Vec<DimensionId>,  // 默认 empty
}
```

**默认与显式声明:**

| `cooking_sensitivity` | 含义 |
|----------------------|------|
| `vec![]`(默认) | 本节点类型对**任何** CookingContext 维度都不敏感。但**节点实例**可能因 Animated 参数自动加入敏感维度(见下) |
| `vec!["frame"]` | 本节点类型本身关心 `frame` 维度(无论参数是否动画) |
| `vec!["frame", "seed"]` | 本节点类型关心两个维度。 |

**实例级动态推导(targetv2 关键):**

`NodeDef.cooking_sensitivity` 是**节点类型级别**的静态声明,但 Planner 在构造签名时使用的是**有效 cooking_sensitivity** —— 它合并了 NodeDef 的静态声明 + 节点实例的 Animated 参数自动推导:

```
effective_sensitivity = NodeDef.cooking_sensitivity
                      ∪ ⋃{ animated_param.curve.context_key for animated_param in node.params }
```

**含义:**

- 一个 `gaussian_blur` 节点的 `NodeDef.cooking_sensitivity = []`(默认)
- 用户在 UI 给 `sigma` 参数加了 keyframe → 实例的 `params["sigma"] = Animated(curve { context_key: "frame", ... })`
- Planner 在构造签名时,**自动推导**该实例的 effective_sensitivity = `["frame"]`
- `cooking_context_hash` 包含 frame 值 → 不同 frame 的签名不同 → 缓存按帧分片
- 用户去掉 keyframe → 实例的 `params["sigma"] = Constant(2.0)` → effective_sensitivity 自动恢复为 `[]` → 单一签名 → 单一缓存条目

**这让"作者标注 cooking_sensitivity"成为可选:** 默认为空,用户的动画参数自动驱动敏感度。详细机制见 `0.1.0-models.md` §2.5.2。

**Planner 构造 `cooking_context_hash` 的算法:**

```rust
fn build_cooking_context_hash(
    context: &CookingContext,
    sensitivity: &[DimensionId],
) -> CookingContextHash {
    if sensitivity.is_empty() {
        return 0;  // 空敏感度 → 恒零
    }
    let mut filtered = BTreeMap::new();  // 排序确保稳定序列化
    for dim_id in sensitivity {
        if let Some(value) = context.dimensions.get(dim_id) {
            filtered.insert(dim_id.clone(), value.clone());
        }
    }
    xxhash3_64(stable_serialize(&filtered))
}
```

**向后兼容保证:**

- **旧节点**(不声明 `cooking_sensitivity`,默认空)→ hash 恒为 0 → 未来加任何维度都不影响旧签名 → 缓存继续命中
- **新节点**(显式声明)→ 只有声明的维度影响 hash → 不声明的维度不影响
- **节点首次开始声明某个维度**时,该节点的签名会变化一次(从恒零到真实 hash),这是**预期行为**——节点作者在改 cooking_sensitivity 时知道会触发一次缓存失效

**静默踩坑警告:**

如果 Planner **不**按 `cooking_sensitivity` 过滤 context,而是直接用完整 context 的 hash,那么:
- 用户把默认 frame range 从 `{}` 改成 `{"frame": 0..100}`
- 所有节点的 `cooking_context_hash` 都会变化(即使大部分节点和 frame 无关)
- 所有节点的签名变化
- **所有缓存失效**

这是典型的静默踩坑——行为看起来"对"(签名变了,缓存失效了,一切有序),但实际上用户改一个默认值就让整个项目重跑。`cooking_sensitivity` 的存在就是为了阻止这种情况。

## §3 与 ExecSignature 的挂接

`ExecSignature` 的完整构造公式(见 `0.1.1-execution-models.md` §3.1):

```
ExecSignature = xxHash3_128(
    upstream_signatures,
    params_hash,
    node_def_type_id,
    node_def_version,
    cooking_context_hash,      // <- 本文档负责这一项
    capability_version,
)
```

**首版实现:**

- Planner 在构造 `ExecSignature` 时,`cooking_context_hash` 传入当前 context 的 hash
- 空 context → 0 → 签名行为与 target 时代一致
- 未来加入 frame / seed 维度时, `cooking_context_hash` 自然变化 → 不同 frame 的同一节点有不同签名 → 缓存按 frame 隔离

**为什么首版就要放这个字段:**

- 如果首版**不**放,未来加入 CookingContext 时,会有两种痛苦选择:
  - A. 改 ExecSignature 公式 → 所有历史签名失效 → 缓存清零
  - B. 额外加一个 "cooking context 签名" 外挂 → 两套签名系统并行,永远别扭
- 现在放一个恒零占位, 未来改恒零 → 有意义的 hash 时, 旧节点的签名**不变**(因为旧节点不用 context, context 恒为空, hash 恒为 0),新节点的签名**自然新**——完美的"向后兼容填槽"

## §4 与 `List<T>` 的边界

### §4.1 职责对照表

| 用途 | 机制 |
|------|------|
| 序列帧(对每帧跑一遍整图) | **`CookingContext`** 的 `frame` 维度 |
| 批处理生成(多种子对比) | **`CookingContext`** 的 `seed` 维度 |
| 参数扫描(参数 A 的不同取值) | **`CookingContext`** 的自定义维度 |
| 视频帧流 | **`CookingContext`** 的 `time` 维度 |
| 检测器输出(图上有 N 个 bbox) | **`List<BoundingBox>`**(值) |
| 角点检测输出 | **`List<Keypoint>`**(值) |
| 调色板 | **`List<Color>`**(值) |
| 图层引用集合 | **`List<LayerRef>`**(值) |

### §4.2 判据(必须明文记住)

> **如果集合的典型语义是"对每个元素独立跑一遍整段下游",它就不应该是 `List<T>`,它是 `CookingContext` 的一个维度。**
>
> **如果集合的典型语义是"整体作为一个值被下游消费",它才是 `List<T>`。**

### §4.3 `List<Image>` 的特殊性

`List<Image>` 是两种语义**最容易混淆**的地方:

- 有时它表示"一批等待处理的图"(应该是 `CookingContext.frame` 维度)
- 有时它表示"一个节点的多个 Image 输出聚合成一个值"(应该是 `List<Image>` 值)

**首版策略:**

- `List<Image>` 作为**过渡白名单**保留
- 明确标注"在 `CookingContext` 未覆盖场景时临时使用"
- 当 `CookingContext.frame` 维度被启用后,`List<Image>` 应该被**仅限于后者语义**(节点聚合输出)
- `List<List<Image>>` 永久禁止(由 `0.1.0-models.md` §1.2 `DataType` 约束保障)

### §4.4 从 CookingContext 收成 `List<T>`

当 Planner 对一个 context 范围枚举后,**如果**下游节点需要把结果汇总成一个 `List<T>` 值,应通过**显式 collect 节点**:

```
graph.node("render_frame")  // output: Image, 不是 List<Image>
     .cook_over(CookingAxis::Frame(0..100))

graph.node("collect_frames")  // input: Image(从 Cooking 上游), output: List<Image>
```

**关键:** `collect_frames` 节点是**显式的**,不是 Planner 自动做的魔法。这让数据流从 Cooking 维度到 `List<T>` 的转换**出现在图上**,用户能看见、能审计、能解耦。

**反方向(从 `List<T>` 解开成 N 次求值)首版不支持**——如果你手上拿的是 `List<Image>`,你只能把它当作一个值使用,不能期望 Planner 自动展开。

**首版 limitation:**

- `List<BoundingBox>` → "对每个 bbox 独立处理" 这种常见用法在首版无法表达
- 用户需要手动把 `List<T>` 通过导出节点写入磁盘,再由外部流程构造新 Graph(低效)
- 或在执行器内部循环(把调度维度藏在执行器里,违反判据精神)

**未来扩展方向(非承诺):**

- 引入**显式 spread 节点**,把上游的 `List<T>` 展开为临时 CookingContext 维度
- Planner 在遇到 spread 节点时识别,对下游按新维度枚举
- spread 节点是**未来工作**,不进首版,也不影响当前真源
- 引入 spread 节点时**无需**改 CookingContext 机制本身——它只是一种新节点类型

## §4.5 CookingContext 与 DirtyState 的关系

`DirtyState` 的首版定义(见 `4.1.1-planner.md`)只按 `NodeId` 记脏,**不按 CookingContext 分片**:

```rust
struct DirtyState {
    dirty_nodes: HashSet<NodeId>,
    dirty_reasons: HashMap<NodeId, DirtyReason>,
}
```

这意味着**首版无法**表达 "节点 N 在 frame=5 是脏的,在 frame=10 不是脏的"。

**首版策略: 脏判定 + 命中判定分离**

- `DirtyState` 只回答 "这个节点**有没有可能**需要重算"(结构级脏)
- **真正的命中判定**由 Runtime 在执行前查 cache: `ExecSignature` 命中 → 跳过,未命中 → 执行
- 这样,节点 N 在 frame=5 和 frame=10 的签名不同(若 sensitivity 包含 frame),自然隔离——Runtime 对每个 context 单独查 cache

**这带来的效果:**

1. Planner 不需要按 context 分片 DirtyState → 空间复杂度保持 `O(nodes)`
2. 用户追加 CookingContext range(如 frame 0..100 → 0..200)时,追加的 100 个 context 下的节点"签名新",缓存未命中,自动重算;既有的 0..100 签名不变,缓存继续命中
3. 用户缩减 range(如 0..200 → 0..100)时,缩减的 100 个 context 的缓存条目继续存在(LRU 逐步淘汰)

**首版 limitation:**

- 如果某个节点在某个 context 下出错重算,DirtyState 无法精确标记"只有这个 context 脏"——它会标整个节点脏,影响其他 context 的未来求值决策
- 首版工作流下影响有限;未来若需精确增量,可扩展到 `(NodeId, ContextHash)` 粒度,**但不用改核心**,只扩展 DirtyState 内部表示

## §5 Planner 的枚举规则

Planner 在处理 `CookingContextRange` 时的行为:

```rust
fn plan(
    graph: &Graph,
    range: &CookingContextRange,
    dirty: &DirtyState,
) -> ExecutionPlan {
    let contexts = enumerate_cartesian(range);
    let subtasks = contexts.into_iter().map(|ctx| {
        plan_single(graph, ctx, dirty)
    }).collect();
    ExecutionPlan { subtasks }
}
```

**首版简化实现:**

- `enumerate_cartesian` 首版就是一个嵌套循环
- `plan_single` 与 target 时代的 `plan()` 行为一致,只是多了 `ctx` 参数
- 空 range → 单次求值 → 退化为当前行为

**不是目标:**

- 首版**不**实现跨 context 的依赖分析(例如"前一帧的输出作为后一帧的输入")
- 首版**不**实现 context 范围内的部分增量(改一个 context 维度只重算受影响 context)
- 这些未来可以加,但**不影响**本文档定义的机制

## §6 首版 Dimension 清单

首版 `CookingContext` 支持的 `DimensionId`(枚举值约定):

| DimensionId | 类型 | 首版状态 | 说明 |
|------------|------|---------|------|
| (空) | — | 首版支持 | 默认单次求值 |
| `"frame"` | `Int` | **[占位]** | 未来序列帧;首版不实现 |
| `"batch_id"` | `Int` | **[占位]** | 未来多批次;首版不实现 |
| `"seed"` | `Int` | **[占位]** | 未来多种子;首版不实现 |
| `"variant"` | `String` | **[占位]** | 未来多变体;首版不实现 |
| `"resolution_tier"` | `String` | **[占位]** | 未来多分辨率;首版不实现 |

**关键:** 这些 DimensionId 在首版**不是**受保留关键字——它们是将来**建议使用**的标准名字。任何 DimensionId 只要在某次 Planner 调用中被认知就可以用,但跨项目共享节点应遵守这个清单。

## §7 与持久化的关系

CookingContext 的持久化归属(对应真源 ⑦):

| 状态项 | 归属 |
|--------|------|
| 项目默认 Context range(如 "默认渲染 frame 0..100") | **进项目文件** |
| 当前 UI 选中的 Cooking axis(如 "查看 frame=42 的预览") | **只在运行时(Session)** |
| 最近一次求值使用的 Context range | **只在运行时(Runtime)** |

## §8 典型反模式清单

以下做法**禁止**:

1. 把 CookingContext 塞进 `Value::List` 变体
2. 让 Planner 自动"展开" `List<T>` 为 Cooking 维度
3. 在 `List<T>` 和 `CookingContext` 之间定义隐式转换(显式 collect 节点是唯一通道)
4. `cooking_context_hash` 在 `ExecSignature` 公式中缺席
5. 空 CookingContext 的 hash **不是 0**
6. 支持 `List<List<T>>`(即使是为了表达 `Cooking × Cooking`)
