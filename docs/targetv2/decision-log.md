## 高层摘要

本轮对齐得到的最高优先级决策如下：

1. 首版不再围绕单一视频调色 demo 叙事，而是三类执行器平权。
2. 首版必须同时有：图片 demo、视频 demo、一个综合 demo。
3. 综合 demo 采用：`Python 出主图和 logo -> API 生视频 -> 图形节点合成/调色 -> 输出视频`。
4. 图形处理节点、本地可控 Python 后端节点、云端 API 节点是三条同等主线。
5. Python 节点 = 可控后端里的底层工作流节点，不引入高层任务节点叙事。
6. API 节点 = 黑盒任务节点，输出接口稳定、少而关键。
7. 图片和视频共享一套图形处理节点，视频在引擎里按 frame 求值为主。
8. 静态图接入视频链时，默认自动广播到每帧。
9. 参数动画首版聚焦 `Constant + Animated(Curve)`，不写表达式。
10. 参数连线优先于本地值；本地值和关键帧保留作 fallback。
11. 连线上传递的是当前 frame 采样后的具体值，不是整条曲线对象。
12. `Continuous` 是首版硬要求，但不把 `60fps` 写成硬承诺，表述为“尽可能快的持续反馈”。
13. 慢节点在 `Continuous` 中采用 cache-only；未命中时占位并支持暂停预热后恢复。
14. 结果历史是工作流核心，不是纯后台缓存。
15. 节点结果需要支持：历史浏览、当前版本选用、标记、清理、撤销恢复。
16. 引入显式 `产物管理节点`，它是图里正式存在的通用节点。
17. 节点原生历史能力与显式产物管理节点共享同一套产物管理抽象。
18. 当前选中版本属于正式图语义，切换后只重算下游，并参与执行/缓存语义。
19. 项目文件应尽量自包含：图结构、源素材、候选历史、导出历史都跟项目走。
20. 当前 frame、临时界面状态、undo/redo、preview cache、凭证不进项目文件。

## 决策清单

### 产品与 Demo

1. 首版不选择单一路线，而是三类节点都要有最小 demo，并且至少有一个三类节点串联的综合 demo。
2. 不设单一主流程锚点，图片、视频、实时三条线并列推进。
3. 三种核心节点/执行来源指：图形处理节点、可控 Python 后端节点、云端 API 节点。
4. 三类执行器在首版文档里是同等主线能力。
5. 首版 demo 的最低门槛是：三类节点各自有最小 demo，且至少有一个三类串联 demo。
6. 综合 demo 的主数据对象不是二选一，图片流和视频流都要有。
7. 图片流和视频流在首版里要同等完整，不接受一条完整一条简化。
8. Python 这条线更像 ComfyUI 风格的可控后端计算，可部署在本机或远端设备。
9. Python 本地/远端只是部署位置差异，属于同类可控后端执行器。
10. Python 后端与云端 API 的本质区别是：可控后端 vs 黑盒服务。
11. 图形处理节点默认画像是：本地、确定性、适合实时预览。
12. 综合 demo 必须在同一张图里把三类执行器串起来，而不是拆成多图工作流。
13. 图形处理节点是一套统一节点，同时处理图片和视频，不拆成两套处理节点。
14. 静态图片接到视频链时，默认自动广播到每帧。
15. 所有节点设计上都具备多输出能力，输出结构尽量和输入对称。
16. 节点输出接口采用稳定命名、提前声明，不允许运行时动态改输出名。
17. 同一套节点的不同用途主要靠参数和提示词区分，不靠拆新的节点类型。
18. 参数被上游连线后，上游连线优先于本地参数值和关键帧。
19. 参数被连线覆盖时，本地值和关键帧保留作 fallback，断线后恢复。
20. 带关键帧的上游节点接到下游参数时，连线上传的是当前 frame 采样后的具体值。

### 参数动画与时间模型

21. 首版参数动画覆盖范围不只 `Float/Int/Color`，而是几乎所有标量都支持。
22. `Bool`、`String` 这类离散标量只支持跳变切换，不做线性插值。
23. 参数表达式首版完全不写进文档，只保留常量和关键帧两态。
24. 认可“节点本身没有时间感，时间通过 `frame` 这种上下文传入”的模型。
25. 允许存在执行器内部有状态的节点，但节点对外仍按 frame 求值。

### Continuous 与实时

26. `Continuous` 是首版硬要求。
27. `Continuous` 的目标表述是“尽可能快即可”，不在文档里写死 `60fps`。
28. `Continuous` 中的慢节点采用 cache-only；未命中时占位并提示用户 warm。
29. 支持在 `Continuous` 中暂停后跑一次 `OneShot Full` 预热，再自动恢复。
30. `Continuous` 运行中改参数/改图时，在 tick 边界热替换当前 plan，不整次重启。

### 结果历史、候选选择、产物管理

31. 用户默认只想在项目里看到正式产物和可用候选，不想看到系统纯后台缓存。
32. Python/API 多轮生成的候选结果默认属于用户可见候选历史，不是后台缓存。
33. 这些候选历史要跟项目一起保存，关项目后重开仍能看到。
34. 候选图/视频默认打包进项目文件，而不是只记外部路径。
35. 候选历史主要按节点输出历史组织，而不是按整图快照组织。
36. 用户需要从某个节点的历史里选择一个当前生效版本继续往下游走。
37. 选中旧候选版本后，它直接成为当前输出，不需要重跑上游确认。
38. `save_image`、`save_video` 这类导出节点的结果也进入节点输出历史。
39. `load_image`、`load_video` 等源素材默认打包进项目文件。
40. 项目文件整体原则是“尽量自包含”。

### 扩展入口与注册

41. 新增节点的对外扩展入口最终统一，不按执行器分不同入口。
42. 节点和执行器注册在启动时完成并冻结，不支持运行中热插拔。
43. 首版不支持用户直接写任意自定义 Python 脚本节点。
44. 若同种能力可由不同后端执行，用户更倾向显式区分执行来源，而不是自动路由。
45. 在用户层面，“本地/可控后端”和“云端 API”更适合拆成不同节点，而不是同节点内选后端。

### 项目状态与 Session 边界

46. 节点历史中的“当前选中版本”要跟项目一起保存，重开项目后恢复。
47. 当前查看 frame / 播放头位置只属于 Session，不进项目文件。
48. undo/redo 只属于 Session，不进项目文件。
49. preview cache 只属于 Session，不进项目文件。
50. 项目文件对用户应表现为单文件 bundle，而不是普通目录。

### 视频模型与 I/O

51. 视频在引擎里以“按 frame 求值”为主，而不是单独的大黑盒对象为主。
52. `load_video` / `save_video` 首版主要只是视频文件和按帧图像流之间的边界节点。

### 节点历史 UI 与布局

53. 候选结果对比主要发生在单个节点的历史内部，而不是跨节点统一比。
54. 节点位置、分组展开状态、画布视口等编辑器布局要跟项目一起保存。
55. 当前选中的节点、当前焦点面板、当前打开的历史窗口等临时界面状态不保存。

### 凭证与后端可用性

56. 凭证绝不进项目文件。
57. 非敏感的后端目标信息可以进项目，用于恢复工作语义。
58. 若项目记录的后端当前不可用，允许离线浏览和挑选历史，但执行时再报错。

### 文档主例子与代表性流程

59. `Python 出主图和 logo -> API 生视频 -> 图形节点合成调色 -> 输出视频` 直接作为文档代表性综合 demo。
60. 除综合视频 demo 外，还要有一个独立的代表性图片 demo。
61. 独立图片 demo 也要覆盖三类执行器，而不是只做轻量图片链。
62. 独立图片 demo 也必须包含“多轮生成 -> 历史对比 -> 选中一个继续往下游走”。

### 生成节点与普通处理节点的历史策略

63. Python/API 这类生成节点默认每次成功执行都留一条可见候选历史。
64. 普通图形处理节点默认不自动留可见历史。
65. 普通节点是否留历史不交给用户随手开关，而取决于节点设计和是否接入产物管理能力。
66. “是否接入产物管理器”主要由节点设计时写死，不由用户后期切换。

### 产物管理节点与统一产物抽象

67. 当 Python AI 是一组子节点组成时，候选历史和版本选择主要由专门的结果/产物管理节点来承载。
68. 这个“产物管理节点”是图里显式存在的正式节点。
69. 不是所有结果都必须显式接产物管理节点；某些 API 生成节点可以原生自带历史能力。
70. 节点原生历史能力与显式产物管理节点最终共享同一套产物管理抽象。
71. 单个产物管理节点一次主要管理一个结果流，不做多结果仓库节点。
72. 产物管理节点对下游默认输出当前选中版本。
73. 在产物管理节点里切换历史版本时，只重算下游，不重算上游。
74. 产物管理节点是一个通用节点，不按图片/视频拆成不同节点。
75. 产物管理节点跟随输入类型工作：接图片就管理图片版本，接视频就管理视频版本。
76. 产物管理节点首版不额外暴露版本元数据 pin，先把主数据流和版本选择做稳。
77. 产物管理首版就区分“静态结果”和“时序结果”两种形态。
78. 首版先不进一步区分“普通时序结果”和“模拟类结果”。
79. 首版就支持后台生成/后台缓存。
80. 后台生成完成后，新结果自动回填到对应节点/产物管理节点的历史列表。
81. 对长时间生成任务，若后端能给中途预览，首版就应先显示预览。
82. 中途预览先只作临时预览，不进入正式候选历史。
83. 正式候选历史首版支持简单标记。
84. 候选对比首版最低形态是“节点级结果面板”，一个节点一个结果库面板。
85. 在结果面板里的“切换当前版本”“给版本打标记”等操作要支持撤销重做。
86. 首版支持清理节点历史里的旧候选结果。
87. 清理删除后的恢复路径首版依赖 undo/redo，不另做回收站。

### Python 节点与 API 节点的层级定义

88. Python 节点在首版文档里明确写成可控后端的底层工作流节点。
89. 首版文档完全按底层 Python 工作流节点来写，不提前引入高层封装节点概念。
90. “Python 节点”的正式定义就是：可控后端里的底层工作流节点，例如 `load_checkpoint`、`clip_text_encode`、`ksampler`、`vae_decode`。
91. API 节点在首版文档里明确写成黑盒任务节点。
92. API 节点的输出接口尽量稳定、少而关键，方便直接接到下游图形节点。
93. API 节点参数采用“共同核心参数 + provider 专属扩展参数”的分层模式。

### Python/API 结果管理的统一方式

94. Python 底层工作流这边，结果历史和版本选择主要通过显式产物管理节点暴露。
95. 黑盒 API 节点可以原生自带结果历史和结果面板，不一定额外插产物管理节点。
96. API 节点自带的结果面板和产物管理节点的结果面板，用户体验要尽量一致。
97. 切换当前选中版本属于正式图语义变化，必须影响下游执行和缓存签名。

### 文档层级与后续落地

98. `README` 和 `roadmap` 的主叙事要改成“三类执行器平权 + 图片 demo + 视频 demo + 一个综合 demo”。
99. “产物管理能力/节点 + 当前选中版本参与图语义”应提升到真源/核心模型层，而不是只留在实现细节里。
100. 下一步优先产出是“文档对齐清单”，先逐篇指出 `docs/targetv2` 哪些地方要改、怎么改。
