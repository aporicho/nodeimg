## §1 执行请求与结果

### §1.1 ExecutionRequest

```rust
struct ExecutionRequest {
    run_id: RunId,
    node_id: NodeId,
    node_def: Arc<NodeDef>,
    inputs: ExecutionInputs,
    exec_signature: ExecSignature,
    generation: GenerationId,
    cooking_context: CookingContext,     // targetv2 新增
    fidelity: EvaluationFidelity,        // targetv2 新增
    timeout_ms: Option<u64>,
    cancel_token: CancelToken,
    progress_sink: ProgressSink,
}
```

**字段语义:**

- `run_id`: 所属执行轮次
- `node_id`: 当前执行的节点实例
- `node_def`: 权威节点静态定义
- `inputs`: 已解析完成的最终输入值
- `exec_signature`: 本次语义计算签名(见 §3)
- `generation`: 缓存代际,仅用于并发防回灌
- **`cooking_context`**: 当前求值的 CookingContext(首版可为空)。见 `0.1.3-cooking-context.md`
- **`fidelity`**: 求值精度模式(`Preview | Full`)。见 `0.1.2-interaction-loop.md` §2.2
- `timeout_ms`: 节点级超时;默认来自 `NodeDef.execution.timeout`
- `cancel_token`: 节点级取消令牌
- `progress_sink`: 节点级进度上报通道

### §1.2 ExecutionInputs / ExecutionOutputs

```rust
type ExecutionInputs = HashMap<String, Value>;

struct ExecutionOutputs {
    values: HashMap<String, Value>,
    /// 执行器诚实报告实际达到的求值精度
    /// Runtime 据此决定是否写正式 cache(见 4.1.2-runtime.md 流程 1b)
    fidelity_achieved: EvaluationFidelity,
}
```

**约束:**

1. `values` key 对应正式接口名称
2. 输入 key 对应正式输入口名称;输出 key 对应正式输出口名称
3. 参数输出接口的值不由执行器手工构造,而由引擎在正式接口层补齐
4. **`fidelity_achieved` 必填**——执行器必须诚实报告实际精度:
   - Full 模式下,必须返回 `Full`
   - Preview 模式下,如果执行器真的降采样了,返回 `Preview { max_side_used, precision_used }`
   - Preview 模式下,如果执行器忽略 hint 全精度算了(首版允许),返回 `Full`
   - **谎报是数据正确性 bug**——见 `4.11.2-executor-contract.md`

### §1.3 EvaluationFidelity(targetv2 新增)

```rust
enum EvaluationFidelity {
    Preview {
        max_side: Option<u32>,       // 可选分辨率上限(长边像素)
        precision: PreviewPrecision, // 可选精度降级
    },
    Full,
}

enum PreviewPrecision {
    Float32,
    Float16,
    Int8,      // [占位] 首版不开
}
```

**约束:**

1. `ExecutionRequest.fidelity` **必填**,任何构造点都必须显式指定
2. 首版允许 `Preview` 与 `Full` 的执行器行为一致,但字段必须存在
3. `Full` 模式下执行器**不得**偷偷降分辨率或精度
4. 详细语义见 `0.1.2-interaction-loop.md` §2.2

### §1.4 ExecutionMode —— 一次性执行 vs 持续 cook(targetv2 M3,首版真实实现)

`fidelity` 控制"一次执行的精度",`ExecutionMode` 控制"执行的形态"。两者正交。**首版两种模式都真实实现。**

```rust
enum ExecutionMode {
    /// 一次性执行: 提交一个 Plan, 跑完后回到 Idle
    /// 用于: 导出、批处理、CLI 单次执行、首次预热
    OneShot {
        fidelity: EvaluationFidelity,
    },

    /// 持续 cook: TouchDesigner 风格 60fps 持续求值
    /// Runtime 进入 tick loop,按 target_fps 持续 cook 同一 plan
    /// 退出: 调用方显式 stop_continuous() 或 cancel
    /// 用于: 实时交互预览、实时视频播放、流体模拟实时演示
    Continuous {
        tick_source: TickSource,
        target_fps: f32,
    },
}

/// 持续 cook 的时钟源
enum TickSource {
    /// **[首版支持]** OS 时钟 —— 每 1/target_fps 秒触发一次 cook
    OsClock,
    /// **[占位]** 外部时钟 —— MIDI clock / OSC tick / audio sample clock 等
    /// id 是开放字符串,允许未来注册新时钟源
    External(String),
    /// **[占位]** 数据流驱动 —— 例如视频流的下一帧到达就 cook 一次
    DataPull(String),
}
```

**首版实现:**

- `OneShot { fidelity }` —— **完整实现**(覆盖 Preview/Full 两种 fidelity)
- `Continuous { OsClock, target_fps }` —— **首版完整实现**(60fps 实时 cook)
- `Continuous { External(_) | DataPull(_), .. }` —— **占位**,首版返回 `RuntimeError::TickSourceNotImplemented(name)`

**Continuous 模式的关键语义(首版冻结):**

1. **clock-driven cooking_context**: Runtime 在每个 tick 内部生成 `CookingContext` —— 通常包含 `frame: current_tick`(根据 target_fps 与项目设置的视频源 fps 推算)
2. **慢节点 cache-only**: `realtime_capable=false` 的节点**不重新执行**——
   - 命中正式 cache → 用缓存
   - 未命中 → 不执行;发 `NodeMissingInContinuous { node_id }` 事件;用占位(黑帧)
3. **退出条件**: 用户显式 `stop_continuous()` 或 `cancel`,**不**自然结束
4. **single-flight 守卫**: 一次最多一个 Continuous run + Continuous 与 OneShot 互斥(进入 Continuous 时若有 OneShot 在跑,先取消)
5. **plan 缓存**: 进入 Continuous 时 Planner 生成一次 plan,Runtime 在 tick loop 中**复用**这个 plan,直到用户改图(GraphChangedEvent → 重新规划)

**对 EngineFacade::ExecuteRequest 的影响:**

```rust
struct ExecuteRequest {
    target: ExecuteTarget,
    /// targetv2 修订: 之前是 fidelity 字段,现在合并到 mode
    /// 对外允许省略,默认 OneShot { fidelity: Full }
    mode: Option<ExecutionMode>,
}
```

GUI 通常构造 `Some(OneShot { fidelity: Preview { ... } })` 或 `Some(Continuous { OsClock, 60.0 })`;CLI 通常省略(默认 OneShot Full)。

详细的 Continuous 模式 Runtime 流程见 `4.1.2-runtime.md` §Continuous 模式。

### §1.5 Plan-level Lifecycle Hooks(targetv2 M5 新增)

执行器除了 `execute()` 外,还有**两个 plan-level lifecycle 回调**,Runtime 在 Plan 边界调用:

```rust
trait Executor: Send + Sync {
    // ... 已有方法

    /// Plan 开始执行前,Runtime 调用一次
    /// 用途: 打开跨 execute() 的资源(视频 encoder、temp file、模型 warm-up)
    /// default: no-op
    fn on_plan_started(&self, ctx: &PlanLifecycleContext) -> Result<(), ExecutorError> {
        Ok(())
    }

    /// Plan 完成后,Runtime 调用一次(无论成功/失败/取消)
    /// 用途: 关闭跨 execute() 的资源(encoder.finalize、清理 temp、释放 GPU 缓存)
    /// default: no-op
    fn on_plan_finished(&self, ctx: &PlanLifecycleContext, status: ExecutionTerminalStatus) {
        // no-op
    }
}

struct PlanLifecycleContext<'a> {
    /// 当前 plan 的 run_id
    pub run_id: RunId,
    /// 当前 plan 的所有 PlannedNode 的子集 —— 仅包含使用本执行器的节点
    pub my_nodes: Vec<&'a PlannedNode>,
    /// 当前模式(OneShot 或 Continuous)
    pub mode: &'a ExecutionMode,
}
```

**关键约束:**

1. **default no-op**: 大多数执行器不需要实现这两个方法。GPU shader 节点、纯算术节点等**不要 override**——Runtime 不会调用任何资源。
2. **必须可重入**: 同一执行器实例可能在多个并发 Plan 中被调用(未来扩展)。`on_plan_started` 必须用 `run_id` 隔离资源(例如 `HashMap<RunId, Encoder>`)。
3. **不持有跨 Plan 的状态**: lifecycle context 只在调用期间有效;执行器持有的"长寿命资源"应该用 `RunId` 隔离,而不是全局共享。
4. **Continuous 模式下的语义**: `on_plan_started` 在进入 Continuous 时调用一次;`on_plan_finished` 在退出 Continuous 时调用一次。tick loop 中**不**反复调用。
5. **错误处理**: `on_plan_started` 返回 `Err` 时,Runtime 中止 Plan,不开始执行;`on_plan_finished` 不能返回错误(已经在终态)。

**典型场景:**

| 执行器 | `on_plan_started` 做什么 | `on_plan_finished` 做什么 |
|--------|-------------------------|--------------------------|
| `save_video` | 打开 output.mp4,创建 ffmpeg encoder | encoder.finalize();关闭文件 |
| `load_video` | (无,decoder pool 在 execute 内 lazy 创建) | (可选)释放该 plan 的 decoder |
| `gaussian_blur` | (default no-op) | (default no-op) |
| `sdxl_inference` | 把 SDXL 模型加载到 GPU(warm-up) | (default no-op,模型保留供下次 plan 用) |
| `temp_file_writer` | 创建临时目录 | 清理临时目录 |

### §2.4 核心运行规则

1. **single-flight**: 同一时刻最多一个活动执行。**由 Runtime(Layer 4)全局持有**,Session / CLI / Server 等调用方只能申请启动,不能直接变更状态。
2. 取消粒度:**run 级 + node 级**
3. 终态必须稳定落为:`Finished / Cancelled / Error` 之一
4. **交互路径优先**(真源 ⑧):当 `Preview` 与 `Full` 竞争资源时,`Preview` 优先。Runtime 的 `single-flight` 守卫允许 `Preview` 抢占正在运行的 `Full`。详见 `0.1.2-interaction-loop.md` §2.3。

## §3 语义签名与缓存键

### §3.1 ExecSignature

> 语义签名,回答"这是否是同一次语义计算"。

```rust
struct ExecSignature {
    hash: u128,
}
```

**构造公式(targetv2 完整版):**

```
ExecSignature.hash = xxHash3_128(
    upstream_signatures,       // Vec<ExecSignature>, 传递闭包
    params_hash,               // 本节点最终有效参数 hash(见 §3.1.1)
    node_def_type_id,          // NodeDef.type_id 的 hash
    node_def_version,          // NodeDef.version
    cooking_context_hash,      // 当前 CookingContext 的 hash(空 context 恒为 0)
    capability_version,        // 本节点使用的 Capability 版本(首版恒为 0)
    selected_artifact_id,      // Impure 节点的当前选用 artifact(Pure 节点恒为 0)
)
```

**`selected_artifact_id` 的语义:**

- **Pure 节点:** `selected_artifact_id` 恒为 `0`——Pure 节点的输出完全由输入决定,不涉及 artifact 选用
- **Impure 节点:** `selected_artifact_id` 是**当前用户选用的该节点历史产物的 ID**(来自 `ArtifactManager::get_selected_artifact(node_id)`),如果没选用则为 `0`
- **为什么 Impure 节点需要这个字段:**
  - Impure 节点(如 AI 生成)每次执行产出不同结果,每次执行产生一个新 `Artifact` 存入历史
  - 用户可以切换选用哪个历史产物作为 "当前输出"
  - 下游节点的输入 = 当前选用 artifact 的内容
  - 如果不把 `selected_artifact_id` 纳入 Impure 节点的 ExecSignature,**切换选用时签名不变**,下游节点查 cache 会命中错误条目

**Planner 如何获取 `selected_artifact_id`:**

Planner 通过 **NodeDefQuery** 或 **Scheduler facade** 传入的 `ArtifactSelectionQuery` trait 查询:

```rust
trait ArtifactSelectionQuery {
    fn current_selection(&self, node_id: NodeId) -> Option<ArtifactId>;
}
```

Planner 的 `plan(graph, ctx, dirty, node_defs, selections)` 签名多一个 `selections` 参数(targetv2 首版加)。Scheduler facade 持有 `ArtifactSelectionQuery` 的实现(由 ArtifactManager 提供),调用 Planner 时传入。

**Pure / Impure 的区分:**

```rust
let selected_artifact_id = match node_def.purity {
    Purity::Pure => 0u64,  // Pure 节点不受 selection 影响
    Purity::Impure => {
        selections.current_selection(node.id)
            .map(|id| id.as_u64())
            .unwrap_or(0)
    }
};
```

**向后兼容:** `selected_artifact_id` 为 0 时,签名与 "没有这个字段" 等价(所有现有 Pure 节点签名不变)。只有 Impure 节点在**有选用**时签名发生变化——这正是期望行为。

**关键约束:**

1. 基于**上游签名的传递闭包** + **本节点最终有效参数 hash** + **CookingContext hash** + **Capability version**
2. **不对 `Value` 本体做 hash**
3. **不含 `generation`**
4. `cooking_context_hash` 和 `capability_version` 首版可恒为 0,但**必须是公式的一部分** —— 见 §3.4 占位字段规则
5. 首版 hash 算法固定为 `xxHash3-128`

### §3.1.1 `params_hash` 构造规则

`params_hash` 是对"**本节点最终有效常量参数**"的 hash。**最终有效**意味着已应用以下规则:

1. **合并 ParamValueMode:** 对每个 `ParamDef`,优先使用 `Node.params` 里的 `ParamValueMode`;若缺失,使用 `ParamDef.default_mode`
2. **按 CookingContext 采样:** 如果是 `Animated(curve)` 模式,**先在当前 CookingContext 上采样**得到具体 Value;`Constant(v)` 直接用 v;`Expression` 首版报错
3. **跳过上游来源参数:** 如果某参数通过 `ParamExpose::Input` 暴露为输入接口,且 Graph 中该接口连接了上游——**不**包含在 `params_hash` 中,其实际值由 `upstream_signatures` 承担
4. **按 key 字典序排序:** 避免 HashMap 遍历顺序影响 hash

**参考实现:**

```rust
fn build_params_hash(
    node: &Node,
    node_def: &NodeDef,
    cooking_context: &CookingContext,
    graph: &Graph,
) -> u128 {
    // BTreeMap 天然按 key 排序,保证 hash 稳定
    let mut sampled: BTreeMap<String, Value> = BTreeMap::new();

    for param_def in &node_def.params {
        // 跳过连接到上游的参数输入接口
        if is_connected_as_input_pin(graph, node.id, &param_def.name) {
            continue;  // 实际值由 upstream_signatures 承担
        }

        // 取实例参数模式;缺失则用 NodeDef 默认
        let mode = node.params
            .get(&param_def.name)
            .unwrap_or(&param_def.default_mode);

        // **关键: 按当前 CookingContext 采样**
        // - Constant(v) → v
        // - Animated(curve) → 在 ctx 上采样曲线
        // - Expression(_) → 首版 panic
        let sampled_value = mode.sample(cooking_context);

        sampled.insert(param_def.name.clone(), sampled_value);
    }

    xxhash3_128(stable_serialize(&sampled))
}
```

**为什么必须先采样再 hash:**

如果不采样直接 hash `ParamValueMode` 本体:
- 同一条 `Animated(curve)` 在 frame=0 和 frame=100 会产出**相同的 hash**(因为 mode 本体是相同的 Curve 对象)
- 但**实际计算值不同** —— 0 帧用 keyframe 0 的值,100 帧用 keyframe 100 的值
- 两次执行返回不同结果,但签名相同 → 缓存命中错误结果 → 静默数据损坏

**采样后 hash 让"frame=0 与 frame=100 签名不同"成为自然结果**,完全不依赖 `cooking_context_hash` 的额外保护(后者是双重保险)。

**为什么跳过上游来源参数:**

参数接口(`ParamExpose::Input`)连接到上游时,参数的实际值是上游节点的输出——该输出的"身份"已经包含在上游的 `ExecSignature` 里。如果 `params_hash` 重复包含它:

- 当上游的 Value 身份变化时,上游 signature 变 → 当前 signature 变(正确)
- 但 `params_hash` 也需要"知道"上游值变化——这需要 Planner 实际求值上游,违反纯函数性

**跳过** 让 Planner 不需要求值上游即可构造 signature,保持纯函数性。

**静默踩坑警告:**

如果实现者 `hash(Node.params)` 直接:
- 参数顺序不确定 → 同参数产出不同 hash → 缓存命中率崩塌
- 不跳过参数接口 → 参数接口节点的签名错误
- **不采样动画参数** → 同 curve 在不同 context 下签名相同,缓存命中错误结果(静默数据损坏)
- 直接 hash `ParamValueMode::Animated(curve)` 本体 → 等同于不采样

这些错误**不会报编译错误**,只会表现为"缓存慢慢失效"或"动画参数无效果"。必须严格按本节规则实现。

### §3.2 CacheKey

> 缓存键,回答"某个输出在某个 generation 下的可复用缓存条目"。

```rust
struct CacheKey {
    node_id: NodeId,
    output_pin: String,
    exec_signature: ExecSignature,
    generation: GenerationId,
}
```

**设计约束:**

1. **语义签名与缓存键严格分离**
2. `generation` 只存在于 `CacheKey` 层,不参与 `ExecSignature`
3. 同一语义在不同 `generation` 下的 `ExecSignature` 必须相同

### §3.3 GenerationId

```rust
struct GenerationId(u64);
```

**推进规则:**

- **仅**以下操作触发 `generation + 1`:
  - `clear_cache`
  - `replace_graph`

其他操作(undo / redo、参数修改、节点增删、连线调整等)不触发 generation bump,而是通过签名变化自然失效。

### §3.4 占位字段规则(targetv2 强制)

`cooking_context_hash` 和 `capability_version` 是**占位字段**,首版可以恒为 0,但必须遵守:

| 规则 | 说明 |
|------|------|
| **必须在公式里** | 公式的字节布局从首版就锁定,未来换值时不改公式 |
| **首版恒零时签名行为与空字段一致** | 保证 target → targetv2 迁移时 **签名兼容** |
| **未来填入真实 hash 不是破坏性变更** | 旧节点不使用对应维度/版本 → hash 仍为 0 → 签名不变;新节点使用 → hash 非零 → 签名自然区分 |

**静默踩坑警告:** 如果首版不放这两个字段,未来加入时必须改公式 → 所有历史签名失效 → 缓存清零。这是 `architecture-invariants.md` §3 列出的最优先静默踩坑点之一。

### §5.2 CachePolicy

```rust

    Disabled,
    SuccessOnly,

```

**含义:**

- `SuccessOnly`: 缓存成功结果
- `SuccessAndHandle`: 缓存成功结果,也允许缓存 `Handle`

**默认推导说明:**

- 首版缓存行为由引擎默认推导,`NodeDef.execution.cache` 只做节点级可选覆盖
- 本文档当前冻结三档枚举值与"允许节点覆盖"这一能力,不冻结更细的默认推导矩阵
- **正式 cache 归 Runtime;preview cache 归 Session,二者不共享存储**(真源 ⑧ 结构义务,见 `0.1.2-interaction-loop.md` §2.2)

### §5.3 ArtifactPolicy

```rust
enum ArtifactPolicy {
    None,
    Persist,
}
```

**默认推导:**

- `purity = Pure` → `None`
- `purity = Impure` → `Persist`

**例外:**

- 导出型节点(如 `save_image`,具有文件 I/O 副作用)不靠 `purity` 判定产物登记
- 这类节点是否登记产物、是否进入项目内版本链路,由其导出语义与 `ArtifactManager` 规则共同决定

**Preview 模式下的 artifact 写入:**

- **禁止**: `fidelity == Preview` 时不得写入 artifact
- 即使节点声明 `ArtifactPolicy::Persist`,Preview 模式下也跳过
- 这是 `0.1.2-interaction-loop.md` 的结构义务

## §6 求值维度与集合值规则(targetv2 重写)

> target 时代的 §6 "列表执行规则" 在 targetv2 中被拆为两节:**求值维度**走 `CookingContext`;**集合值**走 `List<T>`。

### §6.1 求值维度(CookingContext)

**规则:**

1. 对同一张图的"多次求值"(序列帧、批处理、参数扫描、多种子对比等)由 `CookingContext` 承担
2. Planner 对 `CookingContextRange` 做笛卡尔积展开,对每个 context 生成一个独立的子 `ExecutionPlan`
3. 每次求值的 `ExecSignature` 不同(因为 `cooking_context_hash` 不同),独立缓存
4. 详细机制见 `0.1.3-cooking-context.md`

**首版状态:**

- 首版 `CookingContext.dimensions` 允许为空
- 空 context 退化为"单次求值",行为与 target 时代一致
- 但字段必须存在,公式必须包含 `cooking_context_hash`

### §6.2 集合值(List<T>)

**规则:**

1. `List<T>` 只用于承载"一次求值中的集合值"——例如 `List<BoundingBox>`、`List<Keypoint>`、`List<Color>`、`List<LayerRef>`
2. 图像节点**不再默认** map 执行 `List<Image>`——这是 target 时代的过渡行为
3. `List<Image>` 标为 **过渡白名单**,仅在 `CookingContext` 未覆盖场景时临时使用
4. 判据: **如果集合的典型语义是"对每个元素独立跑一遍整段下游",它就是 `CookingContext` 的一个维度,不是 `List<T>`**

### §6.3 从 CookingContext 收成 List<T>

当需要把 CookingContext 的多次求值结果收成一个 `List<T>` 值时,应通过 **显式 collect 节点**:

```
render_frame(CookingContext::frame 0..100)
    → collect_frames node
    → List<Image> value(作为一次性值送给下游)
```

**反方向(从 `List<T>` 解开为 N 次求值)原则上不支持。**

### §6.4 输入提升与降级(保留)

1. `Atomic(T)` 可自动提升为单元素 `List(T)`——仅限于真正的集合值语义
2. `List(T)` 不自动降级为 `Atomic(T)`

## §7 错误模型

### §7.1 ExecutorError —— 执行器边界

```rust
enum ExecutorError {
    /// 执行器内部服务不可用(如 GPU 失效、Python 进程崩溃)
    /// 注: 与 RuntimeError::CapabilityUnavailable(表示 Capability 无 provider)是不同概念
    ServiceDown { message: String },

    /// 输入数据非法(例如空图、维度不匹配)
    InvalidInput { message: String },

    /// 执行超时
    Timeout,

    /// 收到取消信号
    Cancelled,

    /// 执行内部失败(其他原因)
    RuntimeFailed { message: String },

    /// Value 物化失败(GPU 显存不足、格式不支持等)
    MaterializationFailed { target: MaterializationTarget, message: String },
}
```

### §7.2 错误层级映射表

引擎内部多个层持有自己的错误类型。从底层到对外的映射:

```
┌──────────────────────────────────────────────────────┐
│  EngineError (EngineFacade 对外)                      │
│    ↑                                                  │
│  SessionError (Session 层)                            │
│    ↑                                                  │
│  RuntimeError (Runtime 层)                            │
│    ↑                                                  │
│  ExecutorError (执行器边界) + CapabilityRegistryError │
│                PlannerError + GraphError              │
└──────────────────────────────────────────────────────┘
```

**具体映射:**

| 底层错误 | 上层(Runtime/Session)映射 | 对外(EngineError) |
|---------|--------------------------|-------------------|
| `ExecutorError::ServiceDown` | `RuntimeError::ExecutorFailed(inner)` | `EngineError::ExecutionError(msg)` |
| `ExecutorError::InvalidInput` | `RuntimeError::ExecutorFailed(inner)` | `EngineError::InvalidInput(msg)` |
| `ExecutorError::Timeout` | `RuntimeError::ExecutorFailed(inner)` | `EngineError::Timeout` |
| `ExecutorError::Cancelled` | `RuntimeError::Cancelled` | `EngineError::Cancelled` |
| `ExecutorError::MaterializationFailed` | `RuntimeError::MaterializationFailed(inner)` | `EngineError::ExecutionError(msg)` |
| `CapabilityRegistryError::NoProvider(cap)` | `RuntimeError::CapabilityUnavailable(cap)` | `EngineError::CapabilityUnavailable(cap)` |
| (Runtime 内部)single-flight 占用 | `RuntimeError::RunInFlight` | `EngineError::RunInFlight` |
| (Runtime 内部)被 Preview 抢占 | `RuntimeError::Preempted` | (不对外——对内部队列) |
| `PlannerError::UnknownNodeType` | `SessionError::PlannerError(inner)` | `EngineError::InvalidGraph(msg)` |
| `PlannerError::UnknownCapability` | `SessionError::PlannerError(inner)` | `EngineError::CapabilityUnavailable(cap)` |
| `GraphError::*`(变更失败) | `SessionError::GraphError(inner)` | `EngineError::InvalidGraph(msg)` |

**关键语义区分:**

- `ExecutorError::ServiceDown` = 执行器**内部**不可用(GPU 崩溃、后端进程死掉)
- `RuntimeError::CapabilityUnavailable` = 路由表里**找不到**该 Capability 的 provider

这两个错误**不能混淆**。前者是 "东西本来能用但临时坏了",后者是 "东西根本没注册"。

### §7.3 错误向前端暴露规则

- Runtime 发出 `RuntimeError` 或 `ExecutorError`
- Scheduler facade 或 EngineFacade 把这些转译为 `EngineError`
- GUI 路径: 经 Session,SessionError 吸收 RuntimeError 后转译
- CLI 路径: 直接从 EngineFacade 拿 EngineError

**说明:**

- `ExecutorError` 是执行器边界上的**稳定错误类型**——执行器作者只需要知道这 6 个变体
- 向前端暴露时由运行时层层转译,内部细节不泄漏
