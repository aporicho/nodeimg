# GUI Layering

> GUI 从业务状态到 GPU 绘制不是一层完成的。本文定义应用 UI 的完整分层、单向依赖、接口边界和节点卡片所在位置。`控件原子 / 控件框架 / 业务组合` 只是组件构建层内部的子分层，不是完整 GUI 架构。

## 目标

- 明确 UI 绘制链路里每一层负责什么。
- 防止业务概念下沉到 `tree`、`widget`、`renderer`。
- 防止通用控件反向依赖 `workspace`、`engine`、`canvas node`。
- 给节点卡片、参数控件、端口、连接线建立可持续的模块边界。
- 让后续性能优化走 stable id、diff、layout invalidation、spec cache，而不是硬编码专用临时代码。

## 主链路

```text
业务状态层
  -> 应用视图模型层
    -> 业务 UI 组合层
      -> 通用组件层
        -> 描述树层
          -> 实例树层
            -> 布局层
              -> 绘制计划层
                -> Renderer 层
                  -> Shell / GPU
```

事件链路反向进入：

```text
Shell 输入
  -> Event / hit test
  -> Gesture / widget systems
  -> GuiAction
  -> App controller / reducer
  -> 业务状态变化
  -> 重新构建 UI 描述
```

## 1. 业务状态层

业务状态层保存应用真实语义和用户作品状态。

当前代表：

- Engine Graph。
- Session / scheduler / preview / execution 状态。
- Workspace project layout。
- Panel layout。
- Canvas selection、camera、drag session 等可归属到业务交互的状态。

典型文件：

- `app/src/workspace/controller.rs`
- `app/src/workspace/project_layout.rs`
- `app/src/workspace/canvas_drag.rs`
- `engine/*`

职责：

- 回答“当前业务是什么状态”。
- 处理业务动作如何改变状态。
- 维护 undo、project persistence、engine command。

禁止：

- 返回 `Desc`。
- 构造 `WidgetDesc`。
- 直接写 `BoxStyle`、颜色、圆角、边框、文本布局。
- 依赖 `gui::widget`、`gui::tree`、`gui::renderer`。

## 2. 应用视图模型层

应用视图模型层把业务状态转换成 GUI 可消费的纯数据。

当前代表：

- `CanvasNodeTemplate`
- `CanvasNodeInstanceState`
- `CanvasNodeRenderView`
- `CanvasConnectionView`
- `ParamView`
- `NodePaletteItemView`
- `PanelView`

典型文件：

- `app/src/workspace/engine_adapter.rs`
- `app/src/workspace/view.rs`
- `app/src/workspace/showcase_node.rs`

职责：

- 从 engine node def、params、ports、connections 派生 UI view model。
- 把 engine id 转成稳定 UI id 所需的数据。
- 提供业务 UI 组合层需要的所有纯数据。

接口形态：

```rust
pub struct CanvasNodeTemplate {
    pub type_id: String,
    pub title: String,
    pub category: String,
    pub params: Vec<CanvasNodeParamTemplate>,
    pub inputs: Vec<CanvasNodePortTemplate>,
    pub outputs: Vec<CanvasNodePortTemplate>,
}

pub struct CanvasNodeInstanceState {
    pub owner_id: String,
    pub layout: CanvasNodeLayout,
    pub selected: bool,
    pub port_states: Vec<CanvasNodePortState>,
}
```

禁止：

- 输出 `Desc`。
- 保存 widget runtime。
- 直接决定某个控件如何绘制。

说明：

- 这一层可以缓存 `CanvasNodeTemplate` 这类类型级静态结构。
- `NodeRenderSpec` 属于 `gui::canvas` 内部渲染预计算,仍然应该是纯数据,不是 `Desc` 缓存。
- 性能优化应优先发生在 view model diff、spec cache、stable id 这几个位置。

## 3. 业务 UI 组合层

业务 UI 组合层把 view model 组织成 GUI 描述树。

当前代表：

- 节点卡片。
- 节点端口区。
- 参数区。
- 节点 palette。
- workspace 主界面。
- engine panel 内容。
- preview panel 内容。
- toolbar 内容。

典型文件：

- `gui/src/canvas/node_card.rs`
- `gui/src/canvas/param_control.rs`
- `app/src/workspace/node_palette.rs`
- `app/src/panels/*.rs`
- `app/src/demo_gallery.rs`

职责：

- 消费 `CanvasNodeRenderView`、`ParamView`、`PanelView` 等业务视图模型。
- 组合通用 widget、container、leaf。
- 给业务节点、端口、参数生成稳定 id。
- 绑定业务 action id 和 gesture 语义。

接口形态：

```rust
pub fn node_card_from_render_view(view: &CanvasNodeRenderView, theme: &Theme) -> Desc;
pub fn build_param_control(view: &ParamView) -> Desc;
pub fn build_node_palette(items: &[NodePaletteItemView]) -> Desc;
```

禁止：

- 自己实现通用 `Slider`、`TextInput`、`Dropdown` 的内部绘制。
- 把 `ParamRow`、`PortRow` 伪装成通用 widget，除非先证明它们脱离节点业务仍然成立。
- 让通用 widget 反向读取 engine 或 workspace。

节点卡片定位：

- 节点卡片属于业务 UI 组合层。
- 它不是控件原子。
- 它不是通用控件框架。
- 它应该消费 `CanvasNodeRenderView`,内部生成 `NodeRenderSpec`,输出 `Desc`。
- 它内部使用 `Surface`、`Label`、`Dot`、`Slider`、`TextInput`、`Dropdown`、`ScrollArea`、通用 Row/Column/Grid/Layer 能力。

## 4. 通用组件层

通用组件层提供可复用 UI 构件。它不知道业务。

当前目录：

- `gui/src/widget/`

内部子层：

```text
widget::atoms       最小输入/显示单元
widget::frameworks 结构/行为容器
widget::systems    控件运行时系统
widget::painters   控件绘制辅助
```

控件原子：

- `Button`
- `Label`
- `TextInput`
- `NumberInput`
- `Slider`
- `Checkbox`
- `Toggle`
- `Radio`
- `Dropdown`
- `ColorSwatch`
- `Dot`
- `Separator`
- `ImageViewer`
- `TruncatedText`
- `PathInput`

控件框架：

- `Panel`
- `Group`
- `Collapsible`
- `ScrollArea`
- `ListView`
- `Surface`
- 未来的 `Popover`、`Menu`、`Tabs`、`Toolbar`、`Stack`、`Grid`

控件系统：

- Dropdown open/select。
- Text input editing。
- Focus。
- Preedit / selection。
- Scroll offset。

核心接口：

```rust
pub trait WidgetProps {
    fn widget_type(&self) -> &'static str;
    fn build(&self, id: &str, cx: &WidgetBuildCx<'_>) -> WidgetBuild;
    fn props_eq(&self, other: &dyn WidgetProps) -> bool;
    fn clone_box(&self) -> Box<dyn WidgetProps>;
}

pub struct WidgetDesc {
    id: Cow<'static, str>,
    props: Box<dyn WidgetProps>,
    children: Vec<Desc>,
}
```

禁止：

- 引用 engine 类型。
- 引用 app workspace 类型。
- 知道某个参数属于哪个节点。
- 知道 canvas node、port、connection 的业务含义。

## 5. 描述树层

描述树层是 UI 的声明式中间表示，类似简化 DOM / element tree。

当前目录：

- `gui/src/tree/desc.rs`
- `gui/src/widget/desc.rs`
- `gui/src/tree/layout/types.rs`

核心类型：

```rust
pub enum Desc {
    Container { ... },
    Leaf { ... },
    Widget(WidgetDesc),
}
```

职责：

- 表达这一帧 UI 应该长什么样。
- 承载 container、leaf、widget 的声明。
- 承载布局样式、视觉装饰、gesture 声明。
- 提供正式 UI 构建门面，隔离业务层和裸 `Desc` / `BoxStyle` 构造。

正式构建 API：

```text
gui::ui             // 业务层和 widget 子树优先使用的 Desc 构建门面
gui::widget::build  // WidgetProps::build 内部使用的 WidgetBuild 根构建门面
gui::tree::build    // 内部实现归属，负责构造 Desc / builder trait
```

`gui::ui` 只表达通用 UI 结构：

- `row` / `column` / `container`
- `leaf` / `text` / `text_with_layout`
- `widget`
- CSS/Flex 风格 layout 方法
- 通用 decoration 方法
- 通用 interaction 方法

`gui::ui` 不表达业务语义：

- 不提供 `node_card`。
- 不提供 `param_row`。
- 不提供 `port_row`。
- 不提供 `engine_param`。
- 不提供主题语义如 `primary_button` 或 `node_surface`。

构建规则：

- 业务 UI 组合层和通用组件层优先通过 `gui::ui` 构造描述树。
- `WidgetProps::build` 的根 `WidgetBuild` 通过 `gui::widget::build::{root,row,column}` 构造。
- `Desc::Container`、`Desc::Leaf`、`WidgetDesc::new`、裸 `BoxStyle` 字面量只应保留在 `tree` / `widget` 底层实现测试或确实需要验证内部结构的断言里。
- 通用 widget 内部使用 `gui::widget::build` 组合根节点，使用 `gui::ui` 组合 container、leaf 和子 widget，避免每个控件重复手写样式字段。
- 业务层需要特殊结构时，先用 `ui::row`、`ui::column`、`ui::container`、`ui::text`、`ui::widget` 表达；只有当缺少通用能力时，才补 `tree::build` / layout / paint 的基础 API。

禁止：

- 新增 `ParamRow`、`PortRow`、`NodeHeader`、`EngineNode` 这类业务枚举。
- 保存 runtime。
- 做布局计算。
- 直接调用 renderer。

## 6. 实例树层

实例树层把临时描述树 reconcile 成有稳定身份和 runtime 的 GUI Tree。

当前目录：

- `gui/src/tree/tree.rs`
- `gui/src/tree/node.rs`
- `gui/src/tree/diff.rs`
- `gui/src/tree/runtime_slots.rs`
- `gui/src/tree/runtime_policy.rs`

职责：

- `Desc -> Tree`。
- 保持 stable id 对应的 `NodeId`。
- 通过 `props_eq` 减少重建。
- 挂载 runtime slots。
- 管理节点生命周期和 runtime retention。

性能边界：

- 动态构建 `Desc` 本身不是主要性能风险。
- 真正关键的是 stable id、props diff、layout dirty、text measure cache、paint command cache。
- 节点外观预计算应落在 view model / render spec 层，而不是绕过实例树。

## 7. 布局层

布局层计算所有节点的最终几何信息。

当前目录：

- `gui/src/tree/layout/`
- `gui/src/tree/text_layout.rs`
- `gui/src/tree/scroll.rs`

职责：

- 实现 CSS/Flex 对齐的 box model。
- 处理 flow、absolute、relative。
- 处理 flex grow/shrink、min/max size。
- 处理 padding、margin、border、gap。
- 处理 overflow、scroll、transform。
- 处理 text layout 和测量。

禁止：

- 判断这是 Button 还是 NodeCard。
- 根据业务类型做特殊布局。
- 读取 engine 或 widget runtime 的业务字段。

原则：

- Widget 只声明布局意图。
- Layout engine 统一计算最终 rect。
- 节点卡片需要的布局能力必须沉淀为通用 CSS/Flex 能力。

## 8. 绘制计划层

绘制计划层把布局后的 Tree 转成 renderer 可消费的绘制操作。

当前目录：

- `gui/src/tree/paint.rs`
- `gui/src/tree/paint_helpers.rs`
- `gui/src/tree/stacking.rs`
- `gui/src/tree/hit.rs`

职责：

- 按 stacking model 决定绘制顺序。
- 处理 z-index 和 source order。
- 处理 clip、overflow、transform。
- 生成 text、image、circle、curve、quad、shadow 等绘制命令。
- 让 hit test 和 paint order 使用一致的顺序模型。

禁止：

- 读取业务状态。
- 根据 `NodeCard`、`ParamView`、`EngineNode` 做分支。
- 在绘制层修业务布局问题。

## 9. Renderer 层

Renderer 层和 GPU 管线打交道。

当前目录：

- `gui/src/renderer/`

职责：

- 管理 `RenderCommand`。
- 准备 GPU buffer。
- 调用 wgpu pipeline。
- 绘制 quad、circle、curve、text、image、shadow、stencil。

禁止：

- 知道 `Widget`。
- 知道 `NodeCard`。
- 知道 `Panel`。
- 知道 `Workspace`。

## 10. Shell / Runtime 层

Shell / Runtime 层承接平台窗口、输入、GPU surface 和帧循环。

当前目录：

- `gui/src/shell/`
- `gui/src/runtime/`
- `gui/src/context.rs`

职责：

- 窗口和 surface。
- 平台事件翻译。
- Cursor、clipboard、IME、file dialog 等平台效果。
- Frame scheduling。
- Runtime resources。

禁止：

- 写业务 UI。
- 写节点布局规则。
- 知道 engine graph 语义。

## 依赖方向

允许：

```text
app::workspace
  -> app view model
  -> gui::canvas / app::panels business composition
  -> gui::widget
  -> gui::tree
  -> gui::renderer
  -> gui::shell
```

禁止：

```text
gui::widget -> app::workspace
gui::tree -> gui::widget::atoms
gui::renderer -> gui::tree business meaning
engine -> gui
gui::canvas::node_card -> engine mutable controller
```

## Canvas 的拆分方向

当前 `gui/src/canvas/` 同时包含通用画布能力和节点编辑器业务组合。短期可以保持目录不动，但接口上要区分：

Canvas foundation：

- camera。
- pan / navigation。
- canvas coordinate transform。
- background。
- generic connection primitive。

Node editor specialization：

- node card。
- port。
- param control。
- node palette trigger。
- connection semantic mapping。

长期文件结构可以演进为：

```text
gui/src/canvas_core/
gui/src/node_editor/
```

或者保留 `gui/src/canvas/`，但内部按 `core/` 与 `node_editor/` 分区。

## 通用能力与业务组合的判定

可以进入通用层：

- 脱离 nodeimg 业务仍然成立。
- 不依赖 engine、workspace、node、param、port。
- 只表达布局、输入、显示、滚动、浮层、分组、文本编辑等通用 UI 能力。

必须留在业务组合层：

- 知道 engine node。
- 知道 param expose。
- 知道 input/output port。
- 知道 canvas connection 的业务语义。
- 知道 workspace controller action。

判断例子：

| 名称 | 层级 | 原因 |
| --- | --- | --- |
| `Slider` | 通用组件层 / atom | 任意应用都可复用。 |
| `ScrollArea` | 通用组件层 / framework | 只提供滚动结构。 |
| `Surface` | 通用组件层 / framework | 只提供通用视觉外壳。 |
| `ParamControl` | 业务 UI 组合层 | 根据 `ParamView` 选择控件。 |
| `PortRow` | 业务 UI 组合层 | 知道节点端口方向和连接语义。 |
| `NodeCard` | 业务 UI 组合层 | 知道节点标题、参数、端口、连接状态。 |
| `Connection curve` | 绘制图元或 canvas primitive | 只画曲线时通用；端口连接语义在业务层。 |

## 节点外观的预计算

节点外观可以提前计算，但提前计算的对象应该是 spec，不是绕过 UI 层的硬编码绘制。

推荐：

```rust
pub struct NodeRenderSpec {
    pub header: NodeHeaderSpec,
    pub inputs: Vec<NodePortSpec>,
    pub outputs: Vec<NodePortSpec>,
    pub controls: Vec<ParamControlSpec>,
    pub layout: NodeCardLayoutSpec,
}
```

数据流：

```text
Engine NodeDef
  -> CanvasNodeTemplate          // 类型级静态结构,按 type_id + version 缓存
Graph/layout/interaction state
  -> CanvasNodeInstanceState     // 实例级动态状态
CanvasNodeTemplate + CanvasNodeInstanceState + Theme
  -> NodeRenderSpec              // 渲染预计算,不直接缓存 Desc
  -> node_card_from_render_view
  -> Desc
  -> Tree
  -> Layout
  -> Paint
```

说明：

- `CanvasNodeTemplate` 是节点类型级外观结构,由 `app::workspace` 从 `NodeDef` 映射而来,`gui` 不依赖 engine。
- `CanvasNodeInstanceState` 是节点实例状态,只包含 owner/layout/selection/port connection state 等运行时信息。
- `NodeRenderSpec` 是 `gui::canvas` 内部渲染预计算,仍然是纯数据,不是 `Desc` 缓存。
- 节点定义版本不变时复用 `CanvasNodeTemplate`;实例状态变化只重建 state/spec。
- 禁止恢复旧的混合节点视图模型:静态结构、实例状态和渲染 spec 必须保持分层。

## 落地顺序

1. 固化本文档，并在后续评审中用它判断模块边界。
2. 补通用 `tree` / `ui` builder，让业务组合少直接手写裸 `BoxStyle`。
3. 梳理 `gui::canvas`，先在接口上区分 canvas foundation 和 node editor specialization。
4. 引入 `CanvasNodeTemplate` / `CanvasNodeInstanceState` / `NodeRenderSpec`,把节点外观结构和实例状态拆开。
5. 让 `node_card_from_render_view` 只消费 render view/spec,并只组合通用 widget、container、leaf。
6. 对 node card 建立结构测试：标题、端口、参数、连接锚点、绘制层级。

## 评审规则

新增 UI 能力时先回答：

- 这是业务状态、视图模型、业务组合，还是通用组件？
- 它是否知道 engine/workspace/node/param/port？
- 它输出的是纯数据、`Desc`、`Tree`、layout rect，还是 render command？
- 它的 runtime 状态归属在哪个 TreeNode？
- 它是否破坏单向依赖？

如果一个新类型跨了两层，优先拆成：

- 上层 spec / view model。
- 下层通用 widget / tree primitive。
