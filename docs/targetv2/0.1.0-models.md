## §1 类型系统

### §1.1 AtomicType

> 封闭枚举。新增、删除或修改原子类型均为**破坏性变更**,须先改 `architecture-invariants.md` 真源 ③。

```rust
enum AtomicType {
    // 媒体(首版扩充,含占位类型)
    Image,
    Mask,
    Video,
    Audio,
    VectorGraphic,
    LayoutDocument,

    // 标量
    Float,
    Int,
    Bool,
    Color,
    String,

    // 结构化 / 交换
    Json,
    Bytes,
    Path,

    // 运行时引用
    Handle,
    RemoteRef,

    // 集合值(非调度维度)
    BoundingBox,
    Keypoint,
}
```

**首版扩充原则(targetv2):**

- 首版 `AtomicType` 清单扩充到 18 种,包含 `Video` / `Audio` / `VectorGraphic` / `LayoutDocument` / `BoundingBox` / `Keypoint` / `RemoteRef` 等**占位类型**
- 占位类型可以没有任何执行器支持,但**类型系统中必须存在**
- 原因见 `architecture-invariants.md` §2 真源 ③: 未来加类型是破坏性变更,上线前先占位避免后悔

| 原子类型 | 分类 | Rust 类型 | 首版状态 | 首版 `List<T>` |
|---------|------|----------|---------|---------------|
| `Image` | 媒体 | `ImageValue` | 首版支持 | **过渡白名单** |
| `Mask` | 媒体 | `MaskValue` | 首版支持 | 预留 |
| `Video` | 媒体 | `VideoValue` | **[占位]** | 不开放 |
| `Audio` | 媒体 | `AudioValue` | **[占位]** | 不开放 |
| `VectorGraphic` | 媒体 | `VectorValue` | **[占位]** | 不开放 |
| `LayoutDocument` | 媒体 | `LayoutValue` | **[占位]** | 不开放 |
| `Float` | 标量 | `f32` | 首版支持 | 预留 |
| `Int` | 标量 | `i64` | 首版支持 | 预留 |
| `Bool` | 标量 | `bool` | 首版支持 | 不开放 |
| `Color` | 标量 | `[f32; 4]` | 首版支持 | 不开放 |
| `String` | 标量 | `String` | 首版支持 | 预留 |
| `Json` | 结构化 | `serde_json::Value` | 首版支持 | **开放** |
| `Bytes` | 交换格式 | `Vec<u8>` | 首版支持 | 不开放 |
| `Path` | 资源引用 | `PathBuf` | 首版支持 | 预留 |
| `Handle` | 远端引用 | `Handle` | 首版支持 | 不开放 |
| `RemoteRef` | 远端引用 | `RemoteRef` | **[占位]** | 不开放 |
| `BoundingBox` | 集合元素 | `BBox` | **[占位]** | **开放** |
| `Keypoint` | 集合元素 | `KPt` | **[占位]** | **开放** |

**首版 `List<T>` 列含义:**

- **开放** = 首版允许 `List(T)`
- **过渡白名单** = 首版允许 `List(T)` 但标注为过渡状态,长期应迁移到 `CookingContext`
- **预留** = 类型系统层面可支持,首版禁止
- **不开放** = 不允许进入 `List<T>`

**`List<Image>` 的特殊说明:**

`List<Image>` 标为 **过渡白名单**——首版允许,但仅在 `CookingContext` 未覆盖场景时临时使用。详见 `0.1.3-cooking-context.md` §4。

---

**类型补充说明:**

- `Image`: 通过 `Materializable` 协议按需物化到 `Local` 或 `GpuResident`。**`ImageValue` 是多通道 + 元数据的容器**,不是固定的 RGBA 图像——这是 targetv2 与 target 的**关键差异**。详见 §1.3.1 和 `0.1.5-value-materialization.md`。
- `Mask`: 语义独立于 `Image`,不是 `Image` 的子类型。
- `Video` / `Audio` / `VectorGraphic` / `LayoutDocument`: 运行时表示未定;首版作为占位,无执行器支持。**占位实现约定**:首版 `VideoValue` / `AudioValue` / `VectorValue` / `LayoutValue` 应实现为**不可构造的 marker struct**(例如 `pub struct VideoValue { _unimplemented: PhantomData<()> }`,无 public constructor),保证类型系统中存在但运行时无法创建实例。转正时移除 marker 并添加真实字段,**不**视为破坏性变更——因为 `Value::Video(_)` 的位置已经在。
- `Handle`: Python VRAM 引用凭证(见 §1.4)。
- `RemoteRef`: 通用远程资源引用;`Handle` 可以视为 `RemoteRef` 的一个特化子类型,但首版两者并列。
- `BoundingBox` / `Keypoint`: 占位类型,典型用法是 `List<BoundingBox>`、`List<Keypoint>`(检测器输出)。

**`Path` / `Bytes` / `Json` 主语义:**

| 类型 | 主语义 | 说明 |
|------|--------|------|
| `Path` | 资源引用 | 指向文件系统路径,不是媒体内容本体 |
| `Bytes` | 底层交换格式 | 用于导入导出、编码结果、网络载荷等 |
| `Json` | 正式可连线数据 | 可作为节点输入/输出在图中流动,不仅仅是配置 |

### §1.2 DataType

> 两层结构:原子类型 + 类型构造器。

```rust
enum DataType {
    Atomic(AtomicType),
    List(AtomicType),
}
```

**约束:**

1. **禁止嵌套**——`List` 的参数只能是 `AtomicType`,不能是 `DataType`,因此 `List<List<T>>` 不存在
2. **首版白名单**:仅允许 `List(Image)`(过渡)、`List(Json)`、`List(BoundingBox)`、`List(Keypoint)`
3. **类型匹配**:连接校验要求 `DataType` 完全相等;`Atomic(Image)` 与 `List(Image)` 不兼容
4. **扩展路径**:新增原子类型自动获得 `Atomic(T)`;是否开放 `List(T)` 由 §1.1 能力声明 + 白名单共同决定

**`List<T>` 与 `CookingContext` 的边界(targetv2 强制):**

> **如果集合的典型语义是"对每个元素独立跑一遍整段下游",它不应该是 `List<T>`,它是 `CookingContext` 的一个维度。**
>
> **如果集合的典型语义是"整体作为一个值被下游消费",它才是 `List<T>`。**

详见 `0.1.3-cooking-context.md` §4.

### §1.3 Value

> 运行时值。变体与 `AtomicType` 一一对应,另加 `List` 容器变体。

```rust
enum Value {
    // 媒体变体
    Image(ImageValue),
    Mask(MaskValue),
    Video(VideoValue),      // [占位]
    Audio(AudioValue),      // [占位]
    VectorGraphic(VectorValue),    // [占位]
    LayoutDocument(LayoutValue),   // [占位]

    // 标量变体
    Float(f32),
    Int(i64),
    Bool(bool),
    Color([f32; 4]),
    String(String),

    // 结构化 / 交换
    Json(serde_json::Value),
    Bytes(Vec<u8>),
    Path(PathBuf),

    // 运行时引用
    Handle(Handle),
    RemoteRef(RemoteRef),   // [占位]

    // 集合元素
    BoundingBox(BBox),      // [占位]
    Keypoint(KPt),          // [占位]

    // 容器变体
    List { element_type: AtomicType, items: Vec<Value> },
}
```

**约束:**

1. **无全局 Hash / Eq**——`Value` 不实现 `Hash` 或 `Eq`。含 GPU 资源或大数据的变体无法安全 hash。`HashMap<Value, _>` 不存在。计算身份由 `ExecSignature`(见 `0.1.1-execution-models.md`)承担。
2. **Opaque handle**——媒体 `Value`(`Image` / `Mask` / `Video` / `Audio` / `VectorGraphic` / `LayoutDocument`)通过 `Materializable` 协议按需物化。节点 schema 不得引用 `MaterializationTarget`。详见 `0.1.5-value-materialization.md`。
3. **List 约束**:`List.items` 中每个元素须匹配 `element_type` 对应的原子变体(运行时校验);`List.element_type` 须在首版白名单中(见 §1.2 约束 2)。

> *设计备忘:* 大对象(Image/Video/Audio)内部用 `Arc` 共享避免拷贝,API 层统一表现为 `Value`。标量值可在业务逻辑中直接比较,但这不等于 `Value` 拥有统一的全局 `Hash/Eq`。

### §1.3.1 ImageValue —— 多通道 + 元数据

**核心设计(targetv2 新增):** `ImageValue` 不是固定 RGBA 图像,而是 **通道映射 + 元数据 + 物化协议** 的组合。这让它能承载:

- 传统 RGBA 图像(首版正常使用)
- 多通道 EXR(Nuke / 专业 VFX)—— 通道包括 `R/G/B/A/Z/N.X/N.Y/N.Z/MV.X/MV.Y/AOV.*`
- 色彩空间感知图像(DaVinci ACES 工作流)
- 带时间戳的视频帧(未来)
- 元数据驱动的合成操作(深度合成、ID 遮罩)

**类型定义:**

```rust
struct ImageValue {
    inner: Arc<ImageValueInner>,
}

struct ImageValueInner {
    /// 宽高(所有通道必须一致)
    width: u32,
    height: u32,

    /// 通道映射: 通道 id → 通道数据
    /// 通道 id 是**开放字符串**(不是封闭枚举)——加新通道是"填槽",不破坏核心
    /// 首版常用: "R", "G", "B", "A"
    /// 未来: "Z"(深度), "N.X/Y/Z"(法线), "MV.X/Y"(运动向量), "AOV.*"(任意 AOV)
    channels: BTreeMap<ChannelId, ChannelData>,

    /// 元数据(色彩空间、时间戳、帧号等)
    metadata: ImageMetadata,

    /// 运行时物化表示(不在 schema 里)
    /// 首版实现: CPU (DynamicImage) + GPU (wgpu::Texture) 双缓存 + OnceLock
    /// 这是实现细节,不是规范——未来可改
    cpu: OnceLock<DynamicImage>,
    gpu: OnceLock<wgpu::Texture>,
}

type ChannelId = String;

enum ChannelData {
    Float32(Arc<Vec<f32>>),     // HDR / 线性光照 / AOV
    Float16(Arc<Vec<f16>>),     // [占位] 半精度(OpenEXR 标准)
    Uint8(Arc<Vec<u8>>),        // 8bit LDR
    Uint16(Arc<Vec<u16>>),      // 16bit HDR
}
```

**首版 ChannelId 清单:**

| ChannelId | 用途 | 首版状态 |
|-----------|------|---------|
| `"R"` | 红通道 | **[首版支持]** |
| `"G"` | 绿通道 | **[首版支持]** |
| `"B"` | 蓝通道 | **[首版支持]** |
| `"A"` | alpha 通道 | **[首版支持]** |
| `"Z"` | 深度(线性距离或 1/w) | **[占位]** —— 类型系统中存在,首版无节点使用(EXR 多通道延后) |
| `"N.X"` / `"N.Y"` / `"N.Z"` | 法线分量 | **[占位]** |
| `"MV.X"` / `"MV.Y"` | 运动向量分量 | **[占位]** |
| `"ObjectID"` | 对象 ID 通道 | **[占位]** —— 同上 |
| `"AOV.<name>"` | 任意 AOV(开放字符串) | **[演进项]** |

**首版只用 `R/G/B/A` 四个通道。** 多通道机制保留是为了:
- 视频帧本质上也是多通道(虽然首版只暴露 RGBA)
- 未来加 EXR 多通道 / 深度合成时不需要破坏性变更
- `ChannelId` 是开放字符串,加新通道是"填槽"

**关键约束:**

1. **所有通道 width × height 必须一致** —— 跨分辨率通道不支持
2. **通道集合不是固定的** —— 不同 `ImageValue` 实例可以有不同通道集合(一张只有 RGBA,一张有 RGBA + Z)
3. **连线类型兼容性只检查 `AtomicType::Image`** —— 不检查通道集合。节点在执行时按需读取需要的通道,缺失通道由执行器决定处理(报错 / 置零 / 默认值)
4. **`Materializable::materialize` 物化整个 `ImageValue`,不按通道独立物化** —— 物化粒度 = 整个 ImageValue

### §1.3.2 ImageMetadata —— 色彩空间 + 时间戳 + 扩展

```rust
struct ImageMetadata {
    /// 色彩空间(首版明文支持 SRgb / LinearRec709;其他为占位)
    color_space: ColorSpace,

    /// 时间戳(视频帧 / 序列帧的时间位置)
    /// [占位] 首版 None
    timecode: Option<Timecode>,

    /// 帧号(来自序列帧 / 视频源)
    /// [占位] 首版 None
    frame_number: Option<u64>,

    /// 源提示(例如 "camera_01.mp4" / "render_pass_beauty")
    /// [占位] 首版 None
    source_hint: Option<String>,

    /// 自定义元数据(开放 KV)
    /// [演进项] 首版为空
    custom: HashMap<String, Value>,
}

enum ColorSpace {
    /// sRGB 非线性(大多数 JPG / PNG / 网络图像)
    SRgb,
    /// 线性 Rec.709(专业渲染输出 / 线性合成空间)
    LinearRec709,
    /// [占位] 线性 Rec.2020 / HDR 合成
    LinearRec2020,
    /// [占位] ACES 工作流
    ACEScg,
    /// [占位] 未知 / 自定义
    Raw,
    /// [演进项] OCIO 定义的任意色彩空间
    Custom(String),
}

struct Timecode {
    /// 帧率分子 / 分母
    fps_num: u32,
    fps_den: u32,
    /// 时间戳(自源起点的帧数)
    frame_offset: u64,
    /// 是否 drop frame(NTSC 29.97 等)
    drop_frame: bool,
}
```

**首版只启用:**

- `color_space: ColorSpace::SRgb` 或 `ColorSpace::LinearRec709`
- 其他字段都是 `None` / 空

**为什么首版必须有这个结构:**

如果首版 `ImageValue` 只有 `DynamicImage`(隐含 SRgb RGBA),未来想加入 OCIO / HDR / 多通道需要**改 ImageValue 本体** → 影响所有执行器 → 影响签名。**现在把机制放进去,首版填 RGBA + SRgb,未来填更多通道 + 更多色彩空间。**

### §1.4 Handle

> Python VRAM 引用凭证,不含实际数据。

```rust
Handle { id: u64, kind: String }
```

- `kind`: 远端资源语义(`"model"` / `"clip"` / `"vae"` / `"conditioning"` / `"latent"` 等),由 Python 端定义,**开放字符串**。
- 连接校验:`kind` 匹配是 Handle 引脚连接的必要类型条件。

### §1.5 Constraint

> 参数的合法性约束,附加在 `ParamDef` 上。**开放类型**,通过 `ConstraintRegistry` 注册扩展。

```rust
Constraint { type_id: String, params: JsonValue }
```

| type_id | params | 说明 |
|---------|--------|------|
| `range` | `{ min, max }` | 数值范围 |
| `step` | `{ value }` | 数值步长 |
| `enum` | `{ options: [...] }` | 枚举选项 |
| `must_exist` | `{}` | 路径或资源必须存在 |
| `multiline` | `{}` | 多行文本输入 |
| `placeholder` | `{ text }` | 轻量输入提示文本 |
| `secret` | `{}` | 敏感输入,不应明文回显 |
| `file_path` | `{ extensions: [...], mode?: "open" | "save" }` | 文件路径输入与扩展名过滤 |
| `advanced` | `{}` | 高级参数提示 |
| `read_only` | `{}` | 只读参数提示 |

新增约束类型通过注册表扩展,无需修改核心代码。

**边界:**

- `Constraint` 允许表达**数据合法性规则**与**跨前端稳定的轻量控件提示**
- `Constraint` 不表达参数显示位置、节点布局、控件尺寸、折叠状态等 GUI 私有渲染细节
- 参数显示位置由 `PresentationProvider` 负责

> *设计备忘:* `Constraint` 开放与 `AtomicType` 封闭不矛盾——前者是参数校验规则(需求无界),后者是引脚间数据种类(需求有界)。

## §2 节点定义层

### §2.1 NodeSourceKind

```rust
enum NodeSourceKind {
    Builtin,
    Python,
    Api,
}
```

- `Builtin`: Rust 内置节点来源
- `Python`: Python 节点来源
- `Api`: API Provider 来源

### §2.2 Purity

```rust
enum Purity {
    Pure,
    Impure,
}
```

**约束:**

1. `Purity` 独立于 `executor_type`
2. 值域固定为二元,不允许静默扩展
3. `purity` 判定源 = `NodeDef` 必填字段,由节点作者显式声明

### §2.3 InputPinDef / OutputPinDef

```rust
struct InputPinDef {
    name: String,
    data_type: DataType,
    required: bool,
}

struct OutputPinDef {
    name: String,
    data_type: DataType,
}
```

**约束:**

- `required` 只存在于输入口
- `InputPinDef` / `OutputPinDef` 分离,避免把无意义字段塞进统一 `PinDef`

### §2.4 ParamExpose

```rust
enum ParamExpose {
    Control,
    Input,
    Output,
}
```

- `Control`: 参数渲染为控件
- `Input`: 参数暴露为参数输入接口
- `Output`: 参数暴露为参数输出接口

### §2.5 ParamDef

```rust
struct ParamDef {
    name: String,
    data_type: DataType,
    default_mode: ParamValueMode,  // targetv2: 从 default: Value 改为 ParamValueMode
    expose: Vec<ParamExpose>,
    constraints: Vec<Constraint>,
}
```

**约束:**

1. `default_mode` 必填
2. `expose` 为**非空**多值集合
3. 复杂媒体值与外部引用值默认只允许 `ParamValueMode::Constant(<空值>)`
4. `Json` 与 `Path` 允许非空 `Constant` 默认值
5. `constraints` 为列表,允许同时携带多条规则

### §2.5.1 ParamValueMode —— 静态值 / 动画曲线 / 表达式(targetv2 新增)

**这是 targetv2 相对 target 的核心差异之一。** 让参数从"静态常量"升级为"可能随 CookingContext 变化的值"。

```rust
enum ParamValueMode {
    /// 静态常量值(默认模式,与 target 时代一致)
    Constant(Value),

    /// 动画曲线 —— DaVinci / Nuke / AE 风格的 keyframed 参数
    /// Curve 采样依据当前 CookingContext 的 context_key 维度
    Animated(Curve),

    /// 表达式 —— TD / Nuke 风格的 Python / 自定义表达式
    /// [占位] 首版结构保留,具体语法和求值引擎未实现
    Expression(ExpressionAst),
}

struct Curve {
    /// 曲线所依赖的 CookingContext 维度(通常是 "frame")
    /// Planner 据此自动为节点加入 cooking_sensitivity,见 §2.5.2
    context_key: DimensionId,

    /// 关键帧列表(按 context_value 字典序存储)
    keyframes: Vec<Keyframe>,

    /// 曲线整体的插值方式(逐 keyframe 可在 Keyframe 里覆盖)
    interpolation: InterpolationType,
}

struct Keyframe {
    /// 该关键帧对应的 context 值(如 frame=42 对应 `DimensionValue::Int(42)`)
    context_value: DimensionValue,
    /// 关键帧的值(必须与所属 Curve 的 Param data_type 匹配)
    value: Value,
    /// 可选的 per-keyframe 插值覆盖(首版忽略,使用 curve 级设置)
    interpolation: Option<InterpolationType>,
}

enum InterpolationType {
    /// 常量跳跃(前一关键帧保持值直到下一关键帧)
    Constant,
    /// 线性插值(首版默认)
    Linear,
    /// [占位] 贝塞尔曲线,含 in/out tangent
    Bezier {
        in_tangent: (f32, f32),
        out_tangent: (f32, f32),
    },
    /// [占位] Catmull-Rom / Cardinal / TCB 等
    Smooth,
}

struct ExpressionAst {
    /// 表达式原始文本(供编辑器显示)
    raw: String,
    /// [占位] 解析后的 AST 结构,首版 None
    /// 未来:支持 `me.time.frame * 0.5 + param_ref("other.sigma")` 等
    compiled: Option<Box<dyn Expression>>,
}
```

**首版实现范围:**

- `ParamValueMode::Constant(Value)` —— **完整实现**,所有节点首版默认
- `ParamValueMode::Animated(Curve)` —— **首版最小可用**:
  - `InterpolationType::{Constant, Linear}` 支持
  - `Bezier` / `Smooth` 占位(解析字段但不实现曲线数学)
  - `keyframes` 列表按 `context_value` 排序查询
- `ParamValueMode::Expression(_)` —— **占位,运行时报错**

**采样函数(Planner 在 build_signature 时调用):**

```rust
impl ParamValueMode {
    /// 按当前 CookingContext 采样得到具体 Value
    pub fn sample(&self, ctx: &CookingContext) -> Value {
        match self {
            ParamValueMode::Constant(v) => v.clone(),
            ParamValueMode::Animated(curve) => curve.sample(ctx),
            ParamValueMode::Expression(_) => panic!("Expression not supported in first version"),
        }
    }

    /// 返回这个 mode 依赖的 DimensionId 集合(给自动 cooking_sensitivity 推导用)
    pub fn sensitivity(&self) -> Vec<DimensionId> {
        match self {
            ParamValueMode::Constant(_) => vec![],
            ParamValueMode::Animated(curve) => vec![curve.context_key.clone()],
            ParamValueMode::Expression(_) => vec![],  // 首版:表达式尚未分析
        }
    }
}

impl Curve {
    pub fn sample(&self, ctx: &CookingContext) -> Value {
        let current = ctx.dimensions.get(&self.context_key);
        match current {
            None => {
                // context 未提供该维度 —— 返回第一个 keyframe 的值
                self.keyframes.first()
                    .map(|k| k.value.clone())
                    .expect("Curve with no keyframes")
            }
            Some(value) => {
                // 查找包围当前 context_value 的前后 keyframe,按 interpolation 插值
                // (具体算法在 Planner 内实现)
                interpolate_between_keyframes(&self.keyframes, value, self.interpolation)
            }
        }
    }
}
```

### §2.5.2 自动 cooking_sensitivity 推导

**核心洞察:** 如果一个节点使用了 `Animated(curve)` 参数,它就**隐式地对该曲线的 context_key 维度敏感**——不需要节点作者手动在 `NodeDef.cooking_sensitivity` 里声明。

**Planner 在构造签名时,使用"有效 cooking_sensitivity"**:

```rust
// Planner 内部
fn effective_cooking_sensitivity(
    node_def: &NodeDef,
    node_instance: &Node,
) -> Vec<DimensionId> {
    let mut sensitivity = node_def.cooking_sensitivity.clone();

    // 遍历节点实例的参数,收集 Animated/Expression 参数隐含的 sensitivity
    for (_, mode) in &node_instance.params {
        for dim in mode.sensitivity() {
            if !sensitivity.contains(&dim) {
                sensitivity.push(dim);
            }
        }
    }

    sensitivity.sort();  // 稳定序
    sensitivity
}
```

**含义:**

- 作者写 `NodeDef` 时**不需要预判**哪些节点会有动画参数——默认 `cooking_sensitivity: vec![]`
- 用户在 UI 里把一个参数**从静态改为动画**时,Planner 自动计算出该节点对 `frame` 维度敏感
- 对应的 `ExecSignature` 包含 `cooking_context_hash`(基于 frame)—— 缓存自动分帧
- 未来用户把动画改回静态时,sensitivity 自动恢复空,cache 行为也恢复

**与 §2.4 的关系:** `NodeDef.cooking_sensitivity` 字段仍然保留——作者可以显式声明"对某个维度敏感"(例如 `load_frame_number` 节点本身对 `frame` 敏感,即使没有动画参数)。两者互补:

- `NodeDef.cooking_sensitivity` = **作者静态声明**(节点类型级别)
- 节点实例的动画参数 = **实例动态声明**(节点实例级别)

**自动推导发生在 Planner 的 `build_signature` 阶段**,不在 NodeRegistry 注册时——NodeRegistry 只存 NodeDef 的静态声明。

### §2.6 NodeDef

```rust
struct NodeDef {
    type_id: String,
    version: u32,
    source: NodeSourceKind,
    name: String,
    category: String,
    description: Option<String>,
    tags: Vec<String>,
    icon: Option<String>,

    // 执行归类
    executor_type: ExecutorType,        // 保留,作为 Capability 粗粒度分组
    requires: Vec<CapabilityId>,        // targetv2 新增:路由主键
    purity: Purity,
    cooking_sensitivity: Vec<DimensionId>, // targetv2 新增:本节点对哪些 CookingContext 维度敏感
    realtime_capable: bool,             // targetv2 M4 新增:是否能跟得上 Continuous 60fps 持续 cook

    // 接口
    inputs: Vec<InputPinDef>,
    outputs: Vec<OutputPinDef>,
    params: Vec<ParamDef>,

    // 策略
    execution: ExecutionPolicy,
}
```

**字段说明:**

- `category`: 使用路径字符串,如 `image/color`、`ai/generation`
- `tags`: 自由字符串数组
- `icon`: 保存规范化图标 id,而不是 GUI 资源对象
- **`executor_type`**: 保留作为 Capability 的粗粒度分组;**不是**路由主键
- **`requires`** (targetv2 新增): 节点声明需要的 Capability 集合,是 Runtime 路由的主键。详见 `0.1.4-capability.md`
- **`cooking_sensitivity`** (targetv2 新增): 节点声明对哪些 `DimensionId` 敏感。默认为空——空意味着节点对任何 CookingContext 维度**都不敏感**,`cooking_context_hash` 在签名中恒为 0。只有显式声明的维度才会被 Planner 纳入 hash 计算。这是"加新维度不破坏旧节点"的结构保障。详见 `0.1.3-cooking-context.md` §5
- **`realtime_capable`** (targetv2 M4 新增, 必填): 标记该节点是否能跟得上 60fps 持续 cook(`ExecutionMode::Continuous`)
  - **`true` (默认)**: GPU shader、本地算术、生成节点 —— 单次执行 <16ms
  - **`false`**: AI 推理 / API 调用 / 文件 I/O / 长时间运算
  - **行为差异**:
    - **OneShot 模式**(导出):该字段无效,所有节点正常执行
    - **Continuous 模式**(实时预览):Runtime 对 `realtime_capable=false` 的节点**不重新执行**;命中正式 cache 用缓存值,未命中发 `NodeMissingInContinuous` 事件 + 用占位输出
  - **典型节点分类**(首版):
    - `gaussian_blur` / `primary_color_grade` / `pixel_fluid_animation` / `ramp_gradient` / `levels` → `true`
    - `ai_video_generate` / `sdxl_inference` / `cloud_api_call` / `save_video` / `load_video`(seek) → `false`
    - `load_image` / 静态生成节点 → `true`
- `execution` 的正式定义见 `0.1.1-execution-models.md`

**`NodeDef` 负责:**

- 静态身份
- 执行归类(通过 `executor_type` + `requires`)
- 纯/非纯语义
- 静态输入输出
- 静态参数
- 默认执行策略
- 轻展示元数据

**`NodeDef` 不负责:**

- 动态参数 schema
- 参数显示位置
- GUI 渲染细节
- 运行时状态
- `MaterializationTarget` 信息

## §3 图模型层

### §3.1 Graph

```rust
struct Graph {
    nodes: HashMap<NodeId, Node>,
    connections: Vec<Connection>,
}
```

**约束:**

1. `Graph = (nodes, connections)`
2. `Graph` 是不可变值类型
3. `Graph` 不含任何布局信息
4. 图必须满足有向无环、类型匹配、单输入约束
5. **`Graph` 可以脱离 `Project` 独立存在**(CLI scratch / 单元测试 / 临时求值)

### §3.2 Node

```rust
struct Node {
    id: NodeId,
    type_id: String,
    params: HashMap<String, ParamValueMode>,  // targetv2: Value → ParamValueMode
}
```

- `type_id` 指向 `NodeDef.type_id`
- `params` 仅存实例级当前参数模式(Constant / Animated / Expression)
- 缺失的参数通过 `NodeDef.params` 的 `default_mode` 回退
- 布局、视口、选中态等不属于 `Node`

**首版默认**: 所有节点实例的参数都是 `ParamValueMode::Constant(value)`,与 target 时代行为一致。用户在 UI 里加 keyframe 时,参数升级为 `Animated(curve)`,去除 keyframe 时退回 `Constant`。

### §3.3 Connection

```rust
struct Connection {
    from_node: NodeId,

```

**约束:**

- 连接两端的数据类型必须兼容
- 单输入口最多一条入边
- 参数输入/输出接口若被暴露,应与普通引脚一起参与正式接口校验

## §4 节点统一注册框架

```rust
trait NodeSource {
    fn collect(&self) -> Vec<NodeRegistration>;
}

struct NodeRegistration {
    static_def: NodeDef,
    schema_provider: Option<Arc<dyn SchemaProvider>>,
    presentation_provider: Option<Arc<dyn PresentationProvider>>,
    capability_bindings: Vec<(CapabilityId, Arc<dyn Executor>)>,  // 可选
}
```

**约束:**

1. 所有节点来源统一产出 `NodeRegistration`
2. 一个来源可返回多个节点
3. `schema_provider` / `presentation_provider` 都是可选层,且按**节点类型**提供
4. `capability_bindings` 是可选的——如果来源层同时也自带执行器实现(例如 Python Provider 同时是 Capability 提供者),可以在注册时一起声明
5. 执行统一依赖 `NodeDef.requires` + `CapabilityRegistry`

**默认回退:**

- 无 `schema_provider` → 使用 `NodeDef.params`
- 无 `presentation_provider` → 使用统一默认展示规则
- 无 `capability_bindings` → 执行器从 `CapabilityRegistry` 的启动期注册中查询

**`NodeRegistry` façade:**

所有节点来源通过单一入口 **`NodeRegistry::register(source: impl NodeSource)`** 注册,不对外暴露其他扩展通道。这是真源 ② 的结构化保障。详见 `extensibility.md`。
