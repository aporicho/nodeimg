# 第一性原理重构架构

> 本文档不是对当前模块的微调，而是回答一个更上位的问题：**如果从产品目标而不是当前实现出发，nodeimg 应该长成什么样。**

> 它不直接替代 `architecture-invariants.md`、`0.1.0-models.md`、`0.1.1-execution-models.md`，而是作为目标架构思考文档，帮助后续判断哪些设计值得上升为真源，哪些只应视为阶段性实现。

---

## 1. 产品本质

nodeimg 的目标，不是“节点图编辑器”，而是：

> **面向图像、视频、音频、矢量图形、设计排版的自动化设计工作室引擎。**

这意味着它至少同时承载 5 类能力：

1. **媒体处理**：图像 / 视频 / 音频；
2. **图形与排版**：矢量图形、模板、版式参数；
3. **自动化编排**：批处理、序列帧、参数化生产；
4. **AI 增强**：生成、理解、重写、辅助设计；
5. **可追溯生产**：缓存、产物历史、项目保存、版本选用。

因此，节点图只是它的**自动化逻辑层**，不是整个产品本体。

---

## 2. 第一性原理下的三类对象

### 2.1 语义真相

定义“系统中的世界是什么”的对象，应保持稳定：

- 数据类型与运行时值
- 节点静态契约
- 图模型
- 执行身份与缓存身份

在 nodeimg 中，对应：

- `DataType`（数据类型，DataType）/ `Value`（值，Value）
- `NodeDef`（节点定义，NodeDef）/ `Pin` / `Param`
- `Graph`（图，Graph）/ `Node` / `Connection`（连线，Connection）
- `ExecutionRequest`（执行请求，ExecutionRequest）/ `ExecSignature`（执行签名，ExecSignature）/ `CacheKey`（缓存键，CacheKey）

### 2.2 闭环骨架

完整负责一个系统性问题的模块，骨架应稳定：

- 调度器：决定执行什么
- 缓存：决定结果如何复用
- 产物：决定哪些结果成为正式版本
- 项目：决定哪些状态被持久化

这些模块可以演进，但其**职责边界、共享模型、默认规则**不应频繁摇摆。

### 2.3 可插拔适配层

回答“外界如何接入系统”的对象，应做成扩展点：

- 节点来源
- 动态参数 schema（参数结构，schema）
- 展示规则
- 执行器

在 nodeimg 中，对应：

- `NodeSource`
- `SchemaProvider`（动态参数提供器，SchemaProvider）
- `PresentationProvider`（展示提供器，PresentationProvider）
- `Executor`（执行器，Executor）

## 3. 从零设计时的目标分层

如果不受当前实现约束，推荐采用 6 层架构。

### 第 1 层：Workspace / Product Layer

工作室层，面向用户完整工作流：

- 项目
- 模板
- 批次队列
- 审阅与导出
- 资产浏览
- 生成结果管理

这层定义“产品是什么”，而不是“节点怎么执行”。

### 第 2 层：Project / Asset Layer

项目与资产容器层：

- 项目文档
- 资产引用
- 产物版本
- 资产库
- 布局信息
- 用户设置

关键思想：

> **项目是工作内容容器，图只是其中一个执行视图。**

### 第 3 层：Graph Definition Layer

图定义层，只表达自动化逻辑：

- `NodeDef`
- `Graph`
- `Node`
- `Connection`
- 参数、引脚、约束
- 类型系统

这一层**不包含**：

- GUI 布局
- 执行状态
- 缓存值
- 产物文件路径

### 第 4 层：Planner / Execution Runtime Layer

这是从零设计时与当前方案最大的差异点。

#### Planner（规划器，Planner）

负责：

- 依赖分析
- 子图解析
- 批处理 / 序列语义
- map（映射，map）/ zip（并行配对，zip）/ broadcast（广播，broadcast）
- 增量失效与执行计划构建

#### Runtime（运行时，Runtime）

负责：

- 具体执行节点
- 取消与进度
- 缓存读写
- 产物落地

关键思想：

> **批次、序列、广播等语义更像规划规则，不应散落在每个执行器内部。**

### 第 5 层：Capability Providers Layer

能力提供层，向运行时声明“谁能做什么”。

从第一性原理看，执行器不应只按“图像 / AI / API”三类划分，而应按能力划分，例如：

- `Raster`（栅格处理，Raster）
- `Vector`（矢量处理，Vector）
- `Layout`（排版，Layout）
- `MediaDecode`（媒体解码，MediaDecode）
- `AIInference`（AI 推理，AIInference）
- `Http`（网络请求，Http）
- `FileIO`（文件输入输出，FileIO）

现实折中可以保留较粗的执行器类别，但内部应尽量向能力模型靠拢。

### 第 6 层：UI / Interaction Layer

界面与交互层：

- 画布
- Inspector（检查面板，Inspector）
- 预览器
- 时间轴
- 资产面板
- 队列控制台

关键思想：

> **节点画布只是工作室交互的一部分，不是唯一交互中心。**

## 4. 从零设计时的核心对象

### 4.1 AssetType 与 Value 分层

从零设计时，我会先区分：

- **AssetType**：业务语义上的资产种类
- **Value**：运行时求值载体

示意：

- `RasterImage`
- `Video`
- `Audio`
- `VectorGraphic`（矢量图形，VectorGraphic）
- `JsonData`
- `Text`
- `PathRef`（路径引用，PathRef）
- `RemoteHandle`（远端句柄，RemoteHandle）
- `LayoutDocument`（版式文档，LayoutDocument）

这样做的原因：

- 资产库、项目文件、产物历史、导出系统更关注“资产类型”；
- 执行期更关注“运行时值”。

若全部压成一个 `Value` 模型，后续做版本管理和资产系统会比较吃力。

### 4.2 List 语义上升到规划层

我仍会保留：

- `DataType = Atomic(T) | List(T)`

但会把：

- 单值提升
- 列表广播
- 逐帧 map
- 序列对齐

从“执行器特殊行为”提升为**规划层规则**。这样媒体序列能力更干净，也更接近未来视频/批处理方向。

---

## 5. 与当前方案相比的三个关键变化

### 5.1 执行器从“类别”走向“能力”

当前更像：

- 图像执行器
- AI 执行器
- API 执行器

从零设计时，我会把它抽象成：

- 能力集合 + 执行器绑定

这样新增 `VideoExecutor`（视频执行器，VideoExecutor）、`AudioExecutor`（音频执行器，AudioExecutor）、`VectorExecutor`（矢量执行器，VectorExecutor）、`LayoutExecutor`（排版执行器，LayoutExecutor）时，不必推翻总框架。

### 5.2 批次/序列语义从执行器中上提

当前关于 `List<Image>`（图像列表，List<Image>）的讨论，很多是执行层语义。更理想的做法是：

- 这些语义由 Planner 统一解释
- 执行器只负责“对单个已规划任务求值”

### 5.3 项目 / 资产层比图层更重要

当前思路仍较“图引擎中心”。从零设计时，我会让：

- 项目
- 资产
- 产物
- 模板

先成为一等对象，图只是自动化逻辑层。

## 6. 现实中的最小演进路径

上述从零架构不意味着当前项目要推翻重来。更现实的演进路径是：

### 第一步：保留现有稳定本体

继续保留并完善：

- `NodeDef`
- `Graph`
- `ExecutionPolicy`
- `NodeSource`
- `ExecSignature`

### 第二步：引入 Planner 语义文档

把当前关于：

- `List<T>`
- 单值提升
- 序列帧
- map / zip / 显式广播节点

逐步从执行模型中抽到单独的**规划语义层**。

### 第三步：把执行器文档从“类别思维”迁移到“能力思维”

短期内可以仍保留 `executor_type`（执行器类型，executor_type），但文档上应明确：

- 首版类别 != 终局能力模型

### 第四步：把项目 / 产物 / 资产分层做实

逐步强化：

- Project（项目）
- Artifact（产物）
- Asset Library（资产库）

的不同职责，而不是都压在图和缓存周围。

## 7. 设计法则

从第一性原理出发，我会用下面 4 条判断哪些东西该稳定、哪些该扩展：

### 法则 1：定义世界的，优先稳定

若某个对象在回答“系统中的世界是什么”，它应更稳定。

### 法则 2：形成闭环职责的，骨架先稳定

调度器、缓存、产物、项目这类模块，应先稳定职责边界与共享模型，再谈扩展。

### 法则 3：主要以新增成员变化的，设计成扩展点

如：

- 新原子类型
- 新节点来源
- 新执行器
- 新展示方式

### 法则 4：默认推导优先于全面显式配置

若某类规则对大多数对象都有可接受默认，应采用：

- 默认推导
- 少数覆盖

而不是要求所有节点都显式配置全部策略。

---

## 8. 最终一句话

如果从零设计，nodeimg 不应只是“节点图工具”，而应是：

> **项目 / 资产驱动的自动化设计引擎，节点图负责逻辑编排，规划层负责批次与序列语义，执行层按能力扩展，缓存/产物/项目形成稳定运行骨架。**

这份文档的用途，是帮助当前项目判断：哪些设计值得上升为长期目标架构，哪些只是当前实现阶段的妥协。
