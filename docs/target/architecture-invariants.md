# 架构不变量

> 所有 target 文档的前置真源清单。任何引擎接口变更必须能追溯到本文档的某一条真源,否则视为真源清单不完整,应先补真源再改接口。

---

## §0 本文档的地位

本文档列出 nodeimg 引擎的"最底层决议"——它们不是任何单个模块的设计,而是所有模块设计的**前置条件**。

**地位:**

- 是 `0.x.x`、`4.x.x` 所有文档的前置引用。
- 若某条真源发生变更,所有引用它的下游文档必须同步更新。
- 若某个接口变更无法追溯到本文档的某一条真源,说明真源清单不完整,应先补真源再改接口——**不允许绕过**。

**不是什么:**

- 不是模块设计文档,不承载任何具体接口或字段定义。
- 不是 changelog,不记录增量;它记录的是"一旦定下就不应轻易动"的决议。
- 不替代 `0.0.2-module-contract-template.md` 的模块契约模板;两者互补——模板约束"单模块如何写",真源约束"所有模块的共同前提"。

## §1 三层心智模型

```
┌─────────────────────────────────────────────┐
│ 第 -1 层 · 公理层                            │
│   A. 数据公理  DataType 闭集 + Value 身份    │
│   B. 计算公理  节点 = (Inputs,Params)→Outputs│
│                分纯 / 非纯                    │
│   C. 组合公理  Graph 有向无环、类型匹配、     │
│                不可变值类型                   │
└─────────────────────────────────────────────┘
                    ↓ 决定
┌─────────────────────────────────────────────┐
│ 第  0 层 · 真源层(7 条,见 §2)               │
│   ① 责任边界   ② 抽象模式   ③ 数据模型      │
│   ④ 图模型      ⑤ 节点模型  ⑥ 执行模型     │
│   ⑦ 持久化边界                              │
└─────────────────────────────────────────────┘
                    ↓ 派生
┌─────────────────────────────────────────────┐
│ 第  1 层 · 派生层                            │
│   NodeDef / Graph / ExecutionRequest /      │
│   ExecutionOutputs / EngineEvent /          │
│   ExecSignature / CacheKey / 各模块接口     │
└─────────────────────────────────────────────┘
```

**公理层**回答"系统代表什么",**真源层**回答"系统谁负责什么",**派生层**回答"接口长什么样"。三层的责任不同,**不允许混淆**。

公理层一旦更改,真源层和派生层必须同步重审;真源层一旦更改,派生层必须同步重审;派生层变更不回溯影响上层。

## §2 七条真源

每条真源按统一模板描述:

```
① 定义         一句话
② 状态         已冻结 / 部分冻结 / 待确认
③ 权威文档     真正装载细节的 .md 路径
④ 连锁影响     改这条会推倒的模块
⑤ 反证/风险    不冻结会出什么事
⑥ 变更门槛     是否允许普通 PR、必须同步哪些文档
```

### 真源 ① · 责任边界

| 字段 | 内容 |
|------|------|
| **定义** | 引擎内外、各子模块之间的状态所有权归属。谁拥有状态,谁负责变更。 |
| **状态** | 已冻结 |
| **权威文档** | `0.0.2-module-contract-template.md` §全局设计约束 第 1/3/4 条;`4.x.x` 各模块文档的"职责边界"章节 |
| **连锁影响** | GraphController、Scheduler、各 Executor、ProjectManager、ArtifactManager 的接口表 |
| **反证/风险** | **历史教训**:`move_node` 反复返工的根因不是代码质量问题,而是"布局归不归引擎管"一直没写死。责任边界模糊 → 同一行为在不同模块里各实现一遍 → 接口反复重写。 |
| **变更门槛** | 必须先改本文档 + `0.0.2`;普通 PR 不得直接变更责任归属。新增模块时必须显式声明其责任边界。 |

**当前已冻结的责任决议**(引用自 `0.0.2` §全局设计约束,本文档是其上位约束):

1. 布局不属于引擎(归 GUI)。
2. 调度器驱动缓存回源,而不是执行器。
3. 执行器完成计算并返回 `Value`,**不执行任何持久化 I/O**。是否将输出持久化为 `Artifact` 由 Scheduler 依据 `ArtifactPolicy` 判定,`ArtifactManager` 负责实际写入。执行器无落盘权限,也不感知其输出是否会被登记为产物。
4. Provider 属于 APIExecutor,不是独立模块;但其 `param_schema()` 能力作为公共只读接口,允许 NodeManager 间接查询,以便为 API 节点展开动态参数(这不构成所有权破例——查询走单向只读路径,Provider 的生命周期与写入仍由 APIExecutor 独占)。

### 真源 ③ · 数据模型

| 字段 | 内容 |
|------|------|
| **定义** | `DataType` 是**闭集枚举**(新增即破坏性变更);`Value` 本体是否拥有稳定的全局身份(hash / equality)由本真源回答。**如何利用这些身份构造执行签名**属于真源 ⑥,两者不重叠。 |
| **状态** | **待确认** —— `DataType` 封闭性虽然事实成立,但未在 `0.1.0-models.md` 明文声明;`Value` 的身份性质完全未定义。 |
| **权威文档** | `0.1.0-models.md`(待补) |
| **连锁影响** | `Value → PinDef → NodeDef → Connection 类型匹配 → ExecSignature → Cache → Artifact → 所有 Executor` 整条下游链 |
| **反证/风险** | **最高风险**:`Value::Image` 可同时是 CPU bitmap 或 GPU texture。若硬要对 `Value` 本体做 hash,只有两种选择:hash 字节 → GPU 回读性能灾难;hash handle → 相同内容的两次独立产出 hash 不等,缓存命中率崩塌。唯一的出路是**拒绝**给 `Value` 定义全局 hash,由签名系统(真源 ⑥)间接表达身份。 |
| **变更门槛** | 任何新增 `DataType` 或更改 `Value` 的 hash / equal 语义均为破坏性变更,须显式 changelog + 引擎版本升级。 |

**待明文冻结的子项**(见 §3):

- `DataType` 是封闭枚举,新增走破坏性流程。
- `Value` **本体不提供全局可比的 hash 或 equality**。含 GPU 资源或大数据块的 `Value`(如 `Value::Image`)的"身份"不由自身字节决定,而是由**其来源节点的执行签名**间接表达。这是由真源 ⑥ 具体落实的下游契约。

### 真源 ⑤ · 节点模型

| 字段 | 内容 |
|------|------|
| **定义** | `NodeDef` 是瘦核心;`purity`(纯 / 非纯)是 `NodeDef` 的独立字段,**不绑定在 `executor_type` 上**;动态参数由 Provider 通过 `param_schema()` 提供,不硬编码进 `NodeDef`。 |
| **状态** | **已冻结**(待 `0.1.0` 落地)—— purity 独立字段、二元值域、作者标注机制、ArtifactPolicy 默认行为均已拍板;`0.1.0-models.md` 代码层面尚未同步。 |
| **权威文档** | `0.1.0-models.md`;`4.4.0-node-manager.impl.md`;`4.3.0-node.draft.md` |
| **连锁影响** | 所有 Executor、Scheduler 路由、Cache 签名决策、Auto 模式触发策略、ArtifactPolicy |
| **反证/风险** | 如果 `purity` 保持绑定在 `executor_type`,未来出现"本地确定性 AI 节点"(同输入必同输出)或"随机噪声 Image 节点"(无 seed)时,既有规则无法表达,必须回头拆分,连带 Scheduler 的 Auto/Manual 判据重写。 |
| **变更门槛** | `NodeDef` 静态字段新增可走普通 PR(附 `0.1.0` 同步更新);但涉及 `purity`、`executor_type`、`param_schema()` 语义的变更必须先改本文档。 |

**已冻结子项:**

- **`purity` 的值域固定为二元**:`Pure | Impure`。首次在 `0.1.0-models.md` 落地时,必须以二元枚举形式写死(例如 `enum Purity { Pure, Impure }`),不得留作"开放 enum 待扩展"或"字符串标签"。未来若需细分(如 `ImpureDeterministic`、`ImpureStochastic`),视为破坏性变更,须先改本文档 + `0.1.0`,而不是顺手加枚举项。此项标记为"关闭扩展路径",阻止静默扩展。

- **`purity` 判定源 = `NodeDef` 必填字段,由节点作者手动标注**。引擎**不推断**、**不按 `executor_type` 给默认值**、**不读执行历史反推**;所有新节点在 `NodeDef` 注册时必须显式声明 `Pure` 或 `Impure`,否则注册失败。这是"让 purity 真正独立于 `executor_type`"的唯一可靠实现路径——任何形式的"默认值"或"自动推断"都会悄悄重新把 purity 耦合到别的字段上。

- **`ArtifactPolicy` 默认行为**:`purity = Impure` 的节点默认登记为 `Artifact`;`purity = Pure` 的节点默认**不**登记,仅进执行缓存。**导出型节点**(如 `save_image`,具有文件 I/O 副作用)**不靠 `purity` 判定**,凭其副作用属性独立触发登记,该类别的具体定义与判据由 `4.6.0-artifact.draft.md` 负责。这一默认规则意味着:新增一种 Impure 节点 = 自动进入产物历史系统,不需要额外声明;新增一种纯副作用节点 = 必须在 `4.6.0` 里注册为"导出型"。

### 真源 ⑥ · 执行模型

| 字段 | 内容 |
|------|------|
| **定义** | `ExecutionRequest / ExecutionOutputs` 的形状固定;取消粒度 = **run 级 + node 级**;single-flight(同一时刻最多一个活动执行)。**语义签名与缓存键严格分离**:`ExecSignature`(语义签名)= 上游签名传递闭包 + 本节点参数 hash,**不含 generation、不 hash `Value` 本体**;`CacheKey`(缓存键)= `(NodeId, OutputPin, ExecSignature, generation)`,generation 仅作为防回灌(anti-staleness)的并发守卫。 |
| **状态** | **已冻结**(待 `0.1.1` 落地)—— 请求 / 输出形状、single-flight、取消粒度、`ExecSignature` 与 `CacheKey` 分离、generation 触发集、hash 算法均已拍板;`0.1.1-execution-models.md` 代码层面尚未同步。 |
| **权威文档** | `0.1.1-execution-models.md`;`4.1.0-scheduler.impl.md`;`4.11.2-executor-contract.impl.md` |
| **连锁影响** | Scheduler、CacheManager、ArtifactManager、所有 Executor、EngineFacade 的 `execute / cancel_execution / get_execution_state` 接口 |
| **反证/风险** | **高风险 A**:`ExecSignature` 若包含 `Value` 的字节 hash → GPU 回读造成 order-of-magnitude 性能损失;若 hash handle → 缓存命中率崩塌。<br>**高风险 B**:若把 generation 并入 `ExecSignature`,则每次 cache clear / 项目切换都会导致所有签名失效,同一语义的等价计算无法跨 generation 复用——等于把签名从"计算身份"降级成"内存地址"。两种错误都是"写错了完全不报错,只是缓存慢慢失效"的静默踩坑。 |
| **变更门槛** | 任何涉及执行请求形状、取消粒度、`ExecSignature` 构造、`CacheKey` 构造的变更,必须先改本文档 + `0.1.1` + `4.11.2`。 |

**已冻结子项:**

- 取消粒度 = run 级 + node 级。
- single-flight:同一时刻最多一个活动执行。
- **语义签名与缓存键分离**:`ExecSignature` 纯粹回答"这是哪次语义计算",与 generation 无关;generation 只在 `CacheKey` 层存在,其作用是拒绝带旧 generation 的 in-flight 写入(并发守卫),不参与命中判定。同一语义在不同 generation 下的 `ExecSignature` **必须相同**——这是故意的,以便 cache clear / 项目切换后仍能复用等价计算。
- `ExecSignature` = 上游签名的传递闭包 + 本节点参数 hash;不 hash `Value` 本体。
- **`generation +1` 的触发集严格限定为 `{clear_cache, replace_graph}`**。其他所有操作——undo / redo、节点增删、参数改动、连线调整、节点配置变化——**一律不触发** generation bump,而是走正常的签名失效路径(签名变了,自然不命中)。目的是**缩小"鬼结果"的触发面**,避免正常编辑期间的 in-flight 异步执行被误伤作废。
- **`ExecSignature` 的 hash 算法首版选定 `xxHash3-128`**:吞吐约 20 GB/s、128 位宽度、碰撞概率可忽略。非密码学场景,不需要防攻击。换算法视为破坏性变更——须先改本文档 + `0.1.1`,并接受既有缓存全部失效(因为旧签名与新签名位宽或值域不可比)。

## §3 最优先"静默踩坑"冻结点

以下 3 条**藏在**真源 ③⑤⑥ 里,但它们是整份文档里**最容易被无声踩坑**的决策。写错不会立刻报错,也不会被 review 发现,只会表现为"缓存命中率慢慢下降"或"某类节点永远无法表达"。单独列出以强调:

| # | 冻结点 | 归属真源 | 必须明文的内容 |
|---|--------|----------|----------------|
| ① | **`DataType` 封闭 / 开放** | 真源 ③ | `DataType` 是封闭枚举;新增一种 `DataType` 即破坏性变更,须显式 changelog |
| ② | **`ExecSignature` 身份语义** | 真源 ⑥ | `ExecSignature` = 上游签名传递闭包 + 本节点参数 hash;**不对 `Value` 本体做 hash**;**generation 不参与签名**,仅作为 `CacheKey` 层的防回灌守卫 |
| ③ | **`purity` 独立于 `executor_type`** | 真源 ⑤ | `NodeDef` 必须有独立 `purity` 字段;`executor_type` 只决定分发路由,不决定纯性 |

这 3 条必须在第一版就写死,否则后续任何模块文档都可能"按当时的默认值"做出不可逆的假设。

## §4 文档维护规则

### 4.1 三种事实标记

本文档及所有 target 文档必须区分三类内容:

| 标记 | 含义 | 使用规则 |
|------|------|----------|
| **既有决议** | 已有明确出处的决策(某次讨论、某个 PR、某份文档) | 默认状态,无需标记 |
| **推断** | 作者根据上下文推出的、未经显式确认的结论 | 必须以"推断:..."开头,或加 `[推断]` 前缀 |
| **待确认** | 已识别但尚未决议的问题 | 必须以"待确认:..."开头,或加 `[待确认]` 前缀 |

**绝不允许把推断冒充既有决议写入文档。**历史上多次返工源于此类混淆。

### 4.2 真源变更流程

当某条真源需要变更时,必须按顺序执行:

1. **先改本文档**:说明变更原因、新旧差异、版本号递增。
2. **同步权威文档**:更新该真源"权威文档"字段列出的所有 `.md`。
3. **补 changelog**:在 `roadmap.md` 或专门的 changelog 文件中记录变更。
4. **审查下游派生层**:逐一检查该真源影响的模块接口是否需要同步变更。

**反向流程被明令禁止:不允许先改某个模块接口,再倒推修改真源。**

### 4.3 PR 引用规则

所有涉及引擎接口的 PR,描述中必须包含以下之一:

- **`该变更属于真源 ⑤ 的派生层调整`**:说明属于派生层变更,无需改真源。
- **`该变更须先改真源 ③`**:说明需要先改真源,PR 应先分拆。
- **`该变更无法追溯到任何真源,应先补真源`**:说明真源清单不完整,PR 应暂缓。

Reviewer 必须验证引用的真源确实对应,不得放行无真源追溯的接口变更。
